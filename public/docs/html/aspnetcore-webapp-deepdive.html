MODULE 1Layout กลางและโครงหน้าเว็บ
3-4 วัน
ทำไมต้องมี: ถ้าไม่มี layout กลาง ทุกหน้าเว็บต้องคัดลอกเมนู header/footer ซ้ำทุกไฟล์ แก้เมนู 1 ครั้งต้องไปแก้ทุกหน้า Layout คือการเขียน "โครงที่ใช้ร่วมกัน" ไว้ครั้งเดียว

ไฟล์ Layout อยู่ที่ Pages/Shared/_Layout.cshtml ถูกสร้างมาให้อัตโนมัติตั้งแต่สร้างโปรเจกต์ ทุกหน้าที่สร้างขึ้นจะ "ใช้" layout นี้โดยอัตโนมัติ

โครงสร้างของ _Layout.cshtml
<!DOCTYPE html>
<html>
<head>
    <title>@ViewData["Title"]</title>
</head>
<body>
    <header>
        <nav>
            <a asp-page="/Index">หน้าแรก</a>
            <a asp-page="/Products">สินค้า</a>
        </nav>
    </header>

    <main>
        @RenderBody()
    </main>

    <footer>
        <p>&copy; 2026 บริษัทของเรา</p>
    </footer>
</body>
</html>
ความหมายของ syntax สำคัญ

@RenderBody() — จุดที่เนื้อหาของแต่ละหน้า (เช่น Products.cshtml) จะถูก "แทรก" เข้ามา พูดง่ายๆ คือ layout เป็นกรอบ ส่วน @RenderBody() คือช่องว่างตรงกลางที่เปลี่ยนไปตามหน้าที่เปิดอยู่

@ViewData["Title"] — ตัวแปรพิเศษที่แต่ละหน้าตั้งชื่อ title ของตัวเองได้ (ตั้งค่าจากในไฟล์ .cshtml ของแต่ละหน้าด้วย @{ ViewData["Title"] = "รายการสินค้า"; })

asp-page="/Products" — Tag Helper ที่ผูกลิงก์ไปยัง Razor Page ชื่อ Products โดยไม่ต้องพิมพ์ URL ตรงๆ ถ้าเปลี่ยนโครงสร้าง route ทีหลัง ลิงก์จะยังถูกต้องเสมอ

Partial View — แยกชิ้นส่วนที่ใช้ซ้ำในหลายหน้า

ถ้ามีบางส่วนของหน้าเว็บ (ไม่ใช่ทั้งหน้า) ที่ใช้ซ้ำในหลายที่ เช่น การ์ดแสดงสินค้า 1 ชิ้น แยกออกมาเป็น Partial View ได้:

<!-- Pages/Shared/_ProductCard.cshtml -->
@model Product

<div class="card">
    <h3>@Model.Name</h3>
    <p>@Model.Price บาท</p>
</div>
<!-- เรียกใช้จากหน้าอื่น -->
@foreach (var product in Model.Products)
{
    <partial name="_ProductCard" model="product" />
}
แบบฝึกหัด: แก้ _Layout.cshtml ของโปรเจกต์ฝึกให้มีเมนูลิงก์ไปหน้า Products และ Orders แล้วแยกการ์ดแสดงสินค้าออกเป็น Partial View ตามตัวอย่าง
ดูเฉลย
เพิ่มลิงก์ในส่วน nav ของ _Layout.cshtml: 
<nav>
    <a asp-page="/Index">หน้าแรก</a>
    <a asp-page="/Products/Index">สินค้า</a>
    <a asp-page="/Orders/Index">ออเดอร์</a>
</nav>
สร้างไฟล์ Pages/Shared/_ProductCard.cshtml ตามตัวอย่างในเนื้อหา แล้วเปลี่ยนโค้ดที่ foreach แสดงสินค้าเดิม (ที่เคย print ด้วย @foreach ตรงๆ) ให้เรียก <partial name="_ProductCard" model="product" /> แทน ผลลัพธ์ควรแสดงผลเหมือนเดิมทุกประการ ต่างแค่โค้ดถูกแยกไฟล์ออกมา
MODULE 2Navigation และ Route ที่ซับซ้อนขึ้น
2-3 วัน
  • ส่งค่าผ่าน URL แบบมี parameter (เช่น /Products/Detail/5)
  • Route ที่มีหลายระดับ (nested route)
  • Redirect ไปหน้าอื่นพร้อมส่งข้อความแจ้งเตือน
รับค่าจาก URL แบบมี parameter

สร้างไฟล์ที่: Pages/Products/Detail.cshtml (ฝั่งหน้าตา)

@page "{id:int}"
@model DetailModel

<h1>@Model.Product?.Name</h1>
<p>ราคา: @Model.Product?.Price บาท</p>
<a asp-page="Index">← กลับไปหน้ารายการ</a>

สร้างไฟล์ที่: Pages/Products/Detail.cshtml.cs (ฝั่ง logic)

public class DetailModel : PageModel
{
    private readonly AppDbContext _db;
    public DetailModel(AppDbContext db) { _db = db; }

    public Product? Product { get; set; }

    public async Task<IActionResult> OnGetAsync(int id)
    {
        Product = await _db.Products.FindAsync(id);
        if (Product is null)
        {
            return NotFound();
        }
        return Page();
    }
}

@page "{id:int}" — บอกว่า URL ของหน้านี้ต้องมีตัวเลขต่อท้าย เช่น /Products/Detail/5 ส่วน :int คือการบังคับว่าค่านั้นต้องเป็นตัวเลขเท่านั้น ถ้าใส่ตัวอักษรมาจะไม่ match route นี้เลย

Redirect พร้อมข้อความแจ้งเตือน (TempData)
public async Task<IActionResult> OnPostAsync()
{
    // ... บันทึกข้อมูลสำเร็จ ...
    TempData["Message"] = "บันทึกสินค้าเรียบร้อยแล้ว";
    return RedirectToPage("/Products/Index");
}
<!-- แสดงข้อความในหน้าที่ redirect ไป -->
@if (TempData["Message"] != null)
{
    <div class="alert">@TempData["Message"]</div>
}

TempData คือที่เก็บข้อมูลชั่วคราวที่ "อยู่ข้ามหน้า" ได้ 1 ครั้ง (ต่างจากตัวแปรปกติที่หายไปทันที ที่ redirect) เหมาะกับข้อความแจ้งเตือนแบบนี้โดยเฉพาะ

ข้อผิดพลาดที่เจอบ่อย: ลืมเช็ค Product is null หลัง FindAsync แล้วเอา Product ไปใช้ต่อทันที ถ้า id ที่ส่งมาไม่มีอยู่จริงในฐานข้อมูล จะได้ null กลับมา แล้วโปรแกรม error ทันทีที่พยายามอ่าน property ของ null (เรียกว่า NullReferenceException) ต้องเช็คก่อนเสมอ
แบบฝึกหัด: สร้างหน้า Detail ที่รับ id จาก URL ตามตัวอย่าง แล้วลิงก์จากหน้า list สินค้า ไปหน้า Detail ของแต่ละชิ้น
ดูเฉลย
ในหน้า list สินค้า เพิ่มลิงก์ไปหน้า Detail พร้อมส่ง id: 
@foreach (var product in Model.Products)
{
    <a asp-page="/Products/Detail" asp-route-id="@product.Id">@product.Name</a>
}
asp-route-id คือ Tag Helper ที่เติมค่า id ต่อท้าย URL ให้อัตโนมัติ ตรงกับ {id:int} ที่ประกาศไว้ใน @page ของหน้า Detail พอคลิกลิงก์จะไปที่ URL เช่น /Products/Detail/3 แล้ว OnGetAsync(int id) จะได้ id เท่ากับ 3 ไปดึงข้อมูลสินค้าตัวนั้นมาแสดง
MODULE 3ฟอร์มและ Validation แบบเต็มรูปแบบ
4-5 วัน
  • Data Annotation — attribute สำหรับกำหนดกฎ validation บน model
  • แสดงข้อความ error ใต้แต่ละ field
  • validation ฝั่ง client (ก่อน submit) แบบไม่ต้องเขียน JavaScript เอง
กำหนดกฎ validation บน Model
public class Product
{
    public int Id { get; set; }

    [Required(ErrorMessage = "กรุณากรอกชื่อสินค้า")]
    [StringLength(100, ErrorMessage = "ชื่อสินค้าต้องไม่เกิน 100 ตัวอักษร")]
    public string Name { get; set; } = string.Empty;

    [Range(1, 1000000, ErrorMessage = "ราคาต้องอยู่ระหว่าง 1 ถึง 1,000,000")]
    public decimal Price { get; set; }

    [EmailAddress(ErrorMessage = "รูปแบบอีเมลไม่ถูกต้อง")]
    public string? SupplierEmail { get; set; }
}

[Required], [StringLength], [Range], [EmailAddress] คือ Data Annotation attribute ที่กำหนดกฎไว้ที่ตัว Model โดยตรง ASP.NET Core จะเช็คให้อัตโนมัติทั้งฝั่ง server และช่วยแสดงข้อความเตือนฝั่ง client ด้วย โดยไม่ต้องเขียนเช็คเองทีละ field

แสดงข้อความ error ในฟอร์ม
<form method="post">
    <label>ชื่อสินค้า</label>
    <input asp-for="NewProduct.Name" />
    <span asp-validation-for="NewProduct.Name" class="error-text"></span>

    <label>ราคา</label>
    <input asp-for="NewProduct.Price" />
    <span asp-validation-for="NewProduct.Price" class="error-text"></span>

    <button type="submit">บันทึก</button>
</form>

@section Scripts {
    <partial name="_ValidationScriptsPartial" />
}

asp-validation-for — Tag Helper ที่แสดงข้อความ error ของ field นั้นโดยอัตโนมัติ ถ้า validation ไม่ผ่าน (ดึงข้อความจาก ErrorMessage ที่ตั้งไว้บน Model)

_ValidationScriptsPartial — ไฟล์สำเร็จรูปที่มากับ template อยู่แล้ว เปิดใช้งาน validation แบบ real-time ก่อน submit (client-side validation) โดยไม่ต้องเขียน JavaScript เอง

ข้อผิดพลาดที่เจอบ่อย: เขียน Data Annotation บน Model แล้วลืมเช็ค ModelState.IsValid ใน OnPost ทำให้ข้อมูลที่ไม่ผ่านกฎ validation ถูกบันทึกลงฐานข้อมูล ไปแล้วโดยไม่รู้ตัว (client-side validation ป้องกันได้แค่กรณีปกติ แต่ป้องกันคนตั้งใจ bypass ไม่ได้ ต้องเช็คฝั่ง server เสมอ)
แบบฝึกหัด: เพิ่ม Data Annotation ให้ Model Product ครบทุก field ที่เหมาะสม แล้วทดสอบ submit ฟอร์มโดยเว้นช่องชื่อว่างไว้ ดูว่าข้อความ error แสดงถูกต้องไหม
ดูเฉลย
public class Product
{
    public int Id { get; set; }

    [Required(ErrorMessage = "กรุณากรอกชื่อสินค้า")]
    [StringLength(100)]
    public string Name { get; set; } = string.Empty;

    [Range(1, 1000000, ErrorMessage = "ราคาต้องมากกว่า 0")]
    public decimal Price { get; set; }
}
ถ้าเว้นช่องชื่อว่างแล้ว submit ต้องเห็นข้อความ "กรุณากรอกชื่อสินค้า" ปรากฏใต้ช่อง input โดยที่หน้าเว็บ "ไม่ reload" เลยด้วยซ้ำ (เพราะ client-side validation ดักไว้ก่อนส่งจริง) ถ้ายังไม่เห็นข้อความ error ให้เช็คว่าใส่ <span asp-validation-for="..."> คู่กับทุก input และมี _ValidationScriptsPartial อยู่ท้ายไฟล์แล้วหรือยัง
MODULE 4ข้อมูลที่เชื่อมกันหลาย Table (Relationship)
5-6 วัน
ทำไมต้องมี: ระบบจริงแทบไม่มี table เดียวโดดๆ เช่น 1 ออเดอร์มีสินค้าหลายชิ้น 1 ลูกค้ามีหลายออเดอร์ ต้องรู้วิธีออกแบบและ query ข้อมูลที่เชื่อมกันแบบนี้
  • ความสัมพันธ์แบบ one-to-many (หนึ่งลูกค้า มีหลายออเดอร์)
  • Foreign Key — คีย์ที่เชื่อมสอง table เข้าด้วยกัน
  • ดึงข้อมูลที่เชื่อมกันมาแสดงพร้อมกันด้วย Include
ออกแบบ Model ที่เชื่อมกัน
public class Customer
{
    public int Id { get; set; }
    public string Name { get; set; } = string.Empty;

    // 1 ลูกค้า มีได้หลายออเดอร์
    public List<Order> Orders { get; set; } = new();
}

public class Order
{
    public int Id { get; set; }
    public decimal TotalAmount { get; set; }

    // Foreign Key — บอกว่าออเดอร์นี้เป็นของลูกค้าคนไหน
    public int CustomerId { get; set; }
    public Customer? Customer { get; set; }
}

CustomerId คือ Foreign Key เก็บ id ของลูกค้าเจ้าของออเดอร์นี้ ส่วน Customer? Customer คือ "navigation property" ที่ทำให้เขียนโค้ดเข้าถึงข้อมูลลูกค้าจากออเดอร์ได้โดยตรง (เช่น order.Customer.Name) โดย EF Core จัดการ join table ให้เองเบื้องหลัง

ดึงข้อมูลที่เชื่อมกันมาแสดงพร้อมกัน
// ถ้าไม่ใช้ Include, order.Customer จะเป็น null เสมอ
var orders = await _db.Orders
    .Include(o => o.Customer)
    .ToListAsync();

foreach (var order in orders)
{
    Console.WriteLine(order.Customer.Name + " — " + order.TotalAmount);
}

.Include(o => o.Customer) คือการบอก EF Core ว่า "ตอน query Order ให้ดึงข้อมูล Customer ที่เกี่ยวข้องมาด้วยเลย" ถ้าลืมเขียนบรรทัดนี้ order.Customer จะเป็น null เสมอ แม้ในฐานข้อมูลจะมีข้อมูลลูกค้าจริงก็ตาม เพราะ EF Core ไม่ดึงข้อมูลที่เชื่อมกันมาให้อัตโนมัติ ต้องสั่งชัดเจนทุกครั้ง

แสดงข้อมูลที่เชื่อมกันบนหน้าเว็บ (ฝั่งหน้าตา)

แก้ไขไฟล์ที่: Pages/Orders/Index.cshtml (หน้า list ออเดอร์ที่เคยทำไว้ เพิ่มคอลัมน์แสดงชื่อลูกค้า)

<table>
    <tr><th>ลูกค้า</th><th>ยอดรวม</th></tr>
    @foreach (var order in Model.Orders)
    {
        <tr>
            <td>@order.Customer?.Name</td>
            <td>@order.TotalAmount บาท</td>
        </tr>
    }
</table>

ฝั่งหน้าตาไม่ต้องรู้เลยว่าเบื้องหลังมีการ Include ยังไง แค่เรียก @order.Customer?.Name เหมือน property ธรรมดาของ order ปกติ — เครื่องหมาย ? สำคัญตรงนี้เพราะถ้า PageModel ลืม Include (จาก pitfall ด้านบน) หน้าเว็บจะไม่ error แต่แสดงช่องว่างแทนชื่อลูกค้าแทน

ข้อผิดพลาดที่เจอบ่อยที่สุดในหัวข้อนี้: ลืม Include แล้วงงว่าทำไมข้อมูลที่เชื่อมกัน เป็น null ตลอด ทั้งที่ query สำเร็จไม่มี error ใดๆ เป็นปัญหาที่ทำให้เสียเวลา debug บ่อยที่สุดในหัวข้อนี้
แบบฝึกหัด: เพิ่ม Model Customer และผูกกับ Order ตามตัวอย่าง สร้าง migration ใหม่ แล้วทำหน้า list ออเดอร์ที่แสดงชื่อลูกค้าเจ้าของแต่ละออเดอร์ด้วย
ดูเฉลย
เพิ่ม DbSet ให้ AppDbContext ก่อน: 
public DbSet<Customer> Customers => Set<Customer>();
สร้าง migration: 
dotnet ef migrations add AddCustomerOrderRelation
dotnet ef database update
ใน PageModel ของหน้า list ออเดอร์ ต้องมี Include เสมอ ไม่งั้น Customer จะเป็น null: 
public async Task OnGetAsync()
{
    Orders = await _db.Orders.Include(o => o.Customer).ToListAsync();
}
แล้วในหน้า .cshtml แสดงด้วย @order.Customer?.Name (ใส่ ? กันไว้เผื่อกรณี ลืม Include หรือข้อมูลลูกค้าถูกลบไปแล้วจริงๆ จะได้ไม่ error ทันที)
MODULE 5ระบบ Login (Authentication / Authorization)
5-6 วัน
  • ความต่างระหว่าง Authentication (ยืนยันตัวตน) กับ Authorization (สิทธิ์การเข้าถึง)
  • ASP.NET Core Identity — ระบบ login สำเร็จรูปที่มากับ framework
  • จำกัดการเข้าถึงหน้าด้วย [Authorize]
Authentication vs Authorization: Authentication คือ "คุณเป็นใคร" (ล็อกอินสำเร็จหรือยัง) Authorization คือ "คุณทำอะไรได้บ้าง" (มีสิทธิ์เข้าหน้านี้ไหม) สองอย่างนี้แยกกันชัดเจน ล็อกอินสำเร็จ (authenticated) ไม่ได้แปลว่าเข้าได้ทุกหน้าเสมอไป
เพิ่ม ASP.NET Core Identity เข้าโปรเจกต์
dotnet add package Microsoft.AspNetCore.Identity.EntityFrameworkCore
// Program.cs
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlite("Data Source=app.db"));

builder.Services.AddDefaultIdentity<IdentityUser>(options =>
    options.SignIn.RequireConfirmedAccount = false)
    .AddEntityFrameworkStores<AppDbContext>();

// ...

app.UseAuthentication();   // ต้องมาก่อน UseAuthorization เสมอ
app.UseAuthorization();

AddDefaultIdentity<IdentityUser> — เปิดใช้ระบบ login สำเร็จรูปที่มีหน้า register/login/logout ให้พร้อมใช้ทันที ไม่ต้องเขียนเองตั้งแต่ศูนย์

app.UseAuthentication() ต้องอยู่ ก่อน app.UseAuthorization() เสมอใน middleware pipeline เพราะต้องรู้ก่อนว่า "ใครเข้ามา" ถึงจะเช็คต่อได้ว่า "เข้าได้ไหม" สลับลำดับผิดจะทำให้ authorization ทำงานไม่ถูกต้อง

จำกัดการเข้าถึงหน้า
[Authorize]
public class AdminModel : PageModel
{
    // เฉพาะคนที่ login แล้วเท่านั้นที่เข้าหน้านี้ได้
    // ถ้ายังไม่ login จะถูก redirect ไปหน้า login อัตโนมัติ
}
[Authorize(Roles = "Manager")]
public class ReportsModel : PageModel
{
    // เฉพาะคนที่มี role "Manager" เท่านั้น
}
แบบฝึกหัด: เพิ่ม Identity เข้าโปรเจกต์ฝึก ทดลอง register ผู้ใช้ใหม่ 1 คน login เข้าใช้งาน แล้วใส่ [Authorize] ที่หน้า Create สินค้า ทดสอบว่าคนที่ยังไม่ login เข้าหน้านั้นไม่ได้จริง
ดูเฉลย
ติดตั้งและตั้งค่าตามตัวอย่างในเนื้อหา จากนั้นเปิด URL /Identity/Account/Register (หน้านี้มาให้พร้อมกับ AddDefaultIdentity โดยไม่ต้องสร้างเอง) กรอกอีเมลและรหัสผ่านเพื่อสมัคร จากนั้นเพิ่ม attribute บนไฟล์ Create.cshtml.cs: 
[Authorize]
public class CreateModel : PageModel
{
    // ...
}
ทดสอบโดยเปิด browser แบบ Incognito/Private (เพื่อไม่ให้มี session login เดิมค้างอยู่) แล้วพิมพ์ URL ของหน้า Create ตรงๆ ควรถูก redirect ไปหน้า login อัตโนมัติ ถ้ายังเข้าได้ตรงๆ แปลว่าลืมใส่ app.UseAuthentication() ก่อน app.UseAuthorization() ใน Program.cs

ส่ง event จากลูกกลับไปแม่
@* ProductRow.razor — component ลูก *@
<tr>
    <td>@Product.Name</td>
    <td><button @onclick="HandleDelete">ลบ</button></td>
</tr>

@code {
    [Parameter] public Product Product { get; set; } = default!;
    [Parameter] public EventCallback<int> OnDelete { get; set; }

    private async Task HandleDelete()
    {
        await OnDelete.InvokeAsync(Product.Id);
    }
}
@* ProductList.razor — component แม่ *@
@foreach (var product in products)
{
    <ProductRow Product="product" OnDelete="HandleProductDeleted" />
}

@code {
    private async Task HandleProductDeleted(int productId)
    {
        var product = products.First(p => p.Id == productId);
        products.Remove(product);
        await Db.SaveChangesAsync();
    }
}

[Parameter] public EventCallback<int> OnDelete — ประกาศว่า component ลูกนี้ "ยิง event กลับไป" ให้ component แม่ฟังได้ พร้อมส่งค่า int (ในที่นี้คือ id) กลับไปด้วย เทียบได้กับการส่ง callback function เข้าไปเป็น props

Cascading Parameter — แชร์ค่าข้ามหลายชั้นโดยไม่ต้องส่งทีละชั้น
@* App.razor หรือ Layout หลัก *>
<CascadingValue Value="currentUser">
    @Body
</CascadingValue>

@code {
    private string currentUser = "Somchai";
}
@* component ลูกลึกแค่ไหนก็รับได้ โดยไม่ต้องส่งผ่าน parameter ทีละชั้น *>
@code {
    [CascadingParameter] public string CurrentUser { get; set; } = "";
}

มีประโยชน์มากเมื่อค่านั้นต้องใช้ในหลาย component ที่ซ้อนกันลึกมาก เช่น ข้อมูลผู้ใช้ที่ login อยู่ โดยไม่ต้องส่งผ่าน parameter ทีละชั้นซึ่งจะรกและแก้ยากถ้ามีหลายชั้นมาก

ข้อผิดพลาดที่เจอบ่อย: แก้ค่าตัวแปรใน method ที่ไม่ได้ผูกกับ event ของ Blazor โดยตรง (เช่น callback จาก JavaScript หรือ Timer) แล้ว UI ไม่อัพเดทให้ ต้องเรียก StateHasChanged() เองเพื่อบอก Blazor ว่า "ค่าที่แสดงผลเปลี่ยนแล้ว ให้วาดใหม่"
แบบฝึกหัด: แปลงหน้า list สินค้าให้แยกเป็น component ย่อย ProductRow ตามตัวอย่าง พร้อมปุ่มลบที่ยิง event กลับไปหา component แม่
ดูเฉลย
สร้างไฟล์ ProductRow.razor และ ProductList.razor ตามตัวอย่างในเนื้อหาทุกประการ จุดที่มักพลาดบ่อยคือ ลืมประกาศ [Parameter] หน้า property ที่รับค่าจากแม่: 
@code {

}

MODULE 7จัดการ Error และบันทึก Log
2-3 วัน

  • ILogger — ระบบบันทึก log มาตรฐานของ ASP.NET Core
  • หน้า error ที่เป็นมิตรกับผู้ใช้ (ไม่โชว์รายละเอียดทางเทคนิคให้ผู้ใช้ทั่วไปเห็น)
try/catch พื้นฐาน
public async Task<IActionResult> OnPostAsync()
{
    try
    {
        _db.Products.Add(NewProduct);
        await _db.SaveChangesAsync();
        return RedirectToPage("Index");
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "บันทึกสินค้าไม่สำเร็จ");
        ModelState.AddModelError("", "เกิดข้อผิดพลาด กรุณาลองใหม่อีกครั้ง");
        return Page();
    }
}

โค้ดใน try { } คือส่วนที่อาจพังได้ ถ้าพังจริงจะกระโดดไปทำใน catch { } ทันทีแทนที่จะทำให้ทั้งโปรแกรมล่ม เราจับ error ไว้ บันทึก log แล้วแสดงข้อความที่เข้าใจง่ายให้ผู้ใช้แทน

ILogger — inject เข้ามาใช้เหมือน service อื่น
public class ProductsModel : PageModel
{
    private readonly ILogger<ProductsModel> _logger;

    public ProductsModel(ILogger<ProductsModel> logger)
    {
        _logger = logger;
    }

    public void OnGet()
    {
        _logger.LogInformation("มีคนเปิดหน้า Products ตอน {time}", DateTime.Now);
    }
}

ระดับของ log มีหลายแบบ: LogInformation (ข้อมูลทั่วไป), LogWarning (สิ่งผิดปกติแต่ไม่ร้ายแรง), LogError (error จริง) เลือกใช้ตามความรุนแรงของเหตุการณ์

แบบฝึกหัด: เพิ่ม try/catch ในทุก OnPost ที่บันทึกข้อมูลลงฐานข้อมูลในโปรเจกต์ฝึก พร้อม log error เมื่อเกิดปัญหา
ดูเฉลย
เพิ่ม ILogger เข้า constructor ของ PageModel ที่มี OnPost ทุกไฟล์ ตามตัวอย่างในเนื้อหา แล้วครอบโค้ด บันทึกข้อมูลเดิมด้วย try/catch: 
public async Task<IActionResult> OnPostAsync()
{
    try
    {
        _db.Products.Add(NewProduct);

MODULE 8เตรียม Deploy ขึ้นใช้งานจริง
2-3 วัน
  • ความต่างระหว่าง Development และ Production environment
  • เก็บค่าลับ (connection string, API key) อย่างปลอดภัย
  • Build ไฟล์พร้อม deploy
แยกค่า config ตาม environment
appsettings.json              // ค่ากลาง ใช้ทุก environment
appsettings.Development.json  // ค่าเฉพาะตอนพัฒนา (เช่น database ทดสอบ)
appsettings.Production.json   // ค่าเฉพาะตอนใช้งานจริง (เช่น database จริง)

ASP.NET Core จะเลือกอ่านไฟล์ตาม environment ปัจจุบันโดยอัตโนมัติ ค่าใน environment-specific file จะ "ทับ" ค่าจาก appsettings.json กลาง

ข้อควรระวังสำคัญ: ห้ามใส่ connection string หรือ password จริงลงใน appsettings.json แล้ว commit ขึ้น git โดยเด็ดขาด เพราะใครก็เห็นได้ ควรใช้ User Secrets (ตอนพัฒนา) หรือ Environment Variables (ตอน deploy จริง) แทน: 
dotnet user-secrets init
dotnet user-secrets set "ConnectionStrings:Default" "Server=...;Password=..."
Build สำหรับ deploy
dotnet publish -c Release -o ./publish

ได้โฟลเดอร์ publish ที่มีไฟล์พร้อมนำไปวางบน server จริง (IIS, Docker, หรือ hosting อื่น) รายละเอียดการตั้งค่า server ปลายทางเป็นหัวข้อเฉพาะทางที่ควรวางแผนแยกอีกเอกสารเมื่อรู้ว่าจะ deploy ไปที่ไหนจริง

แบบฝึกหัด: ย้าย connection string ของโปรเจกต์ฝึกออกจาก appsettings.json ไปเก็บด้วย User Secrets แทน แล้วรัน dotnet publish ดูว่าได้โฟลเดอร์ publish ออกมาจริง
ดูเฉลย
dotnet user-secrets init
dotnet user-secrets set "ConnectionStrings:Default" "Data Source=app.db"
ลบบรรทัด connection string ออกจาก appsettings.json (หรือเปลี่ยนเป็นค่าว่าง) โค้ดที่อ่านค่า builder.Configuration.GetConnectionString("Default") จะยังทำงานได้ปกติตอน develop เพราะ .NET จะไปอ่านจาก User Secrets โดยอัตโนมัติเมื่อ environment เป็น Development จากนั้นรัน 
dotnet publish -c Release -o ./publish
ตรวจว่ามีโฟลเดอร์ publish เกิดขึ้นพร้อมไฟล์ .dll และ appsettings.json (ที่ไม่มี connection string จริงติดไปด้วย ปลอดภัยกว่าเดิม)

ทำไมต้องมี: เว็บแอปที่เปิดให้คนอื่นใช้งาน (โดยเฉพาะระบบภายในที่มีข้อมูลบริษัท) เป็นเป้าหมายของการโจมตี 3 แบบที่พบบ่อยที่สุดเสมอ ASP.NET Core ป้องกันให้อัตโนมัติในหลายจุด แต่ต้องรู้ว่าจุดไหนป้องกันเอง จุดไหนต้องระวังเอง
XSS (Cross-Site Scripting) — แทรก script ผ่านข้อมูลที่ผู้ใช้กรอก

ถ้าผู้ใช้กรอกชื่อเป็น <script>alert('hacked')</script> แล้วระบบเอาไปแสดงตรงๆ โดยไม่ป้องกัน script นั้นจะรันจริงในเบราว์เซอร์ของคนอื่นที่มาดูหน้านั้น

<!-- ปลอดภัย — Razor encode ให้อัตโนมัติเสมอเมื่อใช้ @ -->
<p>@product.Name</p>

<!-- อันตราย — Html.Raw ข้าม encode ทำให้ script รันได้จริง -->
<p>@Html.Raw(product.Name)</p>

Razor Pages เข้ารหัส (encode) ข้อความที่แสดงด้วย @ ให้อัตโนมัติเสมอ ตัวอักษรอย่าง < จะกลายเป็น &lt; ทำให้ browser แสดงเป็นข้อความธรรมดา ไม่รันเป็นโค้ด ใช้ Html.Raw เฉพาะตอนมั่นใจ 100% ว่าข้อมูลนั้นปลอดภัยจริงเท่านั้น (เช่น เนื้อหาที่แอดมินเขียนเอง ไม่ใช่ input จากผู้ใช้ทั่วไป)

CSRF (Cross-Site Request Forgery) — หลอกให้ browser ส่ง request แทนเรา

ถ้าเรา login เว็บแอปไว้แล้วเผลอเปิดเว็บอันตรายในแท็บอื่น เว็บนั้นอาจแอบสั่ง submit ฟอร์มไปยัง เว็บแอปของเราโดยที่เราไม่รู้ตัว (เพราะ browser แนบ cookie login ไปให้อัตโนมัติ)

<!-- Tag Helper ของ ASP.NET Core แทรก anti-forgery token ให้อัตโนมัติ -->
<form method="post">
    <input asp-for="NewProduct.Name" />
    <button type="submit">บันทึก</button>
</form>
<!-- ไม่ต้องเขียนอะไรเพิ่ม แค่ใช้ <form> ธรรมดา ASP.NET Core แทรก token ที่มองไม่เห็นให้เอง -->

ทุกฟอร์มที่สร้างผ่าน Razor Pages ปกติ (ไม่ใช้ raw HTML form ที่เขียนเองทั้งหมด) จะมี anti-forgery token แทรกมาให้อัตโนมัติอยู่แล้ว server จะเช็ค token นี้ทุกครั้งที่ submit ถ้าไม่ตรงจะปฏิเสธ request ทันที

SQL Injection — แทรกคำสั่ง SQL ผ่านข้อมูลที่กรอก
// ปลอดภัย — EF Core แปลง LINQ เป็น parameterized query ให้อัตโนมัติเสมอ
var product = await db.Products
    .Where(p => p.Name == userInput)
    .FirstOrDefaultAsync();

// อันตรายมาก — เอา userInput มาต่อ string ตรงๆ
var sql = "SELECT * FROM Products WHERE Name = '" + userInput + "'";
// ถ้า userInput คือ  ' OR '1'='1  จะดึงข้อมูลทั้ง table ออกมาหมด

ตราบใดที่ใช้ LINQ ผ่าน EF Core ตามปกติ (ไม่เขียน raw SQL เอง) จะปลอดภัยจาก SQL Injection โดยอัตโนมัติ เพราะ EF Core ไม่เคยเอาค่าจากผู้ใช้มาต่อ string ตรงๆ แต่ส่งเป็น parameter แยกเสมอ ถ้าจำเป็นต้องเขียน raw SQL จริงๆ (เช่น query ซับซ้อนมาก) ต้องใช้ FromSqlInterpolated ไม่ใช่ต่อ string เอง

ข้อผิดพลาดที่เจอบ่อย: ใช้ Html.Raw เพราะอยากให้ HTML ที่ผู้ใช้กรอกแสดงผลสวยงาม (เช่น bold, italic) โดยไม่ผ่านการกรองก่อน วิธีที่ถูกต้องคือใช้ library กรอง HTML ที่อนุญาตเฉพาะ tag ปลอดภัย (เช่น HtmlSanitizer) ไม่ใช่ปล่อยผ่านทั้งหมด
แบบฝึกหัด: ทดลองกรอกชื่อสินค้าเป็น <b>ทดสอบ</b> ในฟอร์มของโปรเจกต์ฝึก แล้วดูว่าหน้า list แสดงเป็นตัวหนาจริงไหม หรือแสดงเป็นข้อความ <b>...</b> ตรงๆ (ควรเป็นแบบหลัง เพราะ Razor encode ให้อัตโนมัติ)
ดูเฉลย
ถ้าใช้ @product.Name ตามปกติ หน้าเว็บควรแสดงข้อความ <b>ทดสอบ</b> ตรงตัว (ไม่ตัวหนา) เพราะ Razor เข้ารหัสเครื่องหมาย < > ให้เป็นข้อความธรรมดาไปแล้ว นี่คือพฤติกรรมที่ถูกต้องและปลอดภัย ถ้าอยากทดสอบด้านตรงข้าม ลองเปลี่ยนเป็น @Html.Raw(product.Name) ชั่วคราว จะเห็นว่าคำว่า "ทดสอบ" กลายเป็นตัวหนาจริง — นั่นคือช่องโหว่ที่ต้องหลีกเลี่ยงในโค้ดจริง ห้ามใช้ Html.Raw กับข้อมูลที่มาจากผู้ใช้โดยไม่กรองก่อน
MODULE 10Performance และ Caching
3-4 วัน
ทำไมต้องมี: พอเว็บแอปมีข้อมูลเยอะขึ้นหรือคนใช้พร้อมกันมากขึ้น การ query ฐานข้อมูลซ้ำๆ โดยไม่จำเป็น ทำให้ช้าลงเรื่อยๆ Caching คือการ "จำผลลัพธ์ไว้ใช้ซ้ำ" แทนที่จะไปถามฐานข้อมูลใหม่ทุกครั้ง
AsNoTracking — เร็วขึ้นสำหรับ query ที่แค่อ่านอย่างเดียว
// ปกติ EF Core จะ "ติดตาม" การเปลี่ยนแปลงของทุกแถวที่ query มา เผื่อจะ Update ทีหลัง
var products = await db.Products.ToListAsync();

// ถ้ารู้แน่ชัดว่าแค่อ่านอย่างเดียว ไม่แก้ไข ปิดการติดตามได้ เร็วขึ้นและกินหน่วยความจำน้อยลง
var products = await db.Products.AsNoTracking().ToListAsync();

ใช้ AsNoTracking() กับทุก query ที่เอาไว้แค่แสดงผล (เช่นหน้า list, report) เก็บไว้เฉพาะ query ที่จะเอาผลลัพธ์ไปแก้ไขแล้ว SaveChanges ต่อเท่านั้นที่ต้อง track

In-Memory Cache — จำผลลัพธ์ไว้ในหน่วยความจำ
// Program.cs
builder.Services.AddMemoryCache();
public class ProductsModel : PageModel
{
    private readonly IMemoryCache _cache;
    private readonly AppDbContext _db;

    public ProductsModel(IMemoryCache cache, AppDbContext db)
    {
        _cache = cache;
        _db = db;
    }

    public async Task OnGetAsync()
    {
        Products = await _cache.GetOrCreateAsync("all-products", async entry =>
        {
            entry.SlidingExpiration = TimeSpan.FromMinutes(5);
            return await _db.Products.AsNoTracking().ToListAsync();
        });
    }
}

GetOrCreateAsync เช็คก่อนว่ามีค่าชื่อ "all-products" ใน cache อยู่ไหม ถ้ามีแล้วก็คืนค่าจาก cache ทันทีโดยไม่ query ฐานข้อมูลเลย ถ้ายังไม่มีถึงจะรัน query จริงแล้วเก็บผลลัพธ์ไว้ใน cache ต่อ SlidingExpiration คือ "ถ้าไม่มีใครเรียกใช้ cache นี้เกิน 5 นาที ให้ลบทิ้ง"

ข้อควรระวัง: ข้อมูลใน cache อาจ "เก่า" กว่าข้อมูลจริงในฐานข้อมูล ถ้ามีคนแก้ไขข้อมูลแต่ cache ยังไม่หมดอายุ คนอื่นจะยังเห็นข้อมูลเก่าอยู่ ต้องจำไว้ลบ cache (_cache.Remove("all-products")) ทุกครั้งที่มีการ Create/Update/Delete ข้อมูลนั้น ไม่งั้นข้อมูลที่แสดงจะไม่ตรงกับความจริง
ปัญหา N+1 Query — สาเหตุความช้าที่พบบ่อยที่สุด
// ผิด — query ฐานข้อมูล 1 ครั้งสำหรับ list + อีก 1 ครั้งต่อออเดอร์ (N+1 ครั้งรวม)
var orders = await db.Orders.ToListAsync();
foreach (var order in orders)
{
    var customer = await db.Customers.FindAsync(order.CustomerId);  // ยิง query ทุกรอบ loop
    Console.WriteLine(customer.Name);
}

// ถูก — Include ดึงมาครั้งเดียวพร้อมกันหมด
var orders = await db.Orders.Include(o => o.Customer).ToListAsync();

ถ้ามีออเดอร์ 100 รายการ โค้ดแบบผิดจะยิง query ไปฐานข้อมูลถึง 101 ครั้ง (1 ครั้งสำหรับ list + 100 ครั้งในลูป) ขณะที่ใช้ Include จะยิงแค่ 1-2 ครั้งเท่านั้น ต่างกันมากเมื่อข้อมูลเยอะขึ้น

แบบฝึกหัด: เพิ่ม caching ให้หน้า list สินค้าของโปรเจกต์ฝึก ตั้ง SlidingExpiration 2 นาที แล้วทดสอบว่าพอแก้ไขสินค้าแล้วกลับมาหน้า list ข้อมูลอัพเดทถูกต้องไหม (ถ้าไม่ถูก ต้องเพิ่มการลบ cache ในหน้า edit ด้วย)

MODULE 11เดินผ่านระบบเดียวครบทุกชั้น
4-5 วัน
ทำไมต้องมี: module ก่อนหน้าทั้งหมดสอนทีละหัวข้อแยกกัน module นี้เอาทุกอย่างมาเดินให้ดูพร้อมกันใน 1 feature เดียว — ตั้งแต่กดปุ่มบนหน้าเว็บ ไปจนถึงข้อมูลกลับมาแสดงผล เพื่อให้เห็นภาพว่าแต่ละชั้นเรียกกันยังไงจริงๆ

สมมติ feature: "อนุมัติออเดอร์" — พนักงานกดปุ่มอนุมัติที่หน้าเว็บ ระบบต้องเช็คสต๊อกสินค้าจาก API ภายนอกก่อน (เช่น IWS) ถ้าพอถึงบันทึกลงฐานข้อมูล ถ้าไม่พอแสดงข้อความเตือน

ชั้นที่ 1 — UI (Razor Page)
<!-- OrderApproval.cshtml -->
@page "{id:int}"
@model OrderApprovalModel

<h1>อนุมัติออเดอร์ #@Model.Order.Id</h1>

    <input type="hidden" asp-for="Order.Id" />

</form>

หน้าเว็บไม่รู้เรื่อง logic ข้างในเลย รู้แค่ว่ากดปุ่มแล้วเรียก OnPost แล้วอาจมีข้อความ error กลับมา แสดง — เป็นหน้าที่ของ "การแสดงผล" อย่างเดียว

ชั้นที่ 2 — PageModel (ตัวกลาง ไม่มี logic ธุรกิจ)
public class OrderApprovalModel : PageModel
{
    private readonly IOrderApprovalService _service;

    public OrderApprovalModel(IOrderApprovalService service)
    {
        _service = service;
    }

    public Order Order { get; set; } = default!;
    public string? ErrorMessage { get; set; }

    public async Task<IActionResult> OnPostAsync(int id)
    {
        var result = await _service.ApproveOrderAsync(id);

        if (!result.Success)
        {
            ErrorMessage = result.ErrorMessage;
            Order = await _service.GetOrderAsync(id);
            return Page();
        }

        return RedirectToPage("Index");
    }
}

PageModel แค่ "ส่งต่อ" งานไปให้ Service ทำ ไม่มี logic ธุรกิจอยู่ในนี้เลย (ไม่เช็คสต๊อกเอง ไม่คุย EF Core ตรงๆ) หน้าที่เดียวคือแปลงผลลัพธ์จาก Service ให้เป็นสิ่งที่หน้าเว็บแสดงได้

ชั้นที่ 3 — Service (business logic + คุยกับ external API)
public class OrderApprovalService : IOrderApprovalService
{
    private readonly AppDbContext _db;
    private readonly HttpClient _httpClient;   // ใช้เรียก external API เช่น IWS

    public OrderApprovalService(AppDbContext db, HttpClient httpClient)
    {
        _db = db;
        _httpClient = httpClient;
    }

    public async Task<ApprovalResult> ApproveOrderAsync(int orderId)
    {
        var order = await _db.Orders.FindAsync(orderId);

        // เรียก external API เช็คสต๊อกจริงก่อนอนุมัติ
        var response = await _httpClient.GetAsync($"https://iws.example.com/api/stock/{order.ProductId}");
        var stockInfo = await response.Content.ReadFromJsonAsync<StockInfo>();

        if (stockInfo!.Quantity < order.Quantity)
        {
            return new ApprovalResult { Success = false, ErrorMessage = "สต๊อกไม่พอ" };
        }

        order.Status = "Approved";
        await _db.SaveChangesAsync();
        return new ApprovalResult { Success = true };
    }
}

ชั้นนี้คือที่ที่ "งานจริง" เกิดขึ้น ทั้งคุยกับฐานข้อมูล (EF Core) และคุยกับระบบภายนอก (HttpClient เรียก IWS หรือ API อื่น) PageModel ไม่ต้องรู้เลยว่าข้างในเช็คสต๊อกยังไง รู้แค่ว่าเรียกแล้วได้ผลลัพธ์ success/fail กลับมา

ลงทะเบียนทุกชั้นใน Program.cs
builder.Services.AddHttpClient<IOrderApprovalService, OrderApprovalService>();
builder.Services.AddDbContext<AppDbContext>(o => o.UseSqlite("Data Source=app.db"));

AddHttpClient<TInterface, TImplementation> เป็นวิธีพิเศษที่ลงทะเบียนทั้ง Service และ HttpClient ที่ใช้ข้างในให้พร้อมกันในบรรทัดเดียว ปลอดภัยกว่าสร้าง new HttpClient() เองตรงๆ เพราะ .NET จัดการเรื่อง connection pool ให้อัตโนมัติ

สรุปภาพรวมที่ควรจำ: UI ไม่ควรรู้จัก DbContext หรือ HttpClient เลย, PageModel ไม่ควรมี business logic เอง (แค่ส่งต่อ), Service เท่านั้นที่คุยกับฐานข้อมูลและ external API โดยตรง การแยกแบบนี้ทำให้ ถ้าต้องเปลี่ยนวิธีเช็คสต๊อก (เช่นเปลี่ยนจาก IWS เป็นระบบอื่น) แก้แค่ใน Service จุดเดียว ไม่ต้องแตะ UI หรือ PageModel เลย
แบบฝึกหัด: ลองสร้าง feature เล็กๆ ที่มี 3 ชั้นแบบนี้ในโปรเจกต์ฝึก เช่น "ตรวจสอบราคาสินค้า จาก API ภายนอกก่อนบันทึกออเดอร์" (ใช้ API สาธารณะที่ทดสอบได้ฟรี เช่น jsonplaceholder.typicode.com แทน IWS จริงไปก่อน)
ดูเฉลย
โครงเหมือนตัวอย่างในเนื้อหาทุกประการ แค่เปลี่ยน URL ที่เรียกเป็น https://jsonplaceholder.typicode.com/posts/1 (คืนค่า JSON ตัวอย่างกลับมาเสมอ ใช้ฝึก HttpClient ได้โดยไม่ต้องมี API จริงของบริษัท) โครงสร้าง 3 ชั้นควรเป็น: Razor Page (ปุ่มกดตรวจสอบ) → PageModel (เรียก Service) → Service (เรียก HttpClient ไปยัง URL ข้างต้น แล้วแปลงผลลัพธ์ JSON กลับมา) ทดสอบว่ากดปุ่มแล้วเห็นข้อมูลจาก API จริงแสดงบนหน้าเว็บได้หรือไม่
MODULE 12Service Layer / Repository Pattern
4-5 วัน
ทำไมต้องมี: ถ้าเขียนทุกอย่าง (query database, business logic, validation) อยู่ใน PageModel โดยตรงแบบที่ทำมาตลอด พอโปรเจกต์ใหญ่ขึ้น PageModel แต่ละไฟล์จะยาวมากและซ้ำกันเยอะ Repository Pattern และ Service Layer คือวิธีจัดระเบียบให้แต่ละชั้นทำหน้าที่ของตัวเองชัดเจน
Repository — ห่อการคุยกับฐานข้อมูลไว้ในที่เดียว
public interface IProductRepository
{
    Task<List<Product>> GetAllAsync();
    Task<Product?> GetByIdAsync(int id);
    Task AddAsync(Product product);
    Task DeleteAsync(int id);
}

public class ProductRepository : IProductRepository
{
    private readonly AppDbContext _db;
    public ProductRepository(AppDbContext db) => _db = db;

    public async Task<List<Product>> GetAllAsync()
        => await _db.Products.AsNoTracking().ToListAsync();

    public async Task<Product?> GetByIdAsync(int id)
        => await _db.Products.FindAsync(id);

    public async Task AddAsync(Product product)
    {
        _db.Products.Add(product);
        await _db.SaveChangesAsync();
    }

    public async Task DeleteAsync(int id)
    {
        var product = await _db.Products.FindAsync(id);
        if (product is not null)
        {
            _db.Products.Remove(product);
            await _db.SaveChangesAsync();
        }
    }
}

Repository รู้เรื่อง EF Core อย่างเดียว ไม่มี business rule ใดๆ ปนอยู่ (เช่น ไม่เช็คว่าราคาต้อง มากกว่า 0 ตรงนี้ — นั่นเป็นหน้าที่ของ Service) ถ้าวันหนึ่งเปลี่ยนจาก EF Core ไปใช้เทคโนโลยีอื่น แก้แค่ไฟล์นี้ไฟล์เดียว โค้ดส่วนอื่นไม่กระทบเลย

Service — business logic ที่ใช้ Repository เป็นเครื่องมือ
public interface IProductService
{
    Task<List<Product>> GetAllAsync();
    Task<ServiceResult> CreateAsync(Product product);
}

public class ProductService : IProductService
{
    private readonly IProductRepository _repo;
    public ProductService(IProductRepository repo) => _repo = repo;

    public Task<List<Product>> GetAllAsync() => _repo.GetAllAsync();

    public async Task<ServiceResult> CreateAsync(Product product)
    {
        // business rule อยู่ตรงนี้ ไม่ใช่ใน Repository
        if (product.Price <= 0)
        {
            return ServiceResult.Fail("ราคาต้องมากกว่า 0");
        }

        await _repo.AddAsync(product);
        return ServiceResult.Ok();
    }
}

Service คือชั้นที่มี "กฎทางธุรกิจ" (business rule) เช่น เงื่อนไขการอนุมัติ, การคำนวณราคาพิเศษ ส่วน Repository มีหน้าที่แค่ "เก็บ/ดึงข้อมูล" ล้วนๆ การแยกสองอย่างนี้ทำให้ทดสอบ business rule ได้โดยไม่ต้องพึ่งฐานข้อมูลจริง (mock Repository แทนได้ตอนเขียน unit test)

PageModel หลังจัดระเบียบ — สั้นลงมาก
public class CreateModel : PageModel
{
    private readonly IProductService _service;
    public CreateModel(IProductService service) => _service = service;

    [BindProperty]
    public Product NewProduct { get; set; } = new();

    public async Task<IActionResult> OnPostAsync()
    {
        var result = await _service.CreateAsync(NewProduct);
        if (!result.Success)
        {
            ModelState.AddModelError("", result.ErrorMessage!);
            return Page();
        }
        return RedirectToPage("Index");
    }
}

เทียบกับตอนที่เขียนทุกอย่างใน PageModel ตรงๆ (แบบที่ทำมาตลอดในหัวข้อก่อนหน้า) โค้ดตรงนี้สั้นลงมาก และอ่านง่ายขึ้น เพราะ PageModel รู้แค่ "เรียก Service แล้วแปลผลลัพธ์เป็นหน้าจอ" เท่านั้น

ลงทะเบียนทั้งสองชั้นใน Program.cs
builder.Services.AddScoped<IProductRepository, ProductRepository>();
builder.Services.AddScoped<IProductService, ProductService>();
ข้อควรระวัง: ไม่ต้องรีบใช้ pattern นี้ตั้งแต่ต้นถ้าโปรเจกต์เล็กมาก (เช่นโปรเจกต์ฝึกที่ทำมาตลอด) การเพิ่มชั้น Repository/Service ให้กับระบบเล็กๆ อาจทำให้โค้ดซับซ้อนเกินความจำเป็น (over-engineering) pattern นี้คุ้มค่าที่สุดเมื่อโปรเจกต์เริ่มมี business rule เยอะขึ้น หรือมีทีมทำงานพร้อมกันหลายคน
แบบฝึกหัด: เลือกฟีเจอร์หนึ่งในโปรเจกต์ฝึก (เช่น การสร้างสินค้าใหม่) แล้วแยกออกเป็น Repository และ Service ตามตัวอย่าง เทียบดูว่า PageModel สั้นลงแค่ไหนจากก่อนแยก

ขั้นที่ 3 — สร้าง Model

สร้างไฟล์ที่: Models/Product.cs

namespace InventoryApp.Models;

public class Product
{
    public int Id { get; set; }

    [Required(ErrorMessage = "กรุณากรอกชื่อสินค้า")]
    [StringLength(100)]
    public string Name { get; set; } = string.Empty;

    [Range(0, 1000000)]
    public decimal Price { get; set; }

    public int StockQuantity { get; set; }
}

ต้องมี using System.ComponentModel.DataAnnotations; บนสุดของไฟล์ด้วย (เพื่อให้ใช้ [Required], [Range] ได้ ตามที่เรียนใน Module 3)

ขั้นที่ 4 — สร้าง DbContext

using Microsoft.EntityFrameworkCore;
using InventoryApp.Models;

namespace InventoryApp.Data;

public class AppDbContext : DbContext
{
    public AppDbContext(DbContextOptions<AppDbContext> options) : base(options) { }
    public DbSet<Product> Products => Set<Product>();
}

สร้างไฟล์ที่: Pages/Products/Index.cshtml.cs

using Microsoft.AspNetCore.Mvc.RazorPages;
using Microsoft.EntityFrameworkCore;
using InventoryApp.Data;
using InventoryApp.Models;

namespace InventoryApp.Pages.Products;

public class IndexModel : PageModel
{
    private readonly AppDbContext _db;
    public IndexModel(AppDbContext db) => _db = db;

    public List<Product> Products { get; set; } = new();

    public async Task OnGetAsync()
    {
        Products = await _db.Products.AsNoTracking().ToListAsync();
    }
}
จุดที่ผิดบ่อยที่สุด: namespace ในไฟล์ .cshtml.cs ต้องตรงกับตำแหน่งโฟลเดอร์จริงเสมอ ไฟล์ที่อยู่ใน Pages/Products/ ต้องมี namespace เป็น InventoryApp.Pages.Products ถ้าพิมพ์ผิดหรือ namespace ไม่ตรงกับโฟลเดอร์ ASP.NET Core จะหาไฟล์ไม่เจอและ error 404 ทั้งที่ไฟล์มีอยู่จริง

using Microsoft.AspNetCore.Mvc;
using Microsoft.AspNetCore.Mvc.RazorPages;
using InventoryApp.Data;
using InventoryApp.Models;

namespace InventoryApp.Pages.Products;

public class CreateModel : PageModel
{
    private readonly AppDbContext _db;
    public CreateModel(AppDbContext db) => _db = db;

    [BindProperty]
    public Product NewProduct { get; set; } = new();

    public IActionResult OnGet() => Page();

    public async Task<IActionResult> OnPostAsync()
    {
        if (!ModelState.IsValid) return Page();

        _db.Products.Add(NewProduct);
        await _db.SaveChangesAsync();
        return RedirectToPage("Index");
    }
}
