5. ทดสอบตาม acceptance criteria ที่เขียนไว้ ไม่ใช่ทดสอบแค่ "ดูเหมือนทำงาน"

MODULE 2Ticket 1 — เพิ่ม Filter ตามสถานะออเดอร์
2 วัน
TICKET #101
จาก: หัวหน้าฝ่ายขาย
"ขอฟิลเตอร์ในหน้ารายการออเดอร์ให้เลือกดูตามสถานะได้ (ทั้งหมด / รอชำระเงิน / ชำระแล้ว / ยกเลิก)"
ขั้น 1-2 — วิเคราะห์ requirement

คำที่ต้องเช็ค: "สถานะ" — ระบบปัจจุบันมี field Status ไหม? ถ้าไม่มี ต้องเพิ่มเข้าไปก่อนซึ่งกระทบ database (ต้อง migration)

Acceptance criteria ที่เขียนเอง:

✓ dropdown มี 4 ตัวเลือก (ทั้งหมด, รอชำระเงิน, ชำระแล้ว, ยกเลิก)
✓ เลือกแล้ว list กรองทันทีโดยไม่ reload หน้า
✓ ค่าเริ่มต้นคือ "ทั้งหมด" (เหมือนเดิมก่อนมี filter)
✓ ออเดอร์เดิมที่สร้างไว้ก่อนมี field Status ต้องแสดงในตัวเลือกที่เหมาะสม (ไม่หายไป)

ขั้น 3 — Impact analysis

ถ้าต้องเพิ่ม field Status ให้ Order: Shift+F12 ที่ class Order ดูว่ามีกี่ที่ที่ new Order() ซึ่งต้องกำหนด Status เริ่มต้นให้ด้วย จุดที่พลาดบ่อยคือลืมจุดสร้างออเดอร์ที่ซ่อนอยู่ในไฟล์ที่ไม่คาดคิด

ขั้น 4 — Implement (thin slice ก่อน)
// Models/OrderStatus.cs (ใหม่)
public enum OrderStatus { PendingPayment, Paid, Cancelled }

// Models/Order.cs (แก้)
public OrderStatus Status { get; set; } = OrderStatus.PendingPayment;
dotnet ef migrations add AddOrderStatus
dotnet ef database update

ประเด็นสำคัญ — ข้อมูลเดิม: ค่า default PendingPayment ที่ตั้งไว้ใน C# จะไม่ถูกใส่ให้แถวเก่าที่มีอยู่แล้วในฐานข้อมูลโดยอัตโนมัติ (ต้องดูว่า migration ที่ generate ให้ตั้ง default value ให้ database ด้วยหรือไม่ ถ้าไม่ตั้ง แถวเก่าอาจได้ค่า 0 ซึ่งตรงกับ PendingPayment เผอิญพอดีเพราะ enum ตัวแรก = 0 แต่ถ้าเรียงลำดับ enum ผิดในอนาคต ข้อมูลเก่าจะกลายเป็นสถานะผิดโดยไม่มีใครรู้ตัว)

ข้อควรจำ: อย่าเปลี่ยนลำดับหรือแทรกค่าใน enum กลางๆ หลังจากมีข้อมูลจริงในฐานข้อมูลแล้ว เพราะ EF Core เก็บ enum เป็นตัวเลข (0, 1, 2...) การแทรกค่าตรงกลางทำให้ตัวเลขของค่าเดิมเปลี่ยน ข้อมูลเก่าทั้งหมดจะแสดงสถานะผิดทันที ถ้าจำเป็นต้องเพิ่มค่าใหม่ ให้เพิ่มต่อท้ายเสมอ

2-3 วัน

"ขอปุ่ม Export รายการออเดอร์ที่กรองอยู่เป็น Excel หน่อย เอาไปทำรายงานต่อ"
วิเคราะห์ — คำที่ต้องจับสังเกต

"ที่กรองอยู่" — หมายถึง export เฉพาะข้อมูลที่กรองอยู่ตอนนี้ (ตามฟิลเตอร์จาก Ticket #101) ไม่ใช่ทั้งหมด ต้องส่งเงื่อนไขกรองไปด้วย ไม่ใช่ export ทุกแถวในตาราง

เตรียม package
dotnet add package ClosedXML
ทำเป็น Service แยก (ไม่ยัดใน component)

สร้างไฟล์ใหม่: Services/ExcelExportService.cs

using ClosedXML.Excel;

public class ExcelExportService
{
    public byte[] ExportOrders(IEnumerable<Order> orders)
    {
        using var workbook = new XLWorkbook();
        var sheet = workbook.Worksheets.Add("Orders");

        sheet.Cell(1, 1).Value = "เลขที่ออเดอร์";
        sheet.Cell(1, 2).Value = "ลูกค้า";
        sheet.Cell(1, 3).Value = "ยอดรวม";
        sheet.Cell(1, 4).Value = "สถานะ";

        int row = 2;
        foreach (var o in orders)
        {
            sheet.Cell(row, 1).Value = o.Id;
            sheet.Cell(row, 2).Value = o.Customer?.Name;
            sheet.Cell(row, 3).Value = o.TotalAmount;
            sheet.Cell(row, 4).Value = o.Status.ToString();
            row++;
        }

        using var stream = new MemoryStream();
        workbook.SaveAs(stream);
        return stream.ToArray();
    }
}

ทำไมแยกเป็น Service: ถ้าฝ่ายอื่นขอ export ตารางอื่นในอนาคต (เช่น รายการสินค้า) จะได้ใช้ pattern เดียวกันซ้ำได้ ไม่ต้องเขียนใหม่ทุกครั้ง และทดสอบแยกจาก UI ได้ง่าย

ดาวน์โหลดไฟล์ใน Blazor — ต้องพึ่ง JS Interop

MODULE 4Ticket 3 — เพิ่มสถานะออเดอร์ (กระทบหลายจุด)
3 วัน
TICKET #103
จาก: ฝ่ายคลังสินค้า
"อยากได้สถานะ 'จัดส่งแล้ว' เพิ่มเข้ามา และตอนกดจัดส่ง ให้ระบบตัดสต๊อกสินค้าจริงตอนนั้นเลย (ไม่ใช่ตอนสั่งซื้อ)"
ทำไม ticket นี้ยากกว่าสองอันแรก: ไม่ใช่แค่เพิ่ม enum อีกค่า แต่เปลี่ยน "จุดตัดสต๊อก" จากตอนสร้างออเดอร์ (ที่ทำไว้ใน Track A Module 4) ไปเป็นตอนจัดส่ง ซึ่งกระทบ business logic เดิมโดยตรง
Impact analysis ที่ต้องทำก่อนแก้

1. หาจุดที่ตัดสต๊อกอยู่ตอนนี้ (Shift+F12 ที่ StockQuantity) → เจอใน Transaction ของ Track A Module 4

2. ตัดสินใจ: ย้ายไปตัดตอนจัดส่ง แล้วตอนสร้างออเดอร์ควรทำอะไรแทน? (จอง/reserve สต๊อกไว้ก่อนไหม หรือปล่อยสั่งซื้อได้ไม่จำกัดจนกว่าจะตัดจริง?) — ต้องถามฝ่ายคลังกลับ เพราะ requirement ไม่ได้บอกชัด

3. ออเดอร์ที่ถูกสร้างไว้แล้วก่อนเปลี่ยน logic (สต๊อกถูกตัดไปแล้วตอนสั่ง) จะเกิดอะไรขึ้นถ้ากดจัดส่งแล้วตัดสต๊อกซ้ำอีกรอบ? = ตัดซ้ำสองเท่า ต้องมีแผนจัดการข้อมูลเดิมนี้

บทเรียนสำคัญ: การเปลี่ยน business rule ที่ฝังอยู่ในระบบมาแล้ว มักมี "ข้อมูลเก่าที่ทำตามกฎเดิม" ซ่อนอยู่เสมอ ต้องคิดเรื่อง data migration หรือ backward compatibility ก่อนลงมือแก้เสมอ ไม่ใช่แค่แก้ logic ใหม่แล้วจบ
MODULE 5Ticket 4 — Requirement กำกวม ต้องถามกลับ
1 วัน
TICKET #104
จาก: ผู้จัดการ
"ทำให้ระบบเร็วขึ้นหน่อย ตอนนี้ช้า"
ทักษะที่สำคัญมาก: requirement แบบนี้มีอยู่จริงในงานทุกที่ ห้ามเริ่มแก้โค้ดทันที ต้องถามกลับให้ได้ข้อมูลที่ทำงานต่อได้ก่อน
คำถามที่ควรถามกลับ (ตัวอย่าง)

1. "ช้า" ตรงหน้าไหน/ฟังก์ชันไหนเป็นหลัก? (หน้าเปิดช้า, กดบันทึกช้า, export ช้า?)

2. ช้าตลอดเวลา หรือช้าเฉพาะบางช่วง/บางข้อมูล? (เช่น เฉพาะตอนมีออเดอร์เยอะเกิน 1000 รายการ)

3. "เร็วพอ" คือกี่วินาที? (ต้องมีตัวเลขเป้าหมาย ไม่งั้นไม่รู้ว่าเมื่อไหร่ถึงจะเสร็จ)

4. เริ่มช้าตั้งแต่เมื่อไหร่? (ถ้าเพิ่งช้าลงหลังจากมีอะไรเปลี่ยนแปลง มักบอกสาเหตุได้ทันที)

ลองทำ: เขียนคำถามกลับสำหรับ requirement กำกวมอื่นๆ เช่น "ขอหน้าตาให้ทันสมัยขึ้น" หรือ "อยากได้รายงานที่ดูง่ายกว่านี้" ฝึกแปลง requirement กำกวมให้เป็นคำถามที่ตอบได้ชัดเจน
