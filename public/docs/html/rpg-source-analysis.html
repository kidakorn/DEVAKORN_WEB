วิเคราะห์ Source Code จริง — พบสถาปัตยกรรม IWS ทั้งระบบ

จาก 5 ไฟล์ที่ส่งมา พบว่าบริษัทไม่ได้เขียน RPG program แยกทุก endpoint แบบที่คิดไว้ แต่มี "เครื่องมือกลาง" ที่ generate JSON ให้อัตโนมัติจากตารางไหนก็ได้

🔑 การค้นพบสำคัญที่สุด: Generic JSON Engine

GENHANDHELD.SQLRPG และ MINPOP03.SQLRPG (APIDEV03_genJson) ไม่ใช่ RPG program เฉพาะของ endpoint ไหน — แต่เป็น service program กลางตัวเดียวที่ใช้ได้กับทุก endpoint รับ 3 พารามิเตอร์ (ชื่อ CL program, ชื่อ table, keys) แล้ว generate JSON ให้อัตโนมัติจาก column จริงของตาราง โดยไม่ต้องเขียน RPG ใหม่ทุกครั้งที่มี endpoint เพิ่ม

พูดง่ายๆ: CL program ต่างหากทำ business logic เฉพาะของแต่ละ endpoint (คิวรี่/join/filter) แล้วเขียนผลลัพธ์ลง QTEMP/<ชื่อไฟล์> — ส่วน RPG ตัวกลางแค่ "อ่านคอลัมน์ที่มีจริงแล้วแปลงเป็น JSON" ไม่สนใจว่าข้างในมี field อะไรบ้าง เพราะ query แบบ dynamic (SELECT COLUMN_NAME FROM QSYS2.SYSCOLUMNS)

สรุปแต่ละไฟล์

GENHANDHELD.SQLRPG เวอร์ชันแรก

บทบาท: Generic JSON generator ตัวแรก — รับ CL name + File name + Keys, เรียก CL, แล้ว query QSYS2.SYSCOLUMNS สร้าง JSON

ข้อสังเกต: มี comment ที่ถูก comment ออกเยอะ (โค้ดทดลอง), ยังไม่มีการป้องกัน column ซ้ำจากหลาย library

MINPOP03.SQLRPG (APIDEV03_genJson) เวอร์ชันปรับปรุง

บทบาท: เวอร์ชันปรับปรุงของ GENHANDHELD — โค้ดสะอาดขึ้น มี input validation, error handling ครบ (Monitor/On-Error), แก้บั๊กเรื่อง column ซ้ำด้วย WITH FirstLib CTE

วันที่: 23/12/'25 โดย M.KOMSAN — ล่าสุดกว่า GENHANDHELD

บทเรียนสำหรับ IWS clone: การใช้ CTE เลือก library แรกที่เจอ column ตรงกัน กันปัญหาตารางชื่อซ้ำหลาย schema — เทคนิคนี้เอาไปใช้ตอนจำลอง "auto-discover columns" ได้

MINPOP.SQLRPG Direct File Access

บทบาท: อ่านไฟล์ MINPOP โดยตรงแบบ keyed file (ไม่ผ่าน generic engine) — คืน array ของ employee (code+name) สูงสุด 9999 แถว

Field จริงที่พบ: cdinop (code), nminop (name) — สังเกตว่า ไม่ตรงกับ prefix convention มาตรฐาน (ควรเป็น CD/NM + ชื่อย่อ ไม่ใช่ CDINOP/NMINOP ที่ดูเหมือนต่อกับคำว่า "inop" ยังไม่แน่ชัดความหมาย — น่าจะเป็นชื่อเก่าก่อนบริษัทมี convention ปัจจุบัน)

Library: DEVDTALIB

GETMINPOP.SQLRPG PoC / Template

บทบาท: ตัวอย่าง service program สำหรับ IWS โดยเฉพาะ (GETEMPINFOWS) — ดูเหมือนเป็น PoC/เทมเพลตตัวอย่าง ไม่ใช่โค้ด production จริง (field ชื่อ EMPID, FNAME, LNAME, DEPT, POS เป็นชื่อทั่วไปไม่ตรง convention บริษัท)

มีประโยชน์เพราะ: โชว์วิธี build JSON string มือ (ไม่ผ่าน generic engine) พร้อม escape อักขระพิเศษ — pattern นี้เอาไปใช้เป็น fallback ได้ถ้าไม่อยากพึ่ง JSON_OBJECT

CHKASSY.SQLRPG Business Logic จริง (talinf)

บทบาท: ตรงกับ endpoint talinf ที่คุยกันมาตลอด! FetchAssemblyLot รับ Lot No. แล้ว join 5 ตารางเพื่อ resolve ชื่อ device/package/wafer

เทียบกับ Naming Convention ที่ทำไว้ก่อนหน้า

Field จริงที่เจอPrefixตรงกับตาราง convention ไหม
CNASSY, CNMARK, CNWEFRCN✅ ตรง — Character-type Number (Assembly/Mark/Wafer no.)
CDDEVC, CDDGRP, CDPAKG, CDWEFRCD✅ ตรง — Code
NMDEVC, NMPAKG, NMWEFRNM✅ ตรง — Name
QTSTKP, QTSTKSQT✅ ตรง — Quantity
CDWINPCD✅ ตรง — Code (WIP code)
cdinop, nminop (MINPOP.SQLRPG)-⚠️ ไม่ตรง pattern มาตรฐาน — อาจเป็นชื่อเก่าก่อนมี convention หรือย่อจาก "Employee/Operator" คนละแบบ

ยืนยันว่า naming convention ที่ทำไว้ก่อนหน้า (ตาราง 18 prefix) ใช้ได้จริงกับ 95% ของ field ที่เจอ — เก็บไว้เป็นมาตรฐานต่อได้เลย
