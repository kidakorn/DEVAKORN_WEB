HR · Purchase · Inventory

แผนสถาปัตยกรรม, workflow, และ ER diagram สำหรับต่อยอด iws-clone ให้เป็น AS400 Gateway กลาง ที่ทุกระบบธุรกิจเรียกใช้ร่วมกัน

01 · ภาพรวมสถาปัตยกรรม

iws-clone เปลี่ยนบทบาทเป็น "AS400 Gateway"

ทุกเว็บระบบใหม่ไม่ต่อ ODBC/itoolkit เอง แต่เรียกผ่าน Gateway ตัวเดียวที่มีอยู่แล้ว — ข้อมูลทั้งหมดเก็บบน AS400 ที่เดียว ไม่ต้องมี database แยก

flowchart LR
  HR["HR Web"] --> GW["iws-clone Gateway"]
  PUR["Purchase Web"] --> GW
  INV["Inventory Web"] --> GW
  GW --> AS400[("AS400 / pub400")]

All-on-AS400 — กฎสำคัญที่สุดของ full solution นี้

ไม่มี database แยกต่างหากอีกต่อไป ทั้ง master data และ workflow state เก็บบน AS400 ทั้งหมด ผ่าน iws-clone ตัวเดียว:

ประเภทข้อมูลเก็บที่ไหนเหตุผล
Master data (Employee, Item, Vendor) AS400 — ตารางที่มีอยู่แล้ว (ถ้ามี) หรือสร้างใหม่ผ่าน Phase 7 เป็นข้อมูลจริงที่ระบบเดิมของบริษัทใช้อยู่ ห้ามสร้างซ้ำถ้ามีอยู่แล้ว
Workflow state (PR, PO, Leave, Approval) AS400 — สร้างเป็นตารางใหม่ (library แยกต่อระบบ) ไม่ต้องซิงค์ข้ามระบบ อ่าน/เขียนที่เดียวกันตลอด ลดความซับซ้อน
Read (query ข้อมูล) ผ่าน Phase 5/5.5/6 (Config, Schema Browser, Query Builder) มีอยู่แล้ว ใช้ซ้ำได้ทันที
Write (insert/update สถานะ approve/reject) ผ่าน Phase 6 (Write Operations) — ต้องทำให้เสร็จก่อน ถึงจะสร้างระบบพวกนี้ได้จริง ทุก workflow (อนุมัติลา, สร้าง PO, รับสินค้า) ต้อง insert/update ข้อมูลจริงบน AS400
ผลที่ตามมา: เพราะไม่มี database แยกแล้ว Phase 6 (Write Operations) ที่เคยพักไว้ก่อนหน้านี้ กลายเป็นสิ่งที่ต้องทำให้เสร็จก่อนเริ่มระบบใดๆ ในแผนนี้ ทั้งหมด เพราะทุก workflow ต้องเขียนสถานะ (อนุมัติ/ปฏิเสธ/รับของ) กลับเข้า AS400 จริงทุกครั้ง

02 · Shared Foundation

ฐานรากที่ต้องทำก่อนทุกระบบ

ทำครั้งเดียว ใช้ร่วมกันได้ทั้ง HR, Purchase, Inventory

  • Login / ตรวจสิทธิ์ (JWT stateless)
  • Role-based Permission (ใครอนุมัติได้แค่ไหน)
  • User ↔ Employee mapping (เชื่อมกับ Employee master บน AS400)
  • Notification กลาง (email + in-app)
  • Audit Log กลาง (ใครทำอะไรเมื่อไหร่)
  • Approval Engine กลาง (ใช้ซ้ำได้ทุก workflow)

ทุกตารางด้านล่างสร้างในไลบรารี APPCORE บน AS400 ผ่าน Phase 7 Table Designer — ชื่อ field ทั้งหมดตั้งตาม Naming Convention (2-char prefix)

หมายเหตุเรื่องชื่อ field: TXHASH, TXMAIL เป็น การเลือก prefix TX (Text/Description) แบบกว้างๆ เพราะยังไม่มี prefix เฉพาะสำหรับ email/hash ในลิสต์เดิม — ตอนสร้างจริงผ่าน Table Designer ถ้า agent เจอ field แบบนี้ควรถามยืนยันชื่อ/prefix กับผู้ใช้ก่อนเสมอ ตามกฎข้อ 7 ใน SKILL.md

06 · ลำดับการสร้าง

Build Order ที่แนะนำ

Step 0 · เสร็จแล้ว ✅

Write Operations (Phase 6)

iws-clone ทำ INSERT/UPDATE บน AS400 ได้แล้วจากก่อนหน้านี้ — เป็นฐานที่ทุก ระบบข้างล่างต้องใช้ เพราะไม่มี database แยกแล้ว

Step 1

Shared Foundation

สร้างตาราง USERS/ROLES/PERMISSIONS/NOTIFICATIONS/AUDIT_LOG/APPROVALS บน AS400 (ไลบรารี APPCORE) ผ่าน Phase 7 Table Designer — ทำครั้งเดียวใช้ทุกระบบ

Step 2

Purchase (นำร่อง)

มี workflow อนุมัติชัดเจนที่สุด เหมาะทดสอบ pattern "AS400-only + approval engine" ก่อนระบบอื่น

Step 3

HR

ใช้ Approval Engine เดิมจาก Purchase ได้เลย เพิ่มแค่ business logic เฉพาะของ HR

Step 4

Inventory

ผูกกับ Purchase (GRN อัปเดต stock อัตโนมัติ) เหมาะทำหลังสุดเพื่อเชื่อมกับของเดิมได้ครบ

Step 5

Cross-system Reporting

Dashboard รวมทุกระบบ (งบ Purchase, การลาพนักงาน, สต็อกคงเหลือ) หลังแต่ละระบบเสถียรแล้ว — query ตรงจาก AS400 ผ่าน Query Builder (Phase 6 เดิม) ได้เลย ไม่ต้องมี data warehouse แยก

Step 6

Mobile / PWA

ต่อยอดให้อนุมัติ/เช็คสต็อกผ่านมือถือได้ เมื่อ core ทั้งหมดใช้งานจริงแล้ว

ทำไมต้อง Purchase ก่อน HR/Inventory: PR→PO มี state และ approval หลายชั้นที่ซับซ้อนที่สุดในสามระบบ ถ้า pattern "เขียนอ่านบน AS400 อย่างเดียว ผ่าน iws-clone + approval engine กลาง" ใช้ได้ดีกับ Purchase ก็มั่นใจได้ว่า เอาไปใช้กับ HR/Inventory ที่ workflow ง่ายกว่าได้แน่นอน
ข้อดีของการไม่มี database แยก: ไม่ต้องกังวลเรื่องข้อมูล 2 ฝั่งไม่ตรงกัน (data consistency) เพราะอ่าน/เขียนที่เดียวกันตลอด แลกกับต้องพึ่ง AS400 ผ่าน iws-clone ในทุก request รวมถึง report/dashboard ด้วย — ถ้าวันหลัง traffic เยอะขึ้นมากจนช้า ค่อยพิจารณาเพิ่ม caching layer เฉพาะจุดที่จำเป็นทีหลังได้
07 · Prompt สำหรับ Agent (แต่ละระบบ)

สั่งทีละ Phase — ใช้ต่อจาก iws-clone เดิม

ทุก prompt ใช้ความสามารถที่ iws-clone มีอยู่แล้ว (Phase 5 Config, Phase 5.5 Schema Browser, Phase 6 Write Ops, Phase 7 Table Designer) ไม่ต้องเขียน backend ใหม่ — งานหลักคือสร้างตาราง/endpoint ผ่าน GUI เดิม แล้วสร้างเว็บ frontend คุยกับ endpoint เหล่านั้น

Phase 0 — Project Setup
สร้างโปรเจกต์ Next.js ใหม่ชื่อ "erp-suite" (แยกออกจาก iws-clone โดยสิ้นเชิง เป็นคนละ process/คนละ repo) ทำทีละขั้นตอน — งานนี้เป็นแค่ scaffold ยังไม่ต้อง สร้างฟีเจอร์ของระบบใดๆ: 1. รัน npx create-next-app@latest erp-suite (เลือก TypeScript, Tailwind CSS, App Router) 2. ติดตั้ง dependencies เพิ่ม: jsonwebtoken, bcryptjs (เทียบ password hash), zod (validation ฟอร์ม) 3. สร้าง .env.local: IWS_CLONE_URL=http://localhost:3000 JWT_SECRET= 4. สร้างโครงสร้างโฟลเดอร์: src/ app/ (auth)/login/ hr/ purchase/ inventory/ components/ NotificationBell.tsx (ยังเป็น placeholder เปล่าก่อน) ApprovalWidget.tsx (ยังเป็น placeholder เปล่าก่อน) lib/ api.ts (wrapper สำหรับเรียก iws-clone REST API) auth.ts (จัดการ JWT) 5. เขียน src/lib/api.ts เป็นฟังก์ชันกลาง เช่น callGateway(path, options) ที่แนบ IWS_CLONE_URL ให้อัตโนมัติ ทุกที่ใน โปรเจกต์เรียกผ่านฟังก์ชันนี้ฟังก์ชันเดียว ห้าม hardcode URL กระจายอยู่ หลายที่ 6. คัดลอกไฟล์ CLAUDE.md, AGENTS.md, .ai/PLAN.md, .ai/skills/erp-conventions/SKILL.md เข้าไปที่ root ของโปรเจกต์ (ผู้ใช้ จะวางให้เองแล้ว แค่ตรวจสอบว่าอยู่ครบตามตำแหน่งที่ถูกต้อง) 7. รัน npm run dev ทดสอบว่าเปิดหน้าเปล่าได้ ไม่มี error ห้ามเริ่มเขียนหน้า Login จริงหรือ business logic ใดๆ ในรอบนี้ เป็นแค่ scaffold โครงโปรเจกต์เท่านั้น
Phase A — Shared Foundation
ก่อนเริ่มทำอะไรทั้งหมด อ่าน CLAUDE.md, .ai/PLAN.md และ .ai/skills/erp-conventions/SKILL.md ก่อน (โปรเจกต์นี้เรียก iws-clone เป็น Gateway ภายนอก ไม่ได้เขียน backend เอง) สร้าง Shared Foundation ทำทีละขั้นตอน: 1. เปิด iws-clone → แท็บ "Table Designer" (Phase 7) สร้างตารางในไลบรารี APPCORE ตาม ER diagram ที่กำหนดไว้: USERS, ROLES, PERMISSIONS, USER_ROLES, ROLE_PERMISSIONS, NOTIFICATIONS, AUDIT_LOG, APPROVALS (ดู field ทั้งหมดใน full-solution-plan.html section 02) — สร้างทีละ ตาราง ยืนยันทุกครั้งก่อน Create Table จริง 2. เปิด iws-clone → แท็บ "Config" (Phase 5) สร้าง endpoint สำหรับ: - GET /api/app/users?username= (login lookup) - GET /api/app/permissions?role= - POST /api/app/notifications (Phase 6 write) - GET /api/app/notifications?user= - POST /api/app/approvals (Phase 6 write — ใช้ร่วมกันทุกระบบผ่าน CDTYPE) - GET /api/app/approvals?type=&reqno= 3. สร้างโปรเจกต์ Next.js ใหม่ชื่อ "erp-suite" (แยกจาก iws-clone) ทำ: - หน้า Login เรียก /api/app/users ตรวจสอบรหัสผ่าน (hash เทียบกับ TXHASH) ออก JWT เก็บใน httpOnly cookie - Middleware ตรวจ JWT ทุก request ที่ต้อง auth - Layout กลาง (Sidebar/Navbar) ให้ทุกระบบ (HR/Purchase/Inventory) ใช้ร่วมกัน - Component "NotificationBell" ดึงจาก /api/app/notifications - Component "ApprovalWidget" ใช้ซ้ำได้ทุกระบบ (รับ props: requestType, requestNo) เรียก /api/app/approvals 4. ทดสอบ: login ได้จริง, เห็น notification, ยิง approval ผ่าน widget แล้ว เช็คว่าเข้าตาราง APPROVALS บน AS400 จริงผ่าน Schema Browser ห้ามเริ่มเขียนโค้ดของ HR/Purchase/Inventory ในรอบนี้ ให้ทำแค่ Shared Foundation ให้เสร็จและทดสอบผ่านก่อน
Phase B — Purchase (นำร่อง)
ก่อนเริ่มทำอะไรทั้งหมด อ่าน CLAUDE.md, .ai/PLAN.md และ .ai/skills/erp-conventions/SKILL.md ก่อน เพื่อดูว่า Phase A (Shared Foundation) ทำอะไรไปแล้วบ้าง (ต้องเสร็จก่อนถึงจะเริ่ม Phase นี้ได้) สร้างระบบ Purchase ทำทีละขั้นตอน: 1. เปิด iws-clone → Table Designer สร้างตารางในไลบรารี APPPUR ตาม ER diagram: PURCHASE_REQUISITIONS, PR_LINES, PURCHASE_ORDERS, PO_LINES, VENDOR, GOODS_RECEIPTS, GR_LINES, INVOICES (ดู field ใน full-solution-plan.html section 04) — ถ้ามีตาราง ITEM master อยู่แล้ว จาก AS400 จริง ใช้ของเดิม ไม่ต้องสร้างใหม่ 2. เปิด iws-clone → Config สร้าง endpoint (อ้างอิง pattern เดียวกับ Shared Foundation): - POST/GET /api/app/pr (สร้าง/ดู PR) - POST/GET /api/app/po (สร้าง/ดู PO) - POST /api/app/grn (รับสินค้า) - POST /api/app/invoice-match (ทำ 3-way match: เทียบ PO/GRN/Invoice แล้ว UPDATE CDMTCH) 3. ในโปรเจกต์ "erp-suite" เพิ่มโมดูล /purchase: - หน้า "สร้าง PR" (ฟอร์ม + add multiple lines เลือก item จาก dropdown) - หน้า "รายการ PR รออนุมัติ" ใช้ ApprovalWidget จาก Phase A - Logic เช็ค Budget ก่อนสร้าง PO (เทียบ AMEST รวมกับงบที่ตั้งไว้ — เก็บ ค่างบไว้เป็น constant/config ก่อน ยังไม่ต้องทำ Budget Master เต็มรูปแบบ) - หน้า "แปลง PR เป็น PO" (เลือก Vendor) - หน้า "รับสินค้า (GRN)" กรอกจำนวนที่รับจริงเทียบกับ PO - หน้า "Invoice Matching" แสดงผลเทียบ 3 ทาง พร้อมสถานะ MATCH/MISMATCH 4. ทดสอบ flow เต็ม: สร้าง PR → อนุมัติผ่าน widget → แปลงเป็น PO → รับของ → matching invoice → เช็คทุกตารางบน AS400 ว่าอัปเดตถูกต้องผ่าน Schema Browser ห้ามเริ่ม HR/Inventory ในรอบนี้ ให้ Purchase ทำงานได้ครบ flow ก่อน
Phase C — HR
ก่อนเริ่มทำอะไรทั้งหมด อ่าน CLAUDE.md, .ai/PLAN.md และ .ai/skills/erp-conventions/SKILL.md ก่อน เพื่อดูว่า Phase A และ B ทำอะไร ไปแล้วบ้าง สร้างระบบ HR ทำทีละขั้นตอน: 1. เปิด iws-clone → Table Designer สร้างตารางในไลบรารี APPHR: LEAVE_REQUESTS, OT_REQUESTS (ดู field ใน full-solution-plan.html section 03) — ถ้ามีตาราง EMPLOYEE master อยู่แล้วจาก AS400 จริง ใช้ ของเดิม ไม่ต้องสร้าง EMPLOYEE ใหม่ 2. เปิด iws-clone → Config สร้าง endpoint: - POST/GET /api/app/leave - POST/GET /api/app/ot 3. ในโปรเจกต์ "erp-suite" เพิ่มโมดูล /hr: - หน้า "ยื่นคำขอลา/OT" (เลือกประเภท, วันที่, เหตุผล) - หน้า "รายการรออนุมัติ" ใช้ ApprovalWidget เดิมจาก Phase A (ส่ง requestType="LV" หรือ "OT") - หน้า ESS สรุปยอดลาคงเหลือของพนักงานคนนั้น (ใช้ query จาก Schema Browser/Query Builder ของ iws-clone) 4. ทดสอบ flow: ยื่นคำขอ → หัวหน้าอนุมัติ → HR อนุมัติ → เช็คสถานะอัปเดต ถูกต้องบน AS400 ห้ามเริ่ม Inventory ในรอบนี้
Phase D — Inventory
ก่อนเริ่มทำอะไรทั้งหมด อ่าน CLAUDE.md, .ai/PLAN.md และ .ai/skills/erp-conventions/SKILL.md ก่อน เพื่อดูว่า Phase A, B, C ทำอะไร ไปแล้วบ้าง สร้างระบบ Inventory ทำทีละขั้นตอน: 1. เปิด iws-clone → Table Designer สร้างตารางในไลบรารี APPINV: ITEM (ถ้า ยังไม่มีจาก Purchase), WAREHOUSE, STOCK_TRANSACTIONS, STOCK_TRANSFERS, CYCLE_COUNTS (ดู field ใน full-solution-plan.html section 05) 2. เปิด iws-clone → Config สร้าง endpoint: - POST /api/app/stock-in, POST /api/app/stock-out - POST /api/app/stock-transfer - POST /api/app/cycle-count - GET /api/app/items?below-reorder=true (เช็คของใกล้หมด) 3. เชื่อมกับ Purchase: พอ GRN ใน Phase B บันทึกสำเร็จ ให้เรียก /api/app/stock-in อัตโนมัติ (item, quantity, warehouse default) เพื่อ อัปเดต stock ทันทีที่รับของเข้า 4. ในโปรเจกต์ "erp-suite" เพิ่มโมดูล /inventory: - หน้า Dashboard สต็อกคงเหลือ + แจ้งเตือนสินค้าใกล้หมด (ต่ำกว่า QTRPT) - หน้า "โอนย้ายสินค้า" ระหว่างคลัง - หน้า "Cycle Count" กรอกจำนวนนับจริงเทียบระบบ 5. ทดสอบ flow เต็ม: รับของผ่าน Purchase → stock อัปเดตอัตโนมัติ → โอนย้าย ระหว่างคลัง → cycle count เจอส่วนต่าง → ปรับยอดถูกต้อง พอครบ 4 Phase แล้ว ระบบทั้งหมด (Shared Foundation + HR + Purchase + Inventory) ควรทำงานร่วมกันได้แบบ full solution ตามที่วางแผนไว้
Audit Prompt — ใช้ซ้ำได้ก่อนขึ้น Phase ถัดไป

ใช้ prompt นี้ระหว่าง Phase ทุกครั้งที่บอก agent ว่า "ทำเสร็จแล้ว" ก่อนจะ วาง prompt ของ Phase ถัดไป เพื่อตรวจสอบว่าของเดิมยังทำงานถูกต้องจริง ไม่ใช่แค่เชื่อคำรายงาน

อ่าน .ai/PLAN.md ก่อน (ห้ามแก้ไขไฟล์หรือเขียนโค้ดใดๆ ในรอบนี้ เป็นแค่การ ตรวจสอบ/audit เท่านั้น) แล้วตรวจสอบและรายงานผลกลับมาเป็นข้อๆ: 1. เปิดทุก endpoint ที่ Phase ล่าสุดสร้างไว้ ยิง request จริงทดสอบ (ไม่ใช่ แค่ดูโค้ด) รายงานว่า endpoint ไหนตอบกลับถูกต้อง ไหนมี error 2. เช็คผ่าน Schema Browser ของ iws-clone ว่าตารางที่สร้างไว้ใน Phase นี้ มี field ครบตาม ER diagram ใน full-solution-plan.html จริงไหม มี field ไหนขาด/เกิน/data type ไม่ตรงบ้าง 3. เช็คว่า Approval flow (ถ้า Phase นี้เกี่ยวข้อง) เขียนเข้าตาราง APPROVALS กลางจริง ไม่ได้สร้างตาราง approval แยกใหม่โดยไม่ตั้งใจ 4. เช็คว่า .ai/PLAN.md ติ๊ก checklist ตรงกับสถานะจริงหรือไม่ ถ้าไม่ตรง ให้ ระบุว่าข้อไหนติ๊กเกินจริงหรือยังไม่ได้ติ๊กทั้งที่ทำเสร็จแล้ว 5. สรุปว่าพร้อมขึ้น Phase ถัดไปหรือยัง มีอะไรต้องแก้ก่อนไหม ห้ามเริ่มเขียนโค้ด Phase ถัดไปในรอบนี้ รอให้ตรวจสอบเสร็จแล้วรายงานผลก่อน
