MODULE 1Logging ที่ใช้ Debug ได้จริงตอน Production
3 วัน
ต่างจากตอน dev: ตอน dev มี breakpoint ให้หยุดดูค่าได้ แต่ตอน production (server จริง มีผู้ใช้จริงอยู่) ทำอย่างนั้นไม่ได้เลย log คือ "หลักฐานเดียว" ที่เหลือไว้ให้ไล่ปัญหาย้อนหลัง ถ้า log ไม่ดี = debug ไม่ได้
ติดตั้ง Serilog — logging library ที่นิยมที่สุดใน .NET
รันที่ root ของโปรเจกต์
dotnet add package Serilog.AspNetCore
dotnet add package Serilog.Sinks.File
แก้ไฟล์: Program.cs
using Serilog;

Log.Logger = new LoggerConfiguration()
    .MinimumLevel.Information()
    .WriteTo.Console()
    .WriteTo.File("logs/app-.log", rollingInterval: RollingInterval.Day)
    .CreateLogger();

builder.Host.UseSerilog();

ผลลัพธ์: log ถูกเขียนลงไฟล์ในโฟลเดอร์ logs/ แยกไฟล์ตามวัน ช่วยให้ย้อนดูปัญหาของวันที่ระบุได้ทันที

Log ที่ดี vs Log ที่ไม่มีประโยชน์
// ไม่มีประโยชน์ — ไม่รู้ว่าอะไรผิด ใคร ตอนไหน
Logger.LogError("เกิดข้อผิดพลาด");

// ดี — มีบริบทครบ ค้นหา/กรองได้
Logger.LogError(ex,
    "สร้างออเดอร์ไม่สำเร็จ CustomerId={CustomerId} ItemCount={ItemCount}",
    customerId, cartItems.Count);

หลักการ: log ต้องตอบได้ว่า "อะไรเกิดขึ้น, กับใคร/ข้อมูลอะไร, ตอนไหน" — placeholder แบบ {CustomerId} (ไม่ใช่ string interpolation) ทำให้ Serilog เก็บเป็น field แยกที่ค้นหา/กรองได้ในภายหลัง

ห้าม log ข้อมูลอ่อนไหวเด็ดขาด: รหัสผ่าน, token, เลขบัตรประชาชน, เลขบัญชี — ไฟล์ log มักถูกเก็บนานกว่าที่คิดและคนเข้าถึงได้กว้างกว่าฐานข้อมูลหลัก ถ้า log มีข้อมูลพวกนี้จะกลายเป็นช่องโหว่ด้านความปลอดภัยทันที
MODULE 2Security Review Checklist
3 วัน

ตรวจทีละข้อก่อนปล่อยระบบจริง (ต่อยอดจาก Module 9 ของ webapp-deepdive ที่สอน XSS/CSRF/SQL Injection ไว้แล้ว):

หัวข้อตรวจอะไรวิธีตรวจ
Authorization ครบทุกหน้าทุกหน้าที่ควรต้อง login มี [Authorize] ครบไหม (ลืมแค่หน้าเดียวก็เข้าตรงๆ ได้)ไล่ดูทุกไฟล์ใน Components/Pages/ ทีละไฟล์
Authorization ฝั่ง backend ด้วยซ่อนปุ่มใน UI ไม่พอ ต้องเช็คสิทธิ์ใน Service ด้วย (ป้องกันการเรียกตรงๆ)ลองเรียก method โดยไม่ผ่านหน้าเว็บ ดูว่ายังเช็คสิทธิ์อยู่ไหม
Connection string / secretไม่มี password จริงใน appsettings.json ที่ commit ขึ้น gitค้นด้วย Ctrl+Shift+F หาคำว่า "Password=" ทั้งโปรเจกต์
Error message ไม่เปิดเผยรายละเอียดภายในProduction ต้องไม่แสดง stack trace ให้ผู้ใช้เห็นเช็ค app.UseExceptionHandler() ตั้งไว้ และ environment เป็น Production จริง
HTTPS บังคับไม่มีทางเข้าใช้ผ่าน http ธรรมดาได้เช็ค app.UseHttpsRedirection() และตั้ง HSTS
Dependency ที่มีช่องโหว่Package ที่ใช้มี security advisory หรือไม่รัน dotnet list package --vulnerable
Input validation ฝั่ง serverทุก form ตรวจข้อมูลฝั่ง server ด้วย ไม่พึ่ง validation ฝั่ง client อย่างเดียวลองส่งข้อมูลผิดรูปแบบตรงๆ (ข้าม UI) ดูว่า reject ไหม
ตรวจ package ที่มีช่องโหว่
dotnet list package --vulnerable
MODULE 3Configuration และ Secret Management
2 วัน
แยก config ตาม environment (ทบทวนจาก webapp-deepdive Module 8 พร้อมลงลึกขึ้น)
appsettings.json                 // ค่ากลาง ไม่มี secret
appsettings.Development.json     // เฉพาะ dev (SQLite ไฟล์ local)
appsettings.Production.json      // เฉพาะ production (ไม่ใส่ secret จริงในไฟล์นี้ด้วย!)

secret จริง (connection string production, API key ของ IWS) ต้องส่งเข้าไปทาง Environment Variable ของ server เท่านั้น ไม่ใส่ในไฟล์ใดๆ ที่ commit ขึ้น git

รูปแบบการตั้ง Environment Variable สำหรับ config ที่ซ้อนกัน
# appsettings.json มี  {"ConnectionStrings": {"Default": "..."}}
# ตั้ง env variable ทับด้วยชื่อแบบมี __ (สองขีดล่าง) คั่นระดับ:
ConnectionStrings__Default="Server=...;Password=..."

ASP.NET Core อ่าน environment variable ทับค่าใน appsettings.json ให้อัตโนมัติ โดยใช้ __ (double underscore) แทนระดับที่ซ้อนกัน

MODULE 4Health Check
1 วัน
ทำไมต้องมี: ให้ระบบ monitoring (หรือแค่เปิดเบราว์เซอร์เช็คเอง) รู้ได้ทันทีว่า "แอปยังทำงานปกติไหม ต่อฐานข้อมูลได้ไหม" โดยไม่ต้องล็อกอินเข้าใช้งานจริง
แก้ไฟล์: Program.cs
builder.Services.AddHealthChecks()
    .AddDbContextCheck<AppDbContext>();

// ...
app.MapHealthChecks("/health");

เปิด /health ในเบราว์เซอร์ ถ้าทุกอย่างปกติจะได้คำตอบ "Healthy" ถ้าต่อฐานข้อมูลไม่ได้จะได้ "Unhealthy" ทันที เหมาะกับ IWS integration ในอนาคตด้วย (เพิ่ม check ว่าเรียก IWS ได้ไหมได้ในที่เดียวกัน)

MODULE 5Deploy ด้วย Docker
3-4 วัน
ทำไมใช้ Docker: แก้ปัญหา "ทำงานบนเครื่องผมได้ แต่บน server พัง" เพราะ Docker จับทุกอย่างที่แอปต้องใช้ (เวอร์ชัน .NET, dependency) ห่อรวมเป็นก้อนเดียว รันได้เหมือนกันทุกที่
สร้างไฟล์ใหม่: Dockerfile (ที่ root ของโปรเจกต์ ไม่มีนามสกุล)
# ขั้น 1: build
FROM mcr.microsoft.com/dotnet/sdk:9.0 AS build
WORKDIR /src
COPY *.csproj .
RUN dotnet restore
COPY . .
RUN dotnet publish -c Release -o /app

# ขั้น 2: run (ใช้ image เล็กกว่า ไม่มี SDK)
FROM mcr.microsoft.com/dotnet/aspnet:9.0
WORKDIR /app
COPY --from=build /app .
ENTRYPOINT ["dotnet", "BlazorCrudApp.dll"]

เปลี่ยนเลขเวอร์ชัน (9.0) ให้ตรงกับ .NET SDK ที่ใช้พัฒนา และเปลี่ยน BlazorCrudApp.dll ให้ตรงกับชื่อโปรเจกต์จริง

Build และรัน
docker build -t blazorcrudapp .
docker run -p 8080:8080 -e ConnectionStrings__Default="..." blazorcrudapp

-p 8080:8080 เปิดพอร์ตจาก container ออกมาให้เข้าถึงจากภายนอก และ -e คือส่ง environment variable เข้าไป (ตรงกับ Module 3)

ข้อควรระวัง: Blazor Server ต้องเปิด WebSocket ผ่าน reverse proxy/load balancer ที่อยู่หน้า container ด้วย ถ้าไม่เปิด SignalR connection จะเชื่อมไม่ได้ หน้าเว็บจะโหลดขึ้นแต่กดอะไรไม่ได้เลย (อาการเดียวกับลืม rendermode แต่สาเหตุต่างกัน)
MODULE 6Deploy บน IIS (Windows Server)
2-3 วัน
ทำไมต้องรู้: หลายบริษัทที่มี Windows Server + SQL Server อยู่แล้ว (เหมือนสภาพแวดล้อมที่คุยกันไว้ตอนต้น) ยังใช้ IIS เป็นหลัก มากกว่า Docker
Publish ไฟล์สำหรับ deploy
dotnet publish -c Release -o ./publish
สิ่งที่ต้องเตรียมบน Windows Server (ทำครั้งเดียว)

1. ติดตั้ง .NET Hosting Bundle (ดาวน์โหลดจาก dotnet.microsoft.com ตรงกับเวอร์ชัน .NET ที่ใช้) — ตัวนี้ทำให้ IIS รัน ASP.NET Core ได้

2. เปิด WebSocket Protocol ใน Windows Features (Server Manager → Add Roles and Features → Web Server → Application Development → WebSocket Protocol) — จำเป็นสำหรับ Blazor Server

3. สร้าง Site ใหม่ใน IIS Manager ชี้ Physical Path ไปที่โฟลเดอร์ที่ copy ไฟล์ publish ไปวาง

4. ตั้ง Application Pool เป็น "No Managed Code" (ASP.NET Core ไม่ได้รันบน .NET Framework แบบเดิม)

5. ตั้ง Environment Variable ของ Application Pool สำหรับ secret ต่างๆ

MODULE 7Checklist ก่อนปล่อยจริง
อ้างอิง

ตรวจทุกข้อก่อนปล่อยระบบให้ผู้ใช้จริงใช้ ทุกข้อที่ยังไม่ผ่าน = ความเสี่ยงที่ยังไม่ได้จัดการ:

หมวดรายการตรวจ
LoggingSerilog ตั้งค่าแล้ว, log เขียนลงไฟล์จริง, ไม่มีข้อมูลอ่อนไหวใน log
Security[Authorize] ครบ, ไม่มี secret ใน git, HTTPS บังคับ, ไม่มี package ช่องโหว่
ConfigEnvironment Variable ตั้งบน server ครบ, ไม่มี connection string จริงใน repo
Health/health ทำงาน และเช็คฐานข้อมูลได้
Testรัน dotnet test ผ่านทุกตัวก่อน publish
Backupฐานข้อมูลมีแผน backup และเคยทดสอบ restore จริงแล้ว (backup ที่ไม่เคยทดสอบ restore = ไม่มี backup)
Rollbackรู้วิธีย้อนกลับเวอร์ชันเก่าถ้า deploy ใหม่แล้วมีปัญหา (เก็บไฟล์ publish เวอร์ชันก่อนหน้าไว้เสมอ)
Monitoringมีคนรู้ทันทีเมื่อระบบล่ม (ไม่ใช่รอผู้ใช้โทรมาแจ้ง)
Track F คือจุดที่ทักษะทั้งหมดจาก Track A-E มาบรรจบกัน — ระบบที่ดีไม่ใช่แค่ทำงานได้ แต่ต้อง "รู้ตัวเมื่อมันพัง" และ "แก้ไขได้เมื่อมันพัง"
