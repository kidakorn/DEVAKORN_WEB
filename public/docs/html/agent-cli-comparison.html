ลำดับเริ่มต้นที่แนะนำ (ใช้ได้กับทุกค่าย)

ลำดับนี้เป็นข้อเสนอของผมเอง ไม่ได้มาจากเอกสารค่ายใดค่ายหนึ่ง แต่ละขั้นมีเหตุผลกำกับ

  1. เริ่มในโฟลเดอร์ของโปรเจกต์ที่อยู่ใน git และ commit งานค้างก่อน เพราะ agent แก้ไฟล์ได้จริง การมี commit ล่าสุดทำให้ย้อนกลับด้วย git diff หรือ git restore ได้เสมอ (Codex exec บังคับให้อยู่ใน git repo ด้วย)
  2. สร้างไฟล์คำสั่งประจำโปรเจกต์ด้วย /init เพื่อให้ agent รู้โครงสร้างและกติกา (build, test, สไตล์โค้ด) โดยไม่ต้องอธิบายซ้ำทุกครั้ง แล้วแก้ไขไฟล์ที่ได้ด้วยมือ เพราะไฟล์ที่ agent สร้างให้มักกว้างเกินจำเป็น
  3. ใช้โหมดวางแผน (plan) กับงานที่ไม่ชัดเจน โหมดนี้อ่านอย่างเดียว ไม่แก้ไฟล์ ได้อ่านแผนก่อนลงมือ ถูกกว่าการแก้ไขผิดทิศแล้วต้องย้อน
  4. เปิดการอนุมัติแบบถามทุกครั้งในช่วงแรก ค่อยอนุญาตเฉพาะคำสั่งที่ปลอดภัยและใช้ซ้ำบ่อย (เช่น รัน test) ผ่านกฎ allow ของแต่ละเครื่องมือ หลีกเลี่ยงโหมดข้ามการอนุมัติทั้งหมดนอกสภาพแวดล้อมที่แยกจากเครื่องจริง
  5. ตรวจ diff ก่อน commit เสมอ agent ทำงานเร็วแต่ผิดได้ ผู้ตรวจสุดท้ายคือคุณ ใช้ /review หรือ /diff เป็นตัวช่วยอ่าน ไม่ใช่ตัวแทนการอ่าน

5. ระบบ Permission และ Sandbox

Claude CodeCodex CLIGemini CLICopilot CLIAider
แนวคิดหลัก โหมดสิทธิ์ 6 แบบ และกฎ allow/ask/deny ต่อเครื่องมือ กฎ deny ใช้ได้ทุกโหมดแม้โหมดข้ามสิทธิ์ สองชั้นแยกกัน: sandbox ที่ระบบปฏิบัติการบังคับ (จำกัดการเข้าถึง) กับ approval policy (ควบคุมว่าเมื่อไรถามคุณ) 4 โหมดอนุมัติ และ policy engine แบบกฎ TOML (allow, deny, ask_user) เมื่อรันแบบไม่โต้ตอบ ask_user ทำงานเป็น deny โฟลเดอร์ที่เชื่อถือ + ถามเป็นรายเครื่องมือ (อนุมัติครั้งเดียว/ทั้งเซสชัน/ปฏิเสธ) การอนุมัติไม่คงข้ามเซสชัน ไม่มีระบบ permission หรือ sandbox ถามยืนยัน yes/no เป็นครั้ง ๆ เช่น เพิ่มไฟล์เข้าแชต
ค่าเริ่มต้น โหมด default ถามก่อนแก้ไฟล์และรันคำสั่ง ใน git repo: workspace-write + on-request
นอก git: read-only
เครือข่ายปิดโดยค่าเริ่มต้น		 โหมด default ถามเชื่อถือโฟลเดอร์ตอนเริ่มครั้งแรก แก้ไฟล์แล้ว auto-commit ทุกครั้ง
Sandbox /sandbox (Windows ต้องใช้ WSL 2 จึงมี sandbox) ในตัว มี codex sandbox แยก; .git, .agents, .codex เป็น read-only ในพื้นที่เขียนได้ เปิดด้วย -s, GEMINI_SANDBOX หรือ settings: macOS Seatbelt, Docker/Podman, gVisor, LXC (ทดลอง), Windows native ทางเลือกด้วย --sandbox หรือ /sandbox enable ไม่มี ใช้ git เป็นตาข่ายนิรภัย: /undo ย้อน commit ล่าสุด
ข้อจำกัดที่เอกสารระบุ CLAUDE.md เป็นคำแนะนำ ไม่ใช่การบังคับ ถ้าต้องการกฎเด็ดขาดให้ใช้ hooks approval_policy = untrusted เลิกใช้แล้ว policy ระดับ workspace ถูกระบุว่าใช้งานไม่ได้ (issue #18186) การจำกัด path ใช้ heuristic ไม่รับประกัน; deny ของ write(PATH) ไม่รองรับ glob แต่ตัวอย่าง allow ใช้ glob ได้ เอกสารยังไม่ชัด commit การเปลี่ยนแปลงของคุณที่ค้างอยู่ก่อนเสมอ ยกเว้นใช้ --no-dirty-commits

มี GitHub MCP server ในตัว นโยบาย MCP ขององค์กรยังไม่ถูกบังคับโดย CLI		 ไม่พบในเอกสารทางการ ถือว่าไม่รองรับโดยตรง (มีโปรเจกต์ภายนอกที่ทำให้ aider เป็น MCP server แต่ไม่ใช่ฟีเจอร์ของ aider)
Hooks มี ตั้งใน settings: PreToolUse, PostToolUse, UserPromptSubmit, Stop, SessionStart ฯลฯ ชนิด handler: command, http, mcp_tool, prompt, agent; exit code 2 บล็อกการทำงาน
รายละเอียดเพิ่มเติม (เอกสาร hooks ฉบับเต็มยังไม่ได้อ่าน) ยังไม่ยืนยัน		 มี 12 events รวม PreToolUse, PermissionRequest, SubagentStart ฯลฯ handler ที่ทำงานจริงคือ command และ mcp_tool (prompt, agent ถูกอ่านแต่ข้าม) ต้องเชื่อถือผ่าน /hooks ก่อนใช้ มี 11 events (เช่น BeforeTool, AfterTool, SessionStart) รองรับเฉพาะ command exit code 2 บล็อก hook ของโปรเจกต์ถูก fingerprint เตือนเมื่อเปลี่ยน ไฟล์ JSON ที่ .github/hooks/NAME.json หรือ ~/.copilot/hooks/ events เช่น sessionStart, preToolUse, postToolUse ชนิด command ต้องรีสตาร์ตหลังแก้ ไม่มี ที่ใกล้เคียงที่สุดคือ --notifications-command และ --git-commit-verify (รัน git pre-commit hook)
Subagents ไฟล์ markdown ใน .claude/agents/ หรือ ~/.claude/agents/ ในตัว: Explore, Plan, General-purpose มี (ฟีเจอร์ multi_agent เปิดโดยค่าเริ่มต้น) ตำแหน่งไฟล์ custom agent ไม่พบในเอกสารที่อ่าน ยังไม่ยืนยัน ไฟล์ markdown ใน .gemini/agents/ หรือ ~/.gemini/agents/ เรียกด้วย @name ในตัว: codebase_investigator, cli_help, generalist; subagent เรียก subagent ไม่ได้ custom agents ใน .github/agents, ~/.copilot/agents เรียกด้วย /agent หรือ --agent=NAME /fleet รัน subagents แบบขนาน ไม่มี (architect/editor คือการจับคู่สองโมเดล ไม่ใช่ subagent)
Plugins / Extensions โฟลเดอร์ที่มี .claude-plugin/plugin.json รวม skills, agents, hooks, MCP
claude plugin install <name>@<marketplace>		 codex plugin และ codex plugin marketplace (skills เป็นรูปแบบเขียน plugin เป็นหน่วยแจกจ่าย) Extensions: gemini extensions install <github-url> รวม prompts, MCP, commands, hooks, subagents, skills copilot plugin และ /plugin รวม skills และ MCP servers ได้; plugin ให้ hooks ได้หรือไม่ ไม่ยืนยัน ยังไม่ยืนยัน ไม่มี

7. รายละเอียดรายค่าย

แต่ละส่วนพับได้ เปิดเฉพาะค่ายที่สนใจ ข้อความ "จุดเด่น/จุดอ่อน" เป็นการสังเคราะห์จากเอกสาร ไม่ใช่คำประกาศของค่ายนั้น

Claude Code

Flag ที่ใช้บ่อย

  • --model, --effort เลือกโมเดลและระดับการให้เหตุผล
  • -c, -r, --fork-session, -n จัดการเซสชัน
  • --allowedTools, --disallowedTools, --tools กำหนดเครื่องมือ
  • --max-turns, --max-budget-usd จำกัดรอบและงบ (โหมด -p)
  • --append-system-prompt[-file], --mcp-config, --settings, -w (worktree)
  • Subcommands: claude mcp, plugin, auth, update, doctor, setup-token, agents

สำหรับสคริปต์: --bare ข้าม hooks, skills, plugins, MCP และ CLAUDE.md เพื่อให้ผลทำซ้ำได้ แต่ต้องใช้ ANTHROPIC_API_KEY เพราะไม่อ่านการ login แบบสมาชิก

จุดเด่น

  • ครบทั้ง hooks, subagents, plugins, MCP, skills
  • โหมด print รองรับ JSON และ streaming
  • กฎ deny ใช้ได้ทุกโหมด
  • รองรับ worktree แยกงาน

จุดอ่อน

  • ต้องมีแผนจ่ายเงินหรือบัญชี Console
  • CLAUDE.md เป็นคำแนะนำ ไม่ใช่การบังคับ
  • Windows แบบ native ไม่มี sandbox (WSL 2 มี) และต้องมี Git for Windows
  • เซสชันยาวทำให้ context และค่าใช้จ่ายโต (เปิด auto-compaction เป็นค่าเริ่มต้น)
Codex CLI

Flag ที่ใช้บ่อย

  • -m, -a, -s, -C, --add-dir
  • -c key=value แทนค่าใน config ชั่วคราว; -p เลือก profile
  • -i แนบรูป; --search ค้นเว็บสด; --oss ใช้โมเดลในเครื่อง
  • codex exec: --json, -o, --output-schema, --skip-git-repo-check, --ephemeral
  • Subcommands: resume, fork, review, mcp, plugin, sandbox, doctor, update และอื่น ๆ (บางตัวทดลอง)

--full-auto ถูกประกาศเลิกใช้ สำหรับงานที่ต้องแก้ไฟล์ใน exec ให้ระบุ --sandbox workspace-write

จุดเด่น

  • sandbox ระดับระบบปฏิบัติการ เครือข่ายปิดเป็นค่าเริ่มต้น
  • เหมาะกับสคริปต์: exec --json, --output-schema, resume, GitHub Action
  • config แบบชั้น พร้อม profiles
  • ใช้แผน ChatGPT ที่มีอยู่ได้ และมีโหมดโมเดลในเครื่อง

จุดอ่อน

  • exec ต้องอยู่ใน git repo และเริ่มที่ read-only
  • ผู้ให้บริการอื่นต้องรองรับ Responses API
  • โมเดลหมุนเวียนและเลิกให้บริการเร็ว ตามเอกสารมีรุ่นที่ถูกเลิกในช่วงสิงหาคม-ตุลาคม 2026
  • เอกสารกระจัดกระจายและเพิ่งย้ายโดเมน (developers.openai.com ไปที่ learn.chatgpt.com)
Gemini CLI
สถานะ ดูกล่องเตือนด้านบนของหน้า เรื่องการแทนที่ด้วย Antigravity CLI ผมไม่ได้ค้นรายละเอียดของ Antigravity CLI ในรอบนี้

Flag ที่ใช้บ่อย

  • -p ไม่โต้ตอบ; -i รัน prompt แล้วต่อแบบโต้ตอบ
  • -m, -s, --approval-mode, -o, --include-directories
  • -r, --list-sessions, --delete-session
  • -w (worktree ต้องเปิด experimental.worktrees)
  • Checkpointing ไม่ใช่ flag แล้ว (ลบใน v0.11.0) ให้เปิด general.checkpointing.enabled: true ใน settings
  • ในแชต: @path แทรกไฟล์หรือโฟลเดอร์, !cmd รันคำสั่งเชลล์

จุดเด่น

  • โอเพนซอร์ส ปรับแต่งได้หลากหลาย: hooks, policy, subagents, extensions, MCP, คำสั่ง TOML
  • มีตัวเลือก sandbox หลายแบบ
  • มี checkpoint และ restore
  • README ระบุ context 1M token (ไม่ได้ตรวจซ้ำ)

จุดอ่อน

  • ถูกแทนที่สำหรับผู้ใช้ฟรีและ Google One ตามประกาศ
  • ใช้ได้เฉพาะโมเดล Gemini
  • policy ระดับ workspace ใช้ไม่ได้ และ checkpointing ปิดเป็นค่าเริ่มต้น
  • หลายฟีเจอร์ยังทดลอง (worktree, ACP, LXC)
GitHub Copilot CLI

Flag ที่ใช้บ่อย

  • -p, -i, -s, --output-format=json, --share=PATH
  • --model, --effort, --max-ai-credits
  • --allow-tool, --deny-tool, --allow-url, --deny-url, --allow-all
  • --continue, -r, -n, -w, --agent, --plugin-dir
  • รูปแบบกฎสิทธิ์: Kind(arg) เช่น shell(git:*), url(github.com), write(src/*.ts)
  • เฉพาะตัว: /fleet (subagents ขนาน), /every (prompt ซ้ำตามเวลา), /after (prompt ครั้งเดียว), /delegate, copilot --cloud (เซสชันบน sandbox คลาวด์ ยังเป็น public preview)

จุดเด่น

  • ผสานกับ GitHub (PR, issues, Actions) แน่น
  • เลือกได้หลายโมเดลหลายค่าย
  • โหมด plan/autopilot, /fleet, sandbox ทั้งแบบคลาวด์และในเครื่อง
  • รวมอยู่ในทุกแผน Copilot ตามเอกสาร

จุดอ่อน

  • องค์กรปิดการใช้ด้วยนโยบายได้
  • นโยบาย MCP ขององค์กรไม่ถูกบังคับโดย CLI
  • การเชื่อถือโฟลเดอร์เป็น heuristic
  • เอกสาร billing ขัดกันเอง (AI credits เทียบ premium requests) ให้ดู copilot help billing
Aider

Slash commands หลัก

  • /add, /drop, /read-only จัดการไฟล์ในแชต
  • /run (หรือ !), /test, /lint รันคำสั่งแล้วป้อนผลกลับเข้าแชต
  • /undo, /diff, /commit, /git ทำงานกับ git
  • /architect, /ask, /code, /context, /chat-mode สลับโหมด
  • /map, /tokens, /web, /paste, /voice

Flag ที่ใช้บ่อย

  • --model, --edit-format, --architect, --editor-model, --map-tokens
  • --message, --message-file, --yes-always, --dry-run
  • --no-auto-commits, --no-dirty-commits, --git-commit-verify
  • --lint-cmd, --test-cmd, --auto-lint, --auto-test
  • ค่าที่ใช้ได้ของ --edit-format ไม่ได้ยืนยันในรอบนี้ ยังไม่ยืนยัน

แนวคิดต่างจากตัวอื่น: Aider เป็นเครื่องมือจับคู่เขียนโค้ดที่ผูกกับ git โดยตรง ทุกการแก้ไขกลายเป็น commit พร้อมข้อความที่โมเดลเขียน และผู้เขียนใน git ต่อท้ายด้วย "(aider)" การย้อนกลับจึงทำได้ด้วย /undo

จุดเด่น

  • ย้อนกลับง่ายด้วย git, มี repo map ช่วยเรื่อง context
  • ใช้ได้กับโมเดลเกือบทุกค่ายและโมเดลในเครื่อง
  • วงจร lint/test ในตัว, โหมด architect/editor
  • เขียนสคริปต์ได้ด้วย --message

จุดอ่อน

  • ไม่มี MCP, hooks, subagents, plugins ตามเอกสาร
  • ไม่มีระบบ permission หรือ sandbox ละเอียด
  • Python API ไม่ได้รับการสนับสนุนอย่างเป็นทางการ
  • คุณภาพขึ้นกับความสามารถของโมเดลในการสร้างรูปแบบการแก้ไขที่ถูกต้อง

8. เลือกใช้ตามสถานการณ์

ส่วนนี้เป็นข้อเสนอจากการสังเคราะห์ข้อมูลข้างบน ไม่ใช่คำแนะนำจากค่ายใดค่ายหนึ่ง

สถานการณ์ตัวเลือกที่เข้าทางเหตุผล
อยากได้ระบบขยายครบ (hooks, subagents, plugins, MCP) และใช้โมเดล ClaudeClaude Codeครบทุกมิติใน section 6 และกฎ deny ใช้ได้ทุกโหมด
มีแผน ChatGPT อยู่แล้ว และอยากได้ sandbox ที่ระบบปฏิบัติการบังคับCodex CLIใช้ล็อกอินเดิมได้ และเครือข่ายปิดโดยค่าเริ่มต้น
ทำงานบน GitHub เป็นหลัก หรืออยากสลับโมเดลหลายค่ายในเครื่องมือเดียวGitHub Copilot CLIผสาน PR/issues ในตัว และเลือกโมเดลได้หลายค่าย
อยากได้เครื่องมือเบา ใช้โมเดลได้อิสระหรือรันในเครื่อง และชอบ workflow ที่ทุกอย่างเป็น commitAiderผูกกับ git และไม่ผูกกับค่ายโมเดล แลกกับการไม่มี MCP/hooks/permission
จะใช้ Geminiตรวจสถานะก่อนดูกล่องเตือนเรื่อง Antigravity CLI และตรวจแผนของคุณกับหน้าเอกสารทางการ

9. ข้อควรระวังและสิ่งที่ยังไม่ยืนยัน

ช่องว่างของข้อมูลในหน้านี้
  • Gemini CLI: สถานะสำหรับแผนจ่ายเงินและโควตาฟรีปัจจุบันไม่ชัด
  • Codex CLI: รายการ slash commands ปนกับแอป, ไม่พบตำแหน่งไฟล์ custom subagent, ไม่พบ custom prompts
  • Copilot CLI: เอกสาร billing ขัดกัน, ยังไม่ยืนยันว่า plugin ให้ hooks ได้หรือไม่, ส่วนท้ายของหน้า reference และส่วน hooks/permissions บางส่วนอ่านไม่ครบ
  • Claude Code: ไม่ได้อ่านเอกสาร hooks ฉบับเต็มและรายการตัวแปรสภาพแวดล้อมทั้งหมด; ชื่อไฟล์ settings ไม่ได้ยืนยัน
  • Aider: ค่า --edit-format และลำดับความสำคัญของไฟล์คอนฟิกไม่ได้ยืนยัน; อ่านหน้า issue tracker ไม่ได้

คำแนะนำก่อนใช้จริง: รัน --help ของแต่ละเครื่องมือ (Claude Code ระบุว่า --help ไม่ได้แสดงทุก flag ให้ดูหน้า CLI reference ประกอบ) และพิมพ์ / ใน TUI เพื่อดูรายการคำสั่งของเวอร์ชันที่ติดตั้งจริง เพราะชื่อโมเดล flag และราคาของเครื่องมือกลุ่มนี้เปลี่ยนภายในไม่กี่เดือน
