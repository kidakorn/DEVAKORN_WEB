01

§สถาปัตยกรรม — เลือกได้ 2 แบบ

จุดตัดสินใจแรกคือ "จะทิ้ง Apps Script ทั้งหมดเลยไหม" — คำตอบส่งผลถึงค่าใช้จ่ายโดยตรง เพราะ Cloud Functions (ตัวรับ LINE Webhook แบบ Firebase) ต้องผูกบัตรเครดิตถึงจะใช้ได้ ในขณะที่ Realtime Database ใช้ฟรีได้เลยไม่ต้องผูกบัตร

แนะนำ — เริ่มจากตรงนี้

B1 — แบบผสม (Hybrid)

ไม่ต้องผูกบัตรเครดิตเลย
  • เปลี่ยนแค่ "ที่เก็บสถานะ/คำสั่ง" จาก Google Sheet ไปเป็น Firebase Realtime Database
  • คง Apps Script ไว้เป็นตัวรับ LINE Webhook เหมือนเดิม แค่แก้ให้เขียนค่าไปที่ Firebase แทน Sheet (ยิง REST API ของ Firebase ได้ตรง ๆ)
  • ESP32 subscribe ค่าจาก Firebase แบบ real-time แทนการ poll ทุก 60 วิ
  • เก็บ log เซนเซอร์ไว้ที่ Google Sheet เหมือนเดิมก็ได้ (ของถนัดอยู่แล้ว)
Realtime Database + Apps Script อยู่ในแผนฟรีทั้งคู่ — ไม่ต้องกรอกบัตรเครดิตที่ไหนเลย

B2 — Full Firebase

ต้องผูกบัตรเครดิต (Blaze plan)
  • ย้าย LINE Webhook จาก Apps Script ไปเป็น Cloud Functions ทั้งหมด
  • เก็บ log เซนเซอร์ใน Firestore แทน Google Sheet
  • ทำเว็บแดชบอร์ดโฮสต์บน Firebase Hosting ในโปรเจ็คเดียวกัน จบทุกอย่างในระบบเดียว
  • ดูแลง่ายกว่าระยะยาวเพราะไม่ต้องสลับไปมาระหว่าง Google Apps Script กับ Firebase Console
ต้องอัปเกรดเป็น Blaze (ใส่บัตรเครดิต) ถึงจะ deploy Cloud Functions ได้ แม้ใช้งานจริงจะยังฟรีอยู่ก็ตาม — ดูรายละเอียดข้อ 06
คำแนะนำ: เริ่มจาก B1 ก่อนเสมอ เพราะได้ real-time control มาใช้จริงโดยไม่ต้องเสี่ยงเรื่องบัตรเครดิตเลย พอทำ B1 จนคล่องแล้วค่อยพิจารณาย้ายไป B2 ทีหลังถ้าอยากได้ระบบที่จบในที่เดียว — เอกสารนี้ครอบคลุมทั้งสองทาง ส่วนไหนต่างกันจะกำกับด้วยแท็ก B1/B2
02

§โครงสร้างข้อมูล (Data Model)

Realtime Database เก็บข้อมูลเป็นต้นไม้ JSON ต้นเดียว ออกแบบให้ ESP32 subscribe เฉพาะกิ่ง control/ พอ ไม่ต้องโหลดข้อมูลทั้งหมด

smart-farm-8/                        // รากของฐานข้อมูล
├── control/                         // ESP32 ฟังกิ่งนี้แบบ real-time
│   ├── fan: 0
│   ├── lamp1: 0
│   ├── lamp2: 0
│   ├── valve_water: 0
│   ├── valve_fertilizer: 0
│   ├── pump: 0
│   ├── mode: 0                      // 0=ปิด 1=เมลอน 2=แตงโม 3=สตอเบอรี่
│   └── camera_request: { cam1: 0, cam2: 0 }
├── sensors/
│   ├── latest/                      // ค่าล่าสุดอย่างเดียว อ่านเร็ว
│   │   ├── soil: { z1_1: 0, z1_2: 0, ... z4_3: 0 }
│   │   ├── temp: 0, humidity: 0, lux: 0
│   │   └── updated_at: 1722600000
│   └── log/{timestamp}/             // ประวัติย้อนหลัง ใช้ทำกราฟ
│       └── { soil, temp, humidity, lux }
└── meta/
    └── line_user_id: "Uxxxxxxxx"    // เก็บไว้ส่ง Push แจ้งเตือน

💡 เหตุผลที่แยก latest/ กับ log/: ESP32 กับแดชบอร์ดต้องการแค่ค่าล่าสุดบ่อย ๆ ถ้าไปอ่านจาก log/ ที่มีข้อมูลสะสมเยอะจะโหลดช้าและกินโควตาดาวน์โหลดเกินจำเป็น

03

§กฎความปลอดภัย (Security Rules)

ปัญหาที่เจอในรายงานก่อนหน้าคือ endpoint เดิมไม่มีการยืนยันตัวตนเลย — Firebase แก้ปัญหานี้ได้ตรงจุดด้วย Security Rules ที่เขียนแยกจากโค้ด ไม่ต้องเช็คเองในทุกฟังก์ชันเหมือนที่ผ่านมา

แนวคิดง่าย ๆ: อนุญาตให้อ่านได้ทุกคนที่มีลิงก์ (เพราะไม่ใช่ข้อมูลลับ) แต่ "เขียน" ได้เฉพาะคนที่ผ่านการยืนยันตัวตนแล้วเท่านั้น

{
  "rules": {
    "control": {
      ".read": true,
      ".write": "auth != null"        // ต้อง login/มี token ก่อนเขียนได้
    },
    "sensors": {
      ".read": true,
      ".write": "auth != null"
    }
  }
}

ฝั่ง ESP32 และ Apps Script ใช้ Firebase Auth แบบ Anonymous หรือ Legacy Database Secret เพื่อให้ผ่านเงื่อนไข auth != null ได้ — ไม่ต้องทำระบบ login ผู้ใช้จริงจังแบบเว็บทั่วไป เพราะอุปกรณ์ในระบบมีแค่ไม่กี่ตัว

05

§ข้อดี — ข้อเสีย ของการย้ายมา Firebase

✓ ข้อดี

  • ควบคุมอุปกรณ์แบบ real-time จริง (ไม่หน่วง 60 วิเหมือนเดิม)
  • Security Rules แยกออกจากโค้ด ปิดช่องโหว่เรื่อง auth ได้เป็นระบบมากกว่าเช็คเองทีละฟังก์ชัน
  • เป็นสกิลที่ใช้ได้จริงในงาน mobile/web dev ทั่วไป ไม่ใช่แค่ในวง Google Workspace
  • สเกลได้ถ้าอยากเพิ่มเซนเซอร์/อุปกรณ์ในอนาคต โดยไม่ต้องออกแบบฐานข้อมูลใหม่
  • มี Hosting + Cloud Messaging + Analytics ให้ในระบบเดียว เผื่อทำแอปมือถือคู่กันทีหลัง

✕ ข้อเสีย

  • ต้องเรียนรู้เพิ่ม: Firebase SDK ฝั่ง ESP32, แนวคิด Security Rules, Firebase Console
  • B2 (Cloud Functions) ต้องผูกบัตรเครดิตแม้บิลจะเป็น $0 ก็ตาม — บางคนไม่สบายใจเรื่องนี้
  • Blaze plan ไม่มีเพดานค่าใช้จ่ายตายตัว (no hard cap) ถ้าตั้งค่าโค้ดผิดเป็น loop ไม่มีที่สิ้นสุดอาจมีบิลไม่คาดคิดได้ ต้องตั้ง Budget Alert กันไว้
  • เอกสาร/ตัวอย่างส่วนใหญ่เป็นภาษาอังกฤษ และเปลี่ยนแปลง UI ของ Console บ่อย
  • ย้ายของเดิมที่ทำงานได้อยู่แล้ว (LINE Bot ผ่าน Apps Script) มีความเสี่ยงต้องดีบักใหม่ช่วงเปลี่ยนผ่าน
06

§ค่าใช้จ่าย — ตัวเลขจริง ไม่ประมาณเอง

Firebase มี 2 แผน: Spark (ฟรี ไม่ต้องผูกบัตร) และ Blaze (จ่ายตามการใช้งานจริง แต่ยังมีโควตาฟรีในตัวเหมือนกัน) ตัวเลขด้านล่างเช็คแล้ว ณ ปี 2026

บริการSpark (ฟรี)Blaze — ราคาเมื่อเกินโควตาฟรี
Realtime Database1GB เก็บข้อมูล + 10GB ดาวน์โหลด/เดือน$5/GB เก็บ, $1/GB ดาวน์โหลด
Firestore50,000 อ่าน + 20,000 เขียน/วัน, 1GB เก็บ$0.06/100k อ่าน, $0.18/100k เขียน
Cloud Functionsต้อง Blaze ถึง deploy ได้ฟรี 2 ล้านครั้งเรียก/เดือน แล้วจึงเริ่มคิดเงิน
Hosting10GB เก็บ+ส่งข้อมูล/เดือนคิดตามการใช้งานจริงถ้าเกิน
ประมาณการสำหรับโปรเจ็คนี้: ฟาร์มเดียว บอร์ดเดียว ส่งข้อมูลเซนเซอร์ไม่กี่ KB ต่อครั้ง — ทาง B1 ไม่ต้องผูกบัตรเลยและไม่มีค่าใช้จ่าย 0 บาทแน่นอน เพราะใช้แค่ Realtime Database (ฟรีในตัว Spark) ทาง B2 ต้องผูกบัตร แต่การใช้งานจริงยังอยู่ในโควตาฟรีของ Blaze สบาย ๆ (ห่างไกลจาก 2 ล้านครั้ง/เดือนมาก) ค่าใช้จ่ายจริงก็ยังเป็น ~$0/เดือน
ข้อควรระวังถ้าเลือก B2: Blaze ไม่มีเพดานตัดอัตโนมัติ แนะนำตั้ง Budget Alert ใน Google Cloud Console แจ้งเตือนทางอีเมลถ้ายอดใช้จ่ายเกิน $1 ไว้เป็นเซฟตี้ตั้งแต่วันแรกที่อัปเกรด กันเผลอเขียนโค้ด loop ผิดพลาดจนบิลบาน

§Roadmap

01เริ่มต้น

ตั้งโปรเจ็ค Firebase B1

  • สร้างโปรเจ็คใน Firebase Console (Spark plan ฟรี ไม่ต้องผูกบัตร)
  • เปิดใช้ Realtime Database เลือก region ที่ใกล้ที่สุด
  • ตั้ง Security Rules ตามข้อ 03 และเปิด Anonymous Auth
02ต่อ ESP32

เชื่อมเฟิร์มแวร์เข้า Firebase B1

  • ติดตั้งไลบรารี Firebase-ESP-Client ผ่าน PlatformIO
  • แก้โค้ดจากที่เคย http.GET() ไปหา Apps Script เป็น subscribe stream จาก control/ แทน
  • ทดสอบผ่าน Wokwi ก่อน ยังไม่ต้องมีบอร์ดจริง
03ต่อ LINE Bot

แก้ code.gs ให้เขียนลง Firebase B1

  • แก้ฟังก์ชัน update_data() / update_status() ให้ยิง REST API ของ Firebase RTDB แทนการเขียน Google Sheet
  • เก็บ line_user_id ไว้ที่ meta/ สำหรับใช้ Push แจ้งเตือนภายหลัง
  • ทดสอบว่าพิมพ์ on_off_fan ในแชทแล้วค่าใน Firebase เปลี่ยนจริง
04แดชบอร์ด

ทำเว็บอ่านค่าจาก Firebase B1

  • หน้าเว็บง่าย ๆ ใช้ Firebase JS SDK อ่าน sensors/latest แบบ real-time ขึ้นจอทันทีไม่ต้องรีเฟรช
  • กราฟย้อนหลังจาก sensors/log ด้วย Chart.js
  • โฮสต์ฟรีบน Firebase Hosting หรือ GitHub Pages ก็ได้ (ยังไม่ต้อง Blaze)
05ถ้าอยากไปต่อ

ย้ายเป็น Full Firebase B2

  • อัปเกรดเป็น Blaze + ตั้ง Budget Alert ทันที
  • เขียน Cloud Function รับ LINE Webhook แทน Apps Script ทั้งหมด
  • ย้าย log เซนเซอร์จาก Google Sheet ไป Firestore ถ้าต้องการ query ที่ซับซ้อนขึ้น
08

§เช็คลิสต์เริ่มต้น

  • สมัคร Firebase project ใหม่ (ใช้ Google account เดียวกับที่มี Google Sheet เดิมก็ได้)
  • เปิด Realtime Database + ตั้ง Security Rules ตามข้อ 03
  • ลองยิง REST API ของ Firebase ด้วย Postman/curl ก่อน ให้เข้าใจการอ่าน/เขียนก่อนไปแตะโค้ด ESP32
  • ตั้งโปรเจ็ค Wokwi จำลอง ESP32 เชื่อม Firebase ทดสอบ control/ ให้ทำงานก่อนมีบอร์ดจริง
  • แก้ code.gs ให้เขียนลง Firebase แทน Sheet ทีละฟังก์ชัน ทดสอบทีละคำสั่งไป
