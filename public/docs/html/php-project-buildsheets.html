ก่อนกลับไปลุย Ledger ERP

คู่มือแบบลงมือทำ ไม่ใช่บทความอ่านเฉยๆ แต่ละโปรเจ็คคือ "ใบสั่งงาน" ที่มีขอบเขตชัดเจนพอจะทำจบได้ในหนึ่งรอบที่ว่าง พร้อมเหตุผลเบื้องหลัง การตัดสินใจทางเทคนิคของแต่ละจุด ไม่ใช่แค่บอกว่าต้องทำอะไร

01

ทำตามลำดับ ไม่ใช่ตามใจ แต่ละโปรเจ็คถูกจัดลำดับให้ทักษะที่ได้จากอันก่อนหน้าถูกใช้ซ้ำในอันถัดไป ข้ามลำดับได้ถ้าอยากลองเรื่องใดเรื่องหนึ่งเจาะจง แต่ถ้าไม่มีเหตุผลเฉพาะ ทำเรียงจะได้ผลลัพธ์การเรียนรู้ดีกว่า

02

อ่านหัวข้อ "แนวคิดหลัก" ในหน้าถัดไปก่อน เป็นแพทเทิร์นที่ใช้ซ้ำในทุกโปรเจ็ค ถ้าเข้าใจตรงนั้นแน่นๆ การอ่านสเปกแต่ละโปรเจ็คจะเร็วขึ้นมาก เพราะจะรู้ทันทีว่า "จุดยากของโปรเจ็คนี้อยู่ตรงไหน"

03

ทำโครงสร้างให้เหมือนงาน Ledger ERP Composer + PSR-4 autoload, ไม่ใช้ framework, แยก Core/Modules/Shared เหมือนเดิม จะได้ไม่ต้องเรียนรู้ pattern ใหม่ทุกครั้ง และเทียบกับงานจริงที่เคยทำได้ตรงๆ

04

สเปกในนี้คือขอบเขตขั้นต่ำ ไม่ใช่เพดาน แต่ละใบบอก "ต้องมีอะไรถึงจะเรียกว่าจบ" ถ้าอยากต่อยอด (เพิ่ม UI สวยๆ, เพิ่ม export Excel ฯลฯ) ทำได้เต็มที่หลังจากจุดที่กำหนดไว้ผ่านแล้ว

Sheet 00 (ต่อ)

แนวคิดหลักที่ใช้ซ้ำทุกโปรเจ็ค

5 pattern นี้จะเจอซ้ำๆ ในทุกใบงาน เข้าใจตรงนี้ก่อนแล้วสเปกที่เหลือจะอ่านง่ายขึ้นมาก

1. ตรวจช่วงเวลาทับซ้อน (Overlap check)

ใช้ในโปรเจ็ค 01 และ 06 ปัญหาคือ "จองเวลา A-B ได้ไหม เมื่อมีคนจองไว้แล้วบางช่วง" เงื่อนไขทับซ้อนที่ถูกต้องคือ: ช่วงใหม่ทับกับช่วงเก่า ก็ต่อเมื่อ เวลาเริ่มใหม่ น้อยกว่า เวลาจบเก่า และ เวลาจบใหม่ มากกว่า เวลาเริ่มเก่า

SELECT COUNT(*) FROM appointments
WHERE staff_id = :staff_id
  AND start_time < :new_end
  AND end_time > :new_start
ทำไมไม่เช็คแค่ "เวลาเริ่มตรงกัน" เพราะการจองจริงมีความยาวไม่เท่ากัน ถ้าเช็คแค่จุดเริ่ม จะพลาดเคสที่ช่วงเวลาซ้อนกันตรงกลาง เช่น ของเก่า 10:00-11:00 ของใหม่ 10:30-10:45 เวลาเริ่มไม่ตรงกันเลยแต่ทับกันเต็มๆ

2. State Machine (เครื่องสถานะ)

ใช้ในโปรเจ็ค 02, 03, 06 คือการกำหนดว่า "จากสถานะ A ไปสถานะไหนได้บ้าง" เขียนเป็นตารางที่เดียว ไม่กระจายเงื่อนไข if/else ไปทั่วโค้ด

const TRANSITIONS = [
    'open'        => ['assigned'],
    'assigned'    => ['in_progress', 'open'],
    'in_progress' => ['resolved'],
    'resolved'    => ['closed', 'in_progress'],
    'closed'      => [],
];
ทำไมไม่ใช้ if แยกทีละจุด ถ้าเขียน if ทั่วระบบ วันหนึ่งกฎเปลี่ยน (เช่น เพิ่มสถานะ "รอชิ้นส่วน") จะต้องไล่แก้หลายที่ เก็บกฎไว้ในตารางเดียว แก้ที่เดียวจบ และตรวจสอบ transition ผิดกฎได้ง่ายด้วยเช็คตารางนี้ก่อนบันทึก

3. Immutable log (บันทึกที่แก้ไขย้อนหลังไม่ได้)

ใช้ในโปรเจ็ค 02 และ 04 หลักการคือ ห้าม UPDATE หรือ DELETE แถวประวัติ ถ้าข้อมูลเปลี่ยน ให้ INSERT แถวใหม่แทน แล้วคำนวณค่าปัจจุบันจากผลรวมของ log ทั้งหมด

-- ยอดคะแนนสมาชิกไม่ใช่ column ที่ UPDATE ตรงๆ
-- แต่คำนวณจาก log ทุกครั้ง
SELECT SUM(points) FROM point_transactions
WHERE member_id = :member_id
ทำไมไม่เก็บแค่ยอดรวมแล้วอัปเดตทับ ถ้าเก็บแค่ยอดปัจจุบันแล้ว UPDATE ทับทุกครั้ง เวลามีข้อผิดพลาด (เช่น แต้มผิด, ทุจริต) จะตรวจสอบย้อนหลังไม่ได้ว่าเกิดอะไรขึ้น การเก็บ log ทำให้ตรวจสอบได้เสมอ เหมือนสมุดบัญชีจริง ที่ไม่มีใครขีดฆ่าตัวเลขแล้วเขียนทับ

4. Transaction สำหรับงานข้ามตาราง

ใช้ทุกโปรเจ็คที่มีการ "ตัดของ" พร้อมกับ "บันทึกรายการ" (เบิกของ, จองอุปกรณ์, แลกแต้ม) สองการเขียนนี้ต้องสำเร็จพร้อมกันหรือไม่สำเร็จเลยทั้งคู่

$db->beginTransaction();
try {
    // 1. ลดจำนวนของที่มีอยู่
    // 2. บันทึกรายการเบิก
    $db->commit();
} catch (Throwable $e) {
    $db->rollBack();
    throw $e;
}
ทำไมต้องเป็น transaction ถ้าขั้นตอนที่ 1 สำเร็จแต่ขั้นตอนที่ 2 ล้มเหลว (เซิร์ฟเวอร์ล่มพอดี) ของจะถูกตัดออกจากสต็อก โดยไม่มีบันทึกว่าใครเอาไป ข้อมูลจะไม่ตรงกับความจริงถาวร transaction ป้องกันเคสแบบนี้

5. Role-based access (สิทธิ์ตามบทบาท)

ใช้ในโปรเจ็ค 02, 03, 06 คนละบทบาทเห็นคนละหน้า/ทำคนละ action ได้ เขียนเป็น middleware ตรวจก่อนเข้า route เดียว ไม่ใช่เช็คสิทธิ์ซ้ำในทุก Controller

ทำไมเช็คที่ middleware ไม่ใช่ในแต่ละ Controller ถ้าลืมเช็คในสัก Controller เดียว จะเป็นช่องโหว่ทันที การเช็คที่จุดเดียวก่อนเข้าถึง route ทุกเส้นทางไม่มีทางลืม เพราะเป็นด่านที่บังคับผ่านเสมอ

BUILD SHEET NO. 01

ระบบจองคิวร้านตัดผม / คลินิก

ความยาก: เล็ก
เวลา: 1–2 วัน
โฟกัส: Overlap Check

เป้าหมายการฝึก

ฝึก CRUD พื้นฐานให้คล่องมือ พร้อมโจทย์แรกที่ "ตรรกะ" สำคัญกว่าหน้าตา: กันไม่ให้จองเวลาที่ทับกับคิวเดิมของช่างคนเดียวกัน

ตารางที่ต้องมี

ตารางคอลัมน์สำคัญ
staffid, name, service_ids (บริการที่ทำได้)
servicesid, name, duration_minutes, price
customersid, name, phone
appointmentsid, staff_id, customer_id, service_id, start_time, end_time, status

จุดที่ต้องคิดให้ดีก่อนเขียนโค้ด

  • เวลาเริ่ม-จบคำนวณจาก duration_minutes ของบริการที่เลือก ไม่ใช่ให้ผู้ใช้กรอกเอง
  • เช็ค overlap (ดูแนวคิดหลักข้อ 1) ก่อน INSERT ทุกครั้ง ไม่ใช่แค่ฝั่ง JavaScript หน้าเว็บ เพราะ client-side ข้ามได้เสมอ
  • สถานะนัดหมาย: booked → completed หรือ cancelled ยกเลิกแล้วต้องเปิดช่องเวลานั้นให้จองใหม่ได้

ขั้นตอนการทำ

  1. ตั้งโครงโปรเจ็ค composer.json แบบ PSR-4, ก็อปปี้ Core/ (Router, Database, BaseController, BaseModel) จากงาน Ledger ERP มาใช้ตรงๆ ได้เลย ไม่ต้องเขียนใหม่
  2. เขียน schema.sql สร้าง 4 ตารางตามสเปกด้านบน ใส่ข้อมูลตัวอย่าง (seed) ช่าง 2-3 คน และบริการ 3-4 รายการ จะได้มีข้อมูลทดสอบทันทีโดยไม่ต้องกรอกเองทุกครั้ง
  3. สร้าง Model ทั้ง 4 ตัว StaffModel, ServiceModel, CustomerModel, AppointmentModel extends BaseModel ตั้งแค่ $table ก่อน ยังไม่ต้องมี method พิเศษ
  4. ทำหน้ารายการนัดหมาย route GET /appointments แสดงนัดหมายของวันนั้นๆ เรียงตามเวลา ทำให้ดูออกก่อนว่าข้อมูลไหลถูกต้อง ก่อนจะไปยุ่งกับ logic ที่ซับซ้อนกว่า
  5. เขียน overlap check ก่อน แยกเป็น method เดี่ยว AppointmentModel::hasOverlap($staffId, $start, $end) ตามแนวคิดหลักข้อ 1 เขียนแยกและทดสอบให้แน่ใจว่าถูกก่อน ค่อยเอาไปต่อกับฟอร์ม จะดีบักง่ายกว่าเขียนปนกับ Controller
  6. ทำฟอร์มจองคิว route GET /appointments/create (ฟอร์ม) และ POST /appointments (บันทึก) คำนวณ end_time จาก duration_minutes ของบริการที่เลือก เรียก hasOverlap ก่อน insert เสมอ
  7. ทำปุ่มยกเลิกนัด route POST /appointments/{id}/cancel เปลี่ยน status เป็น cancelled ไม่ต้องลบแถวทิ้ง เก็บไว้เป็นประวัติ
  8. ทดสอบตามเกณฑ์ด้านล่างด้วยมือ ลองจองซ้อนเวลาจริงๆ ดูว่าโดนปฏิเสธไหม ก่อนจะถือว่าจบ

เกณฑ์ว่าจบแล้ว

  • จองสำเร็จเมื่อเวลาว่างจริง
  • พยายามจองเวลาที่ทับกับคิวเดิมของช่างคนเดียวกัน ต้องถูกปฏิเสธพร้อมข้อความบอกเหตุผล
  • ยกเลิกนัดแล้ว ช่วงเวลานั้นจองใหม่ได้ทันที
Prompt คัดลอกทั้งกล่องไปวางสั่ง agent ได้เลย 
สร้างระบบจองคิวร้านตัดผม/คลินิกด้วย Plain PHP ไม่ใช้ framework ใดๆ ใช้ Composer เฉพาะ PSR-4 autoload เท่านั้น

กติกาที่ต้องทำตามทุกจุด:
- ห้ามใช้ emoji ทุกที่ ทั้งโค้ด คอมเมนต์ และข้อความในระบบ
- เข้าถึงฐานข้อมูลด้วย PDO prepared statements เท่านั้น ห้าม concatenate string เข้า SQL
- โค้ดที่มี logic ไม่ตรงไปตรงมา ต้องมีคอมเมนต์อธิบายว่าทำไมถึงเขียนแบบนี้ ไม่ใช่แค่อธิบายว่าทำอะไร
- ทุก input ต้อง validate ก่อนถึงชั้น Model เสมอ

โครงสร้าง: src/Core (Router, Database, BaseController, BaseModel แบบ CRUD ทั่วไป), src/Modules ต่อโมดูล, views เป็น PHP template ธรรมดา

สร้าง 4 ตาราง: staff, services, customers, appointments (ดูคอลัมน์จากสเปกที่แนบ) ทำ overlap check เป็น method แยกชื่อ AppointmentModel::hasOverlap($staffId, $start, $end) โดยเช็คเงื่อนไข: เวลาเริ่มใหม่ < เวลาจบเก่า AND เวลาจบใหม่ > เวลาเริ่มเก่า ต้องเรียก method นี้ก่อน insert นัดหมายทุกครั้ง ห้าม bypass

ทำตามลำดับนี้: (1) schema + seed ข้อมูล (2) Model ทั้ง 4 ตัว (3) หน้ารายการนัดหมาย (4) hasOverlap แยกทดสอบก่อน (5) ฟอร์มจอง (6) ปุ่มยกเลิก

ทำทีละขั้นแล้วรายงานผลก่อนไปขั้นถัดไป เกณฑ์จบ: จองซ้อนเวลาต้องถูกปฏิเสธจริงจากฝั่งเซิร์ฟเวอร์ (ทดสอบด้วยการยิง request ตรงๆ ไม่ใช่แค่ผ่าน UI) และยกเลิกนัดแล้วเวลานั้นต้องจองใหม่ได้ทันที

BUILD SHEET NO. 02

ระบบเบิก-คืนอุปกรณ์ในออฟฟิศ

ความยาก: เล็ก-กลาง
เวลา: 1–2 วัน
โฟกัส: Workflow + Audit Trail

เป้าหมายการฝึก

ฝึก workflow ที่มีขั้นตอนอนุมัติ และฝึกเก็บ audit trail แบบ immutable log (แนวคิดหลักข้อ 3) ซึ่งเป็นพื้นฐานสำคัญของงานบัญชี/การเงินที่จะเจอในงานจริงบ่อยๆ

ตารางที่ต้องมี

ตารางคอลัมน์สำคัญ
equipment_itemsid, name, total_qty, available_qty
employeesid, name, department
checkout_requestsid, item_id, employee_id, qty, status, requested_at
checkout_logsid, request_id, action, actor_id, created_at (insert-only)

จุดที่ต้องคิดให้ดีก่อนเขียนโค้ด

  • สถานะ: requested → approved → checked_out → returned (หรือ rejected จาก requested) ใช้ตาราง transition แบบแนวคิดหลักข้อ 2
  • ทุกการเปลี่ยนสถานะ INSERT แถวใหม่ใน checkout_logs ห้ามลบของเก่า แม้ผู้ดูแลจะอยากแก้ประวัติก็ตาม
  • การลด/เพิ่ม available_qty ต้องอยู่ใน transaction เดียวกับการเปลี่ยนสถานะ (แนวคิดหลักข้อ 4)

ขั้นตอนการทำ

  1. ตั้งโครงโปรเจ็ค + schema Core เดิมจาก ERP, สร้าง 4 ตารางตามสเปก ใส่อุปกรณ์ตัวอย่าง 5-6 ชิ้น พร้อม available_qty เริ่มต้น
  2. เขียนตาราง state transition ก่อน ตาม pattern แนวคิดหลักข้อ 2 กำหนดให้ชัดว่าจาก requested ไปได้แค่ approved หรือ rejected เท่านั้น เขียนเป็น const ในคลาสเดียว ก่อนเริ่มเขียน Controller ใดๆ
  3. ทำ RequestModel + LogModel extends BaseModel ปกติ แต่ LogModel ไม่มี method update หรือ delete เลย (ลบ method ออกจากคลาสไปเลยเพื่อบังคับว่า insert-only จริง)
  4. ทำ POST /requests (สร้างคำขอ) สถานะเริ่มต้น requested พร้อม insert แถวแรกใน checkout_logs
  5. ทำ POST /requests/{id}/approve เช็คตาราง transition ก่อนว่า requested → approved ถูกกฎไหม เฉพาะ role ผู้อนุมัติเรียกได้ เปลี่ยนสถานะ + insert log ในการเรียกเดียวกัน
  6. ทำ POST /requests/{id}/checkout ลด available_qty ของอุปกรณ์ พร้อมเปลี่ยนสถานะเป็น checked_out และ insert log ทั้งหมดอยู่ใน transaction เดียว (แนวคิดหลักข้อ 4) เพราะถ้าลด qty สำเร็จ แต่เปลี่ยนสถานะไม่สำเร็จ ข้อมูลจะเพี้ยนทันที
  7. ทำ POST /requests/{id}/return คืน available_qty กลับ, สถานะเป็น returned, insert log ปิดท้าย

จุดที่ต้องคิดให้ดีก่อนเขียนโค้ด

  • slug ต้อง unique เสมอ ถ้าชื่อโพสต์ซ้ำ ต้องต่อท้ายอัตโนมัติ (เช่น -2) ไม่ใช่ปล่อยให้ error ตอน INSERT
  • อัปโหลดไฟล์ต้องตรวจ MIME type จริงของไฟล์ (ไม่ใช่เชื่อแค่นามสกุลที่ผู้ใช้ตั้ง) และเปลี่ยนชื่อไฟล์เป็นค่าที่ระบบสร้างเอง ไม่ใช้ชื่อไฟล์เดิมจากผู้ใช้ตรงๆ (ป้องกัน path/injection ผ่านชื่อไฟล์)
  • โพสต์ draft เข้าถึงได้เฉพาะคนที่ล็อกอินเป็นแอดมิน ส่วน published เท่านั้นที่คนทั่วไปเห็น

ขั้นตอนการทำ

  1. ตั้งโครงโปรเจ็ค + schema Core เดิม, สร้าง 4 ตาราง, สร้างโฟลเดอร์ public/uploads/ แยกออกจาก src/ ให้ชัดเจน (ไฟล์ที่ผู้ใช้อัปโหลดไม่ควรอยู่ปนกับโค้ด)
  2. เขียนฟังก์ชันสร้าง slug ก่อน แปลงชื่อโพสต์เป็น slug, เช็คว่าซ้ำไหมใน DB, ถ้าซ้ำต่อท้ายด้วยเลข (-2, -3 ไล่ไป) เขียนและทดสอบฟังก์ชันนี้แยกก่อนเอาไปต่อกับฟอร์ม
  3. ทำ PostModel + CategoryModel extends BaseModel ปกติ
  4. ทำฟอร์มสร้าง/แก้ไขโพสต์ POST /posts บันทึกเป็น status = draft เสมอ ไม่มีทางสร้างโพสต์ที่ publish ทันทีจากฟอร์มนี้ ต้องกดปุ่ม publish แยกต่างหาก
  5. ทำตัวจัดการอัปโหลดไฟล์แยกเป็น class เดียว Shared\FileUploader ใช้ finfo_file() ตรวจ MIME type จริง ของไฟล์ (ไม่ใช่ดูแค่นามสกุล) แล้วสร้างชื่อไฟล์ใหม่ด้วย uniqid() หรือ hash ไม่ใช้ชื่อไฟล์เดิมจากผู้ใช้เด็ดขาด
  6. เชื่อมอัปโหลดเข้ากับฟอร์มโพสต์ บันทึกผลลัพธ์ลง media พร้อม post_id ที่เกี่ยวข้อง
  7. ทำปุ่ม publish POST /posts/{id}/publish เปลี่ยน status = published และตั้ง published_at = NOW()
  8. ทำหน้ารายการสาธารณะ query เฉพาะ status = published เท่านั้น เรียงตาม published_at ล่าสุดก่อน
  9. ทดสอบ ตั้งชื่อโพสต์ซ้ำ 2 ครั้งดู slug, ลองอัปโหลดไฟล์ปลอมนามสกุล (เช่นเปลี่ยน .php เป็น .jpg) ต้องถูกปฏิเสธจาก MIME check ไม่ใช่แค่ดูนามสกุลผ่าน

เกณฑ์ว่าจบแล้ว

  • ตั้งชื่อโพสต์ซ้ำกัน 2 ครั้ง ได้ slug ไม่ชนกันทั้งคู่
  • อัปโหลดไฟล์ที่ไม่ใช่รูปภาพ (เช่นเปลี่ยนนามสกุล .php เป็น .jpg) ต้องถูกปฏิเสธ
  • โพสต์สถานะ draft ไม่โผล่ในหน้ารายการสาธารณะ

กติกาที่ต้องทำตามทุกจุด:
- ห้ามใช้ emoji ทุกที่ ทั้งโค้ด คอมเมนต์ และข้อความในระบบ
- เข้าถึงฐานข้อมูลด้วย PDO prepared statements เท่านั้น
- โค้ดที่มี logic ไม่ตรงไปตรงมา ต้องมีคอมเมนต์อธิบายว่าทำไมถึงเขียนแบบนี้
- ทุก input ต้อง validate ก่อนถึงชั้น Model เสมอ

สร้าง 4 ตาราง: posts, categories, post_categories (many-to-many), media เก็บไฟล์อัปโหลดไว้ที่ public/uploads/ แยกจาก src/ ให้ชัดเจน

จุดสำคัญที่หนึ่งของงานนี้: เขียนฟังก์ชันสร้าง slug ก่อนอย่างอื่นทั้งหมด แปลงชื่อโพสต์เป็น slug แบบ URL-safe เช็คว่าซ้ำกับที่มีอยู่ใน DB ไหม ถ้าซ้ำต่อท้ายด้วยเลข -2, -3 ไล่ไปจนกว่าจะไม่ซ้ำ ห้ามปล่อยให้ INSERT ล้มเหลวเพราะ slug ซ้ำ

จุดสำคัญที่สองของงานนี้: การอัปโหลดไฟล์ทำเป็นคลาสแยก (เช่น Shared\FileUploader) ตรวจชนิดไฟล์จริงด้วย finfo_file() ไม่ใช่ดูจากนามสกุลไฟล์ที่ผู้ใช้ตั้ง อนุญาตเฉพาะ MIME type ของรูปภาพเท่านั้น (image/jpeg, image/png, image/webp) แล้วสร้างชื่อไฟล์ใหม่ด้วย hash หรือ uniqid ห้ามใช้ชื่อไฟล์เดิมจากผู้ใช้เก็บลงระบบไฟล์เด็ดขาด

โพสต์ที่สร้างใหม่ทุกครั้งต้องมี status = draft เท่านั้น การเปลี่ยนเป็น published ต้องทำผ่าน endpoint แยกต่างหากเสมอ ไม่มีทางสร้างโพสต์ publish ได้ในการเรียกครั้งเดียว

ทำตามลำดับ: (1) schema + โฟลเดอร์ uploads (2) ฟังก์ชันสร้าง slug แยกทดสอบก่อน (3) Model (4) ฟอร์มสร้าง/แก้ไขโพสต์ (5) FileUploader (6) เชื่อมอัปโหลดเข้าฟอร์ม (7) ปุ่ม publish (8) หน้ารายการสาธารณะ

ทำทีละขั้นแล้วรายงานผลก่อนไปขั้นถัดไป เกณฑ์จบ: ตั้งชื่อโพสต์ซ้ำ 2 ครั้งต้องได้ slug ไม่ชนกัน, อัปโหลดไฟล์ปลอมนามสกุลต้องถูกปฏิเสธจาก MIME check จริง ไม่ใช่แค่ดูนามสกุลผ่าน

ระบบเช่า-คืนอุปกรณ์ (กล้อง / เครื่องมือช่าง)

ความยาก: กลาง-ใหญ่
เวลา: 3–4 วัน
โฟกัส: รวมทุกแนวคิดหลัก

เป้าหมายการฝึก

โปรเจ็คปิดท้าย รวมทุกแนวคิดหลัก (1–5) ไว้ในระบบเดียว: จองล่วงหน้าแบบเช็คช่วงวันที่ทับซ้อน, สถานะของหลายขั้น, คำนวณค่าปรับคืนช้าแบบธุรกรรมการเงิน, และสิทธิ์ตามบทบาท

ตารางที่ต้องมี

ตารางคอลัมน์สำคัญ
equipmentid, name, daily_rate, condition (ok/damaged), status
rentalsid, equipment_id, customer_id, start_date, due_date, returned_date, status
late_feesid, rental_id, days_late, amount (insert-only)
damage_reportsid, rental_id, description, reported_at

จุดที่ต้องคิดให้ดีก่อนเขียนโค้ด

  • เช็คทับซ้อนของช่วง start_date–due_date เหมือนโปรเจ็ค 01 แต่เป็นระดับวันแทนนาที (แนวคิดหลักข้อ 1)
  • สถานะของ: available → reserved → rented → returned หรือ damaged ถ้าคืนแล้วชำรุด
  • ค่าปรับคำนวณตอนคืนของ: days_late = คืนจริง - due_date (ถ้าติดลบหรือศูนย์ = ไม่มีค่าปรับ) แล้ว amount = days_late * daily_rate บันทึกเป็นแถวใหม่เสมอ ไม่ทับของเดิม
  • อัปเดตสถานะของ, บันทึกค่าปรับ, และปิด rental ต้องอยู่ใน transaction เดียวกัน

ขั้นตอนการทำ

  1. ตั้งโครงโปรเจ็ค + schema Core เดิม, สร้าง 4 ตาราง, seed อุปกรณ์ตัวอย่าง 5-6 ชิ้น พร้อม daily_rate
  2. ทำ overlap check ระดับวัน RentalModel::hasOverlap($equipmentId, $startDate, $dueDate) ใช้ตรรกะเดียวกับโปรเจ็ค 01 (แนวคิดหลักข้อ 1) แค่เทียบเป็นวันแทนนาที เขียนแยกทดสอบก่อนต่อกับฟอร์มเหมือนเดิม
  3. เขียนตาราง state transition ของอุปกรณ์ available → reserved → rented → returned หรือแตกไป damaged ตอนคืน ตามแนวคิดหลักข้อ 2
  4. ทำ POST /rentals (จอง) เรียก hasOverlap ก่อน insert เสมอ สถานะเริ่มต้น reserved
  5. ทำ POST /rentals/{id}/checkout เปลี่ยนสถานะอุปกรณ์เป็น rented ตอนลูกค้ามารับของจริง
  6. ทำฟังก์ชันคำนวณค่าปรับแยกเป็น method เดียว calculateLateFee($dueDate, $returnedDate, $dailyRate): days_late = returnedDate - dueDate ถ้าค่าติดลบหรือศูนย์คืนค่า 0 ไม่ใช่ค่าติดลบ เขียนและทดสอบแยกก่อนต่อกับ route คืนของ
  7. ทำ POST /rentals/{id}/return ขั้นตอนภายในต้องอยู่ใน transaction เดียว: เรียก calculateLateFee, insert แถวใน late_fees ถ้ามีค่าปรับ, รับ input ว่าชำรุดไหม (ถ้าใช่ insert damage_reports และตั้งสถานะอุปกรณ์เป็น damaged แทน available), ปิด rental เป็น returned
  8. ทำหน้ารายงานของชำรุด join damage_reports กับ rentals เพื่อดูว่าใครยืมตอนของชำรุด
  9. ทดสอบครบทั้ง 4 เกณฑ์ด้านล่าง โดยเฉพาะกรณีคืนตรงเวลาต้องไม่มีค่าปรับเกิดขึ้นเลย (ไม่ใช่ค่าปรับ 0 บาทที่ insert ทิ้งไว้เฉยๆ)

เกณฑ์ว่าจบแล้ว

  • จองอุปกรณ์ชิ้นเดียวกันในช่วงวันที่ทับซ้อนกัน ต้องถูกปฏิเสธ
  • คืนของช้า 3 วัน อัตรา 100 บาท/วัน ต้องคำนวณค่าปรับได้ 300 บาทพอดี
  • คืนของตรงเวลาหรือเร็วกว่ากำหนด ไม่มีค่าปรับเกิดขึ้น
  • รายงานของที่ชำรุดเชื่อมกับ rental ที่ถูกต้อง ตรวจสอบย้อนกลับได้ว่าใครยืมตอนชำรุด

กติกาที่ต้องทำตามทุกจุด:
- ห้ามใช้ emoji ทุกที่ ทั้งโค้ด คอมเมนต์ และข้อความในระบบ
- เข้าถึงฐานข้อมูลด้วย PDO prepared statements เท่านั้น
- โค้ดที่มี logic ไม่ตรงไปตรงมา ต้องมีคอมเมนต์อธิบายว่าทำไมถึงเขียนแบบนี้

สร้าง 4 ตาราง: equipment, rentals, late_fees (insert-only), damage_reports

เขียน RentalModel::hasOverlap($equipmentId, $startDate, $dueDate) ก่อนอย่างอื่น ใช้ตรรกะเดียวกับการเช็คช่วงเวลาทับซ้อนทั่วไป: เริ่มใหม่ < จบเก่า AND จบใหม่ > เริ่มเก่า แต่เทียบเป็นวันแทนนาที ต้องเรียกก่อน insert การจองทุกครั้ง

เขียนตาราง state transition ของอุปกรณ์ก่อนเขียน Controller: available -> reserved -> rented -> returned หรือแตกไป damaged ตอนคืนถ้าชำรุด เก็บเป็น const array ที่เดียว

จุดสำคัญที่สุดของงานนี้คือการคำนวณค่าปรับ เขียนเป็น method แยก calculateLateFee($dueDate, $returnedDate, $dailyRate): คำนวณ days_late = returnedDate - dueDate ถ้าค่าออกมาติดลบหรือศูนย์ให้คืนค่า 0 (ห้ามคืนค่าติดลบ) แล้ว amount = days_late * dailyRate เขียนและทดสอบ method นี้แยกก่อนเอาไปต่อกับ route คืนของ

ขั้นตอนคืนของ (return) ต้องอยู่ใน database transaction เดียว: เรียก calculateLateFee, insert แถวใน late_fees เฉพาะกรณีมีค่าปรับจริง (ห้าม insert แถวค่าปรับ 0 บาททิ้งไว้เฉยๆ), รับ input ว่าชำรุดไหม ถ้าใช่ insert damage_reports และตั้งสถานะอุปกรณ์เป็น damaged แทน available, ปิดสถานะ rental เป็น returned

ทำตามลำดับ: (1) schema + seed อุปกรณ์ (2) hasOverlap แยกทดสอบก่อน (3) ตาราง state transition (4) สร้างการจอง (5) checkout (6) calculateLateFee แยกทดสอบก่อน (7) return รวมทุกอย่างใน transaction (8) หน้ารายงานของชำรุด
