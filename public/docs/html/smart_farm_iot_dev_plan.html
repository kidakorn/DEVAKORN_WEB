01

§เป้าหมายเฟสนี้

จากรายงานสำรวจรอบแรก ตอนนี้รู้แล้วว่าอะไรพังจริง (LINE Notify) อะไรใช้ได้จริง (LINE Bot แชท) และอะไรเป็นแค่ "ข้อจำกัดที่ต้องรู้ไว้" ไม่ใช่ปัญหาเร่งด่วน (โควตา Apps Script) เป้าหมายเฟสนี้คือ 3 อย่าง:

  • ตัดสินใจว่าจะ "อยู่กับของเดิม + ปะรู" หรือ "ย้ายสถาปัตยกรรมใหม่บางส่วน" โดยมีข้อมูลโควตา/ข้อจำกัดจริงประกอบการตัดสินใจ ไม่ใช่เดา
  • ปิดช่องโหว่ความปลอดภัยที่เจอไปแล้ว (token ฝังโค้ด, ไม่เช็ค signature) ไม่ว่าจะเลือกทางไหน
  • ทำทุกอย่างได้บนคอมพิวเตอร์ล้วน ๆ ผ่านการจำลอง จนกว่าฮาร์ดแวร์จริงจะพร้อม
02

§เช็คสถานะบริการที่ใช้อยู่

ไล่ทีละบริการที่โปรเจ็คพึ่งพา ว่าตอนนี้ (สิงหาคม 2026) สถานะเป็นยังไง — ข้อมูลจากการค้นล่าสุด ไม่ใช่ความจำเก่า เพราะบริการพวกนี้เปลี่ยนนโยบายกันบ่อย

สถานะบริการรายละเอียด
เลิกใช้แล้วLINE Notifyปิดถาวรตั้งแต่ 31 มี.ค. 2025 — ฟังก์ชัน LINE.notify() ในเฟิร์มแวร์ใช้ไม่ได้อีกต่อไป ต้องแทนที่ทั้งหมด ไม่มีทางเลือกอื่นนอกจากย้าย
ใช้งานได้Google Apps Script (Web App)ยังใช้งานได้ปกติ ฟรี ไม่มีค่าใช้จ่าย โควตาบัญชีทั่วไป: URL Fetch 20,000 ครั้ง/วัน, รันสคริปต์ต่อครั้งไม่เกิน 6 นาที, trigger รวม 90 นาที/วัน — ระบบปัจจุบัน poll ทุก 60 วิ ≈ 1,440 ครั้ง/วัน ใช้ไปแค่ ~7% ของโควตา ยังไม่ใช่คอขวดสำหรับสเกลนี้
ใช้งานได้LINE Messaging API — Replyข้อความตอบกลับผ่าน replyToken (ที่ code.gs ใช้อยู่ตอนนี้) ฟรีไม่จำกัดจำนวน ไม่นับรวมโควตารายเดือน — ส่วนควบคุมแบบแชทที่มีอยู่แล้วปลอดภัยเรื่องโควตา 100%
มี limitLINE Messaging API — Push/Broadcastข้อความที่บอทส่งเองโดยไม่มีคนทักมาก่อน (เช่น แจ้งเตือนน้ำหมด, ส่งรูปกล้องอัตโนมัติ) นับรวมโควตาฟรีแผน Communication ~500 ข้อความ/เดือน (ประเทศไทย) — ถ้าส่งรูปกล้องอัตโนมัติทุกชั่วโมงจะเกินโควตา (720/เดือน) ต้องคุมความถี่
สรุปสำหรับคำถามเรื่องโควตา: Apps Script ไม่ใช่ปัญหาจริงในสเกลของโปรเจ็คนี้ (ฟาร์มเดียว บอร์ดเดียว) ตัวที่ต้องระวังโควตาจริง ๆ คือ LINE Push API ถ้าจะใช้แจ้งเตือนถี่ ๆ — เหตุผลหลักที่ควรพิจารณาย้าย backend คือเรื่อง ความปลอดภัยและการตอบสนองแบบ real-time ไม่ใช่เพราะโควตาฟรีหมด
03

§เลือกสถาปัตยกรรม Backend

3 ทางเลือก เรียงจากเปลี่ยนน้อยสุดไปเปลี่ยนเยอะสุด — เลือกได้เลยว่าอยากไปทางไหน แต่ละทางมี Roadmap ในข้อ 06 รองรับ

แนะนำ — เริ่มจากตรงนี้

A. Apps Script (เดิม) + ปะรู

เปลี่ยนน้อยสุด · ใช้ของเดิมต่อ
  • คงสถาปัตยกรรม ESP32 poll + Google Sheet ไว้ทั้งหมด
  • ปิดช่องโหว่: ย้าย token ไป Script Properties, เช็ค LINE signature
  • เพิ่ม pushMessage() reuse token เดิมแทน LINE Notify
  • เหมาะกับงานส่งอาจารย์ที่มีเวลาจำกัด ไม่ต้องเรียนเทคโนโลยีใหม่
ใช้ได้ฟรีต่อไป — โควตาปัจจุบันเหลือเฟือ (ดูข้อ 02)

B. Firebase (Realtime DB + Functions)

เปลี่ยนปานกลาง · ได้ real-time จริง
  • ESP32 subscribe การเปลี่ยนแปลงค่าแบบ real-time แทนการ poll ทุก 60 วิ (สั่งงานหน่วงน้อยลงมาก)
  • Cloud Functions รับ Webhook จาก LINE แทน Apps Script
  • มี Firebase Hosting ทำเว็บแดชบอร์ดได้ในระบบเดียวกัน
  • ต้องเรียนรู้ Firebase SDK เพิ่ม — ใช้เวลามากกว่าทาง A
Spark Plan ฟรี: Firestore 50k reads/20k writes ต่อวัน, Realtime DB 1GB เก็บ+10GB โอนย้าย/เดือน, เชื่อมต่อพร้อมกันได้ 100

C. Node.js + MQTT Broker

เปลี่ยนมากสุด · ควบคุมได้เต็มที่
  • ESP32 เชื่อม MQTT broker (HiveMQ Cloud ฟรี) รับคำสั่งทันทีแบบ push จริง ไม่ต้อง poll เลย
  • เขียน backend เอง (Node.js/Express) host ฟรีบน Railway/Render — ควบคุม logic ได้ทุกจุด
  • เหมาะถ้าตั้งใจต่อยอดเป็นพอร์ตโฟลิโอ/โปรเจ็คจริงจังหลังเรียนจบ
  • ใช้เวลาพัฒนามากที่สุด ต้องดูแล backend เองทั้งหมด (ไม่มี Google ช่วยดูแล)
HiveMQ Cloud ฟรี: เชื่อมต่อ 100 อุปกรณ์, โอนข้อมูล 10GB/เดือน, เก็บข้อมูลย้อนหลัง 3 วัน — Node.js hosting ฟรีมักจำกัดชั่วโมงรันต่อเดือน
คำแนะนำ: ถ้าเวลาเหลือน้อยและงานหลักคือส่งวิชานี้ให้เสร็จ ไปทาง A ก่อน เพราะของเดิมทำงานได้ 80% อยู่แล้ว แค่ปะรู ถ้าอยากได้ประสบการณ์ทำระบบ real-time จริงจังและมีเวลาเพิ่ม ไปทาง B เพราะ Firebase เรียนง่ายกว่า MQTT และให้ dashboard มาในตัว ทาง C เหมาะเป็นโปรเจ็คแยกต่างหากหลังจบวิชานี้มากกว่า
04

§เลือกช่องทางแจ้งเตือน/ส่งรูปกล้อง

ส่วนนี้แยกจาก backend เพราะเลือกผสมกันได้ — คำถามหลักคือจะแทน LINE Notify เดิมด้วยอะไร

ทางเลือกข้อดีข้อจำกัด
LINE Push API
(ใช้ token เดิมที่มีอยู่)		ผู้ใช้เห็นแจ้งเตือนทันทีในแชทเดิม ไม่ต้องเปิดแอปอื่น ทำได้เร็วเพราะ setup ไว้แล้วฟรี ~500 ครั้ง/เดือน — ต้องส่งเฉพาะ event สำคัญ (น้ำหมด, ค่าผิดปกติ) ไม่ใช่ทุกรอบ poll
เว็บแดชบอร์ดดูรูปกล้อง/กราฟย้อนหลังได้ไม่จำกัดจำนวนครั้ง ไม่กินโควตา LINE เลยต้องเปิดเบราว์เซอร์เข้าดูเอง ไม่มีการแจ้งเตือนเชิงรุก
ผสมทั้งคู่ (แนะนำ)LINE Push แจ้งเฉพาะ alert วิกฤต + แดชบอร์ดไว้ดูภาพรวม/กราฟ/รูปกล้องแบบละเอียดต้องทำ 2 อย่าง ใช้เวลาพัฒนาเพิ่มขึ้นเล็กน้อย
05

§สภาพแวดล้อมจำลอง (ไม่ใช้ฮาร์ดแวร์จริง)

ใช้ได้กับทุกทางเลือกใน backend เพราะจำลองแค่ฝั่งเฟิร์มแวร์ ไม่เกี่ยวกับว่าปลายทางเป็น Apps Script, Firebase หรือ MQTT

เครื่องมือใช้ทำอะไร
Wokwi (wokwi.com)จำลอง ESP32 เต็มรูปแบบ — DHT22 จริง, ตัวต้านทานปรับค่าแทนเซนเซอร์ดิน, LED แทนรีเลย์ เชื่อม WiFi ออกอินเทอร์เน็ตจริงได้ ยิง HTTP/MQTT ไปปลายทางจริงได้เลย
VS Code + PlatformIO + Wokwi pluginย้ายจาก Arduino IDE มาเขียนใน VS Code พร้อมรันจำลองในตัวผ่านไฟล์ wokwi.toml — ใช้ AI agent ช่วยเขียน/รีแฟกเตอร์โค้ดได้สะดวกกว่า Arduino IDE มาก
Postman / curlยิงทดสอบ endpoint ของ Apps Script หรือ Firebase Functions แยกจากเฟิร์มแวร์ เพื่อดีบัก backend ได้เร็วโดยไม่ต้องรอจำลองบอร์ด
06

§Roadmap เต็ม

Phase 0 ทำเหมือนกันทุกทางเลือก จากนั้น Phase 1-2 แยกตามว่าเลือกทาง A หรือ B — ถ้าเลือกทาง C (MQTT) ใช้โครงเดียวกับ B แต่สลับ Firebase เป็น Node.js+MQTT ในขั้นเชื่อมต่ออุปกรณ์

00สัปดาห์ 1

Refactor + Security (ทำก่อนเสมอ ไม่ว่าจะเลือกทางไหน)

  • แก้บั๊ก 3 จุดในเฟิร์มแวร์: pin สลับกัน, sum_soil_all ถูกเขียนทับ, now_day นับผิดหน่วย
  • ย้าย WiFi password / LINE token / รหัสกล้อง ออกจากโค้ด ไปเก็บใน secrets.h (เฟิร์มแวร์) และ Script Properties (Apps Script)
  • ย้ายพินรีเลย์ออกจาก GPIO 0 และ 12 (strapping pin)
  • เพิ่มการเช็ค x-line-signature ใน webhook ก่อนประมวลผลคำสั่ง
01สัปดาห์ 2

ตั้งสภาพแวดล้อมจำลอง A/B/C

  • ตั้งโปรเจ็ค Wokwi + PlatformIO ใน VS Code รันเฟิร์มแวร์ที่แก้แล้วแบบจำลอง
  • ทดสอบ logic 3 โหมดปลูกด้วยค่าจำลอง ยืนยันว่ารอบน้ำ/ปุ๋ยถูกต้องหลังแก้บั๊ก
02aสัปดาห์ 3

ทาง A: ต่อยอด Apps Script A

  • เพิ่มฟังก์ชัน pushMessage() ใน code.gs ใช้ token เดิม ส่งเฉพาะ alert สำคัญ (น้ำหมด/ค่าผิดปกติ) เพื่อไม่ให้เกินโควตา 500/เดือน
  • เก็บ userId ของผู้ทักบอทครั้งแรกไว้ใน Script Properties สำหรับใช้ push
  • ตรวจสอบว่ามี/เพิ่ม doGet(e) ให้ตรงกับที่เฟิร์มแวร์ยิง GET เข้ามา
02bสัปดาห์ 3–4

ทาง B/C: ย้ายไป Firebase หรือ MQTT B/C

  • สร้างโปรเจ็ค Firebase (Spark plan ฟรี) หรือ HiveMQ Cloud cluster (ฟรี)
  • ปรับเฟิร์มแวร์ให้ subscribe ค่าจาก Realtime DB / MQTT topic แทนการ poll HTTP GET
  • เขียน Cloud Function หรือ Node.js server รับ LINE Webhook แทน Apps Script
  • ย้ายข้อมูล log เซนเซอร์จาก Google Sheet ไป Firestore/ฐานข้อมูลใหม่ (หรือคงคู่ขนานไว้ก่อนก็ได้)
03สัปดาห์ 4–5

เว็บแดชบอร์ด A/B/C

  • หน้าเว็บอ่านค่าจากปลายทางที่เลือก (Sheet/Firestore) แสดงกราฟความชื้นดิน/อุณหภูมิย้อนหลังด้วย Chart.js
  • ปุ่มควบคุม manual + ปุ่มดูรูปกล้องล่าสุด ลดจำนวนครั้งที่ต้องพึ่ง LINE Push
04สัปดาห์ 5–6

เตรียมขึ้นฮาร์ดแวร์จริง A/B/C

  • สลับจากค่าจำลอง Wokwi ไปใช้เซนเซอร์/รีเลย์จริงทีละตัว ทดสอบแยกก่อนประกอบรวม
  • ตรวจ pin-map กับ PCB จริงอีกครั้งตามที่แก้ไว้ในเฟิร์มแวร์
  • รวบรวม README, diagram, วิดีโอสาธิตจากผลจำลองไว้ประกอบการนำเสนอ
07

§เช็คลิสต์ตัดสินใจ

ตอบคำถามพวกนี้แล้วจะรู้ว่าควรเลือกทางไหนในข้อ 03

  • มีเวลาถึงกำหนดส่งเหลือน้อยกว่า 3 สัปดาห์? → ไปทาง A
  • อยากได้ประสบการณ์ทำระบบ real-time / อยากใส่ในพอร์ตโฟลิโอ? → ไปทาง B หรือ C
  • ยังไม่เคยใช้ Firebase/MQTT มาก่อนและไม่มีใครในกลุ่มถนัด? → เริ่มทาง A ก่อน แล้วค่อยลองทาง B เป็นโปรเจ็คเสริมถ้ามีเวลา
  • ต้องการส่งรูปกล้อง/แจ้งเตือนถี่กว่าทุกชั่วโมง? → อย่าพึ่ง LINE Push อย่างเดียว ต้องมีเว็บแดชบอร์ดร่วมด้วย (ข้อ 04)
