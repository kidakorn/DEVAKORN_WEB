5. ตอน Setup / รันครั้งแรก
  • 'dotnet' is not recognized as a command / command not found
  • Address already in use / port ถูกใช้งานอยู่แล้ว
  • เปิด URL แล้วเจอ "Your connection is not private"
5. Error ตอนเขียน C# พื้นฐาน
  • error CS1002: ; expected
  • error CS0103: The name 'x' does not exist in the current context
  • Unhandled exception: System.FormatException ตอนใช้ int.Parse
5. Error ในหน้า Razor Pages
  • 404 Not Found ทั้งที่สร้างไฟล์ .cshtml แล้ว
  • The model item passed into the dictionary is null / ไม่พบ property ของ Model
  • กด submit ฟอร์มแล้วค่าที่กรอกไม่เข้ามาที่ [BindProperty]
5. Error เกี่ยวกับฐานข้อมูล (EF Core)
  • No database provider has been configured / Unable to resolve DbContext
  • ดึงข้อมูลที่เชื่อมกัน (เช่น order.Customer) ได้ null ตลอด ทั้งที่มีข้อมูลจริง
  • Pending model changes / No migrations found ตอนรันโปรเจกต์
5. Error ใน Blazor
  • แก้ค่าตัวแปรแล้วหน้าจอไม่อัพเดทให้
  • Object reference not set to an instance of an object ใน component
5. Error ตอน Runtime ทั่วไป
  • Object reference not set to an instance of an object (NullReferenceException)
  • โปรแกรมค้าง (deadlock) ตอนเรียก method แบบ async
  • CORS policy ไม่อนุญาต (ตอนมี frontend แยก เช่น React)

01โปรแกรมคืออะไร

โปรแกรม คือ ชุดคำสั่งที่บอกให้คอมพิวเตอร์ทำอะไรบางอย่าง ทีละขั้น ทีละขั้น เหมือนสูตรอาหารที่บอกว่า "ทำขั้นที่ 1 ก่อน แล้วค่อยทำขั้นที่ 2" คอมพิวเตอร์เองไม่ได้ฉลาดหรือคิดเองได้ มันแค่ทำตามคำสั่งที่เราเขียนไว้ ทีละบรรทัดอย่างเคร่งครัด

เปรียบเทียบ: ถ้าเราสั่งให้เพื่อนชงกาแฟโดยบอกแค่ "ชงกาแฟให้หน่อย" เพื่อนอาจจะเข้าใจเองว่าต้องทำอะไรบ้าง แต่คอมพิวเตอร์ทำแบบนั้นไม่ได้ เราต้องบอกละเอียดทุกขั้น เช่น "ต้มน้ำ" → "ใส่กาแฟ 2 ช้อน" → "เทน้ำร้อนลงไป" → "คนให้เข้ากัน" การเขียนโปรแกรม คือการเขียนคำสั่งละเอียดขนาดนั้นให้คอมพิวเตอร์ทำตาม

ภาษาโปรแกรม (เช่น C# ที่เรากำลังจะเรียน) คือภาษาที่มนุษย์ใช้เขียนคำสั่งเหล่านั้น ให้คอมพิวเตอร์เข้าใจได้

02Source Code กับการรันโค้ด ต่างกันยังไง

Source code คือ ตัวหนังสือที่เราพิมพ์เขียนคำสั่งไว้ในไฟล์ (ยังไม่ได้ทำงานอะไร แค่เป็นตัวอักษรอยู่ในไฟล์)

การรันโค้ด (run) คือ การสั่งให้คอมพิวเตอร์อ่าน source code นั้น แล้วทำตามคำสั่งจริงๆ ทีละบรรทัด

เปรียบเทียบ: source code เหมือนสูตรอาหารที่เขียนไว้ในกระดาษ ส่วนการรันโค้ด คือตอนที่เรา "ลงมือทำตามสูตรนั้นจริงๆ" ในครัว สูตรอาหารเฉยๆ ไม่ทำให้เกิดอาหารขึ้นมา ต้องมีคนลงมือทำตามถึงจะได้อาหารจริง

สำหรับภาษา C# ตัวที่ทำหน้าที่ "อ่านแล้วรันตามคำสั่ง" เรียกว่า .NET (อ่านว่า ดอท-เน็ต) เราจะติดตั้งมันในหัวข้อถัดไป

สิ่งที่มักเกิดขึ้นตอนรัน — Error: ถ้าเราเขียนคำสั่งผิด (เช่น สะกดผิด ลืมใส่เครื่องหมาย) ตอนรันโค้ด .NET จะไม่ทำงานให้แล้วแจ้ง error (ข้อผิดพลาด) กลับมาบอกว่าพังตรงไหน error ไม่ใช่เรื่องน่ากลัว มันคือข้อความช่วยบอกว่าต้องแก้ตรงไหน โปรแกรมเมอร์ทุกคนเจอ error ทุกวันแม้จะเขียนมานานแล้วก็ตาม ส่วนการหาสาเหตุที่โค้ดพังแล้วแก้ไข เรียกว่า debug
Compile กับ Run ต่างกันยังไง: ก่อนที่ .NET จะรันโค้ด C# ได้จริง มันต้อง "แปล" source code (ที่มนุษย์อ่านเข้าใจ) ให้กลายเป็นภาษาที่คอมพิวเตอร์เข้าใจก่อน ขั้นตอนแปลนี้เรียกว่า compile ถ้า source code เขียนผิดหลักไวยากรณ์ (เช่น ลืมใส่ ;) จะ compile ไม่ผ่านและไม่ได้รันเลย ต่างจาก error บางแบบที่ compile ผ่านแต่พังตอนรันจริง (เช่น เอา 10 หารด้วย 0)
ทำไมบางทีรันไม่ได้: ก่อนรันจริง .NET จะ "ตรวจสอบ" source code ก่อนว่าเขียนถูกไวยากรณ์ไหม ขั้นตอนนี้เรียกว่า compile ถ้าเขียนผิด (เช่น ลืมใส่เครื่องหมาย ; ท้ายบรรทัด หรือสะกดคำสั่งผิด) จะเจอ "compile error" และโปรแกรมจะไม่รันเลยแม้แต่บรรทัดเดียว ต่างจากตอนรันแล้วเกิดปัญหาระหว่างทาง (เรียกว่า "runtime error") ที่อย่างน้อยโปรแกรมได้เริ่มทำงานไปบ้างแล้วก่อนจะพัง จุดนี้สำคัญเวลา debug เพราะบอกได้ทันทีว่าปัญหาอยู่ที่ "เขียนผิดไวยากรณ์" หรือ "ตรรกะผิดตอนรัน"
ลองนึกภาพ: เทียบกับสูตรอาหารที่เขียนขั้นตอนไม่ครบ (เช่น "ผัดจนสุก" แต่ไม่บอกว่าผัดอะไร) คนทำอาหารอาจงงตั้งแต่ยังไม่เริ่มทำ นั่นคล้ายกับ compile error ส่วนถ้าสูตรเขียนครบแต่ทำไปแล้วไฟไหม้กลางทาง (เช่น ลืมปิดเตา) นั่นคล้ายกับ runtime error — ยังไม่ต้องเขียนโค้ดในหัวข้อนี้ แค่จำภาพนี้ไว้ก่อน

03เขียนบรรทัดแรก (Hello World)

ก่อนเขียนโค้ด ต้องติดตั้งเครื่องมือ 2 อย่างก่อน:

อย่างแรก — ติดตั้ง .NET SDK จาก dotnet.microsoft.com/download เลือกเวอร์ชัน LTS (เวอร์ชันที่แนะนำ) แล้วติดตั้งตามขั้นตอนของโปรแกรมติดตั้งปกติ

อย่างที่สอง — เปิด VS Code แล้วติดตั้ง extension ชื่อ "C# Dev Kit" (กดที่ไอคอน Extensions ด้านซ้าย พิมพ์ค้นหา แล้วกด Install)

ตรวจสอบว่าติดตั้งสำเร็จ เปิด terminal ใน VS Code (กด Ctrl+`) แล้วพิมพ์:

dotnet --version

ถ้าเห็นตัวเลขเวอร์ชัน (เช่น 8.0.100) แปลว่าเรียบร้อย ถ้าขึ้น error ว่าไม่รู้จักคำสั่งนี้ แปลว่ายังติดตั้งไม่สำเร็จ ต้องกลับไปข้อแรกก่อน

ตอนนี้ลองสร้างโปรแกรมแรกในชีวิต ที่แค่ print ข้อความออกมา:

mkdir hello-world
cd hello-world
dotnet new console
dotnet run

คำสั่ง dotnet new console คือการสร้างโปรแกรมเปล่าๆ แบบง่ายที่สุดให้ ส่วน dotnet run คือการสั่งรันโปรแกรมนั้น ถ้าทำถูกต้อง จะเห็นคำว่า Hello, World! ปรากฏขึ้นมาในหน้าจอ terminal

ตอนพิมพ์ dotnet run เกิดอะไรขึ้นบ้าง: เบื้องหลังมี 2 ขั้นตอนซ้อนกันอยู่ ต่อเนื่องจากหัวข้อ 2 ขั้นแรก .NET จะ compile source code ในไฟล์ Program.cs ก่อน (ตรวจไวยากรณ์ให้) ถ้าผ่านแล้วถึงจะเข้าขั้นที่สอง คือรันจริง ถ้าเจอ compile error จะเห็นข้อความ error สีแดงแทนคำว่า Hello, World! และโปรแกรมจะไม่เริ่มทำงานเลย
ลองทำ: เปิดไฟล์ Program.cs ที่ถูกสร้างขึ้นมา (อยู่ในโฟลเดอร์ hello-world) จะเห็นบรรทัดเดียวที่เขียนว่า Console.WriteLine("Hello, World!"); ลองแก้ข้อความในเครื่องหมายคำพูด เป็นชื่อตัวเองแล้วรัน dotnet run ใหม่ ดูว่าข้อความเปลี่ยนไหม
ดูเฉลย
Console.WriteLine("Somchai");
เปลี่ยนแค่ข้อความในเครื่องหมายคำพูด ผลลัพธ์ตอนรัน dotnet run จะแสดงชื่อแทนคำว่า Hello, World!
Comment คืออะไร: บางครั้งอยากเขียนโน้ตไว้ในโค้ดเพื่อเตือนความจำตัวเองหรืออธิบายให้คนอื่นเข้าใจ โดยไม่ให้คอมพิวเตอร์เอาไปรันด้วย ใช้เครื่องหมาย // นำหน้าบรรทัดนั้น 
// บรรทัดนี้คือ comment คอมพิวเตอร์จะข้ามไปเลย ไม่รันอะไร
Console.WriteLine("Hello, World!");   // เขียนโน้ตต่อท้ายบรรทัดโค้ดก็ได้
comment มีประโยชน์มากตอนกลับมาอ่านโค้ดตัวเองหลังผ่านไปนานๆ หรือมีคนอื่นมาอ่านโค้ดของเรา
Console.WriteLine ทำอะไรกันแน่: Console คือชื่อของหน้าจอ terminal ที่กำลังใช้อยู่ WriteLine คือคำสั่ง "เขียนข้อความแล้วขึ้นบรรทัดใหม่" ส่วนข้อความในวงเล็บคือสิ่งที่จะให้แสดง ถ้าอยากเขียนโดยไม่ขึ้นบรรทัดใหม่ ใช้ Console.Write แทน (ไม่มี Line ต่อท้าย)
ลองทำอีกอย่าง: ลองลบเครื่องหมาย ; ท้ายบรรทัดออกไปก่อน 1 ตัว แล้วรัน dotnet run ดูว่าเจอ compile error แบบไหน (นี่คือตัวอย่าง compile error จริงที่เพิ่งพูดถึง) แก้กลับคืนเป็นเดิมก่อนไปหัวข้อถัดไป

นี่คือตัวอย่าง error ที่เกิดตอน compile (ก่อนรันจริง) เพราะ C# บังคับให้ทุกคำสั่งจบด้วย ; เสมอ อย่าลืมใส่ ; กลับคืนก่อนไปหัวข้อถัดไป

04ตัวแปรคืออะไร

ตัวแปร คือ ที่สำหรับเก็บค่าไว้ใช้ในภายหลัง เหมือนกล่องที่มีชื่อติดไว้ ใส่ของลงไปแล้วเรียกของนั้นออกมาใช้ทีหลังได้ โดยเรียกผ่านชื่อกล่อง

เปรียบเทียบ: เหมือนเขียนชื่อกำกับบนกล่องเก็บของ เช่น กล่องชื่อ "อายุ" ใส่เลข 25 ไว้ข้างใน ทีหลังพอเราพูดถึง "อายุ" คอมพิวเตอร์ก็รู้ว่าหมายถึง 25

ในภาษา C# การสร้างตัวแปรเขียนแบบนี้:

int age = 25;
string name = "Somchai";

อ่านว่า "สร้างตัวแปรชื่อ age เก็บค่าเป็นตัวเลข 25" และ "สร้างตัวแปรชื่อ name เก็บค่าเป็นข้อความ Somchai" คำว่า int และ string ด้านหน้า คือการบอกว่าของในกล่องนี้เป็น "ชนิด" ไหน ซึ่งจะอธิบายละเอียดในหัวข้อถัดไป

เปลี่ยนค่าในตัวแปรได้ตลอด: ตัวแปรเรียกว่า "แปร" เพราะเปลี่ยนค่าได้ ไม่ใช่กำหนดครั้งเดียวแล้วตายตัว 
int age = 25;
Console.WriteLine(age);   // แสดง 25

age = 26;                 // เปลี่ยนค่าในกล่องเดิม ไม่ต้องเขียน int ซ้ำ
Console.WriteLine(age);   // แสดง 26
สังเกตว่าบรรทัดที่สองไม่มีคำว่า int นำหน้าอีก เพราะกล่องชื่อ age ถูกสร้างไปแล้วตั้งแต่บรรทัดแรก บรรทัดนี้แค่ "เปลี่ยนของข้างใน" เท่านั้น
กฎการตั้งชื่อตัวแปร: ต้องขึ้นต้นด้วยตัวอักษรหรือ underscore (ห้ามขึ้นต้นด้วยตัวเลข) ห้ามมีช่องว่าง และห้ามซ้ำกับคำสั่งที่ภาษา C# ใช้เอง (เช่นห้ามตั้งชื่อตัวแปรว่า int) ธรรมเนียมที่นิยมใช้กันคือ ตั้งชื่อแบบ camelCase (ตัวแรกเล็ก คำถัดไปขึ้นต้นด้วยตัวใหญ่) เช่น customerName, totalAmount เพื่อให้อ่านง่ายเมื่อชื่อมีหลายคำ
ลองทำ: ในไฟล์ Program.cs เดิม เพิ่มบรรทัด int age = 25; ไว้ก่อนบรรทัด Console.WriteLine แล้วเปลี่ยนบรรทัดนั้นเป็น Console.WriteLine(age); รันดูว่าเห็นเลข 25 ปรากฏขึ้นมาไหม
ดูเฉลย
int age = 25;
Console.WriteLine(age);
รันแล้วจะเห็นเลข 25 ปรากฏในหน้าจอ terminal
เปลี่ยนค่าในตัวแปรได้ทีหลัง: ตัวแปรเรียกว่า "ตัวแปร" เพราะค่าข้างในเปลี่ยนได้ตลอดเวลา 
int age = 25;
Console.WriteLine(age);   // แสดง 25

age = 26;                 // เปลี่ยนค่าใหม่ (ไม่ต้องเขียน int ซ้ำ)
Console.WriteLine(age);   // แสดง 26
สังเกตว่าตอนเปลี่ยนค่าครั้งที่สอง ไม่ต้องเขียน int นำหน้าอีก เพราะกล่องชื่อ age ถูกสร้างไปแล้วตั้งแต่บรรทัดแรก แค่ใส่ของใหม่ลงไปแทนของเดิม
ค่าคงที่ (const): ถ้ามีค่าที่ไม่อยากให้ใครเผลอไปเปลี่ยนทีหลัง ใช้ const แทน int/string ปกติ 
const double TaxRate = 0.07;
// TaxRate = 0.08;   ถ้าเขียนบรรทัดนี้จะ error ทันที เพราะ const ห้ามเปลี่ยนค่า
วิธีตั้งชื่อตัวแปรที่นิยมใน C#: ตัวแปรทั่วไปมักตั้งชื่อแบบ camelCase (ขึ้นต้นตัวเล็ก คำถัดไปขึ้นตัวใหญ่) เช่น customerName, totalAmount ชื่อควรสื่อความหมายชัดเจน หลีกเลี่ยงชื่อสั้นๆ กำกวมอย่าง x, data1 เพราะทำให้กลับมาอ่านโค้ดทีหลังยากขึ้นมาก
ลองทำอีกอย่าง: เพิ่มบรรทัด age = 30; ต่อจากบรรทัดเดิม แล้ว Console.WriteLine(age) อีกครั้ง สังเกตว่าครั้งที่สองแสดงผลเป็น 30 ไม่ใช่ 25 แล้ว เพราะค่าถูกเปลี่ยนไปแล้ว

int age = 25;

age = 30;
Console.WriteLine(age);   // แสดง 30

07การทำซ้ำ (Loop)

ถ้าต้องการให้คอมพิวเตอร์ทำอะไรซ้ำๆ กันหลายรอบ เช่น print ข้อความ 5 ครั้ง แทนที่จะเขียน Console.WriteLine ซ้ำ 5 บรรทัด เราใช้ loop (การวนซ้ำ) แทน

for (int i = 1; i <= 5; i++)
{
    Console.WriteLine("รอบที่ " + i);
}

อ่านว่า "เริ่มจาก i เท่ากับ 1 ทำซ้ำไปเรื่อยๆ ตราบใดที่ i ยังน้อยกว่าหรือเท่ากับ 5 แล้วเพิ่มค่า i ทีละ 1 ในแต่ละรอบ" ผลลัพธ์คือจะ print คำว่า "รอบที่ 1" ถึง "รอบที่ 5" ออกมาทั้งหมด 5 บรรทัด

เปรียบเทียบ: เหมือนบอกให้ใครทำ squat 5 ครั้ง แทนที่จะบอกทีละครั้งว่า "squat 1 ครั้ง" ซ้ำ 5 รอบ เราแค่บอกครั้งเดียวว่า "ทำ squat 5 ครั้ง" loop ก็ทำหน้าที่แบบนั้น

int total = 0;
int i = 1;

{

    i++;
}

Console.WriteLine(total);

    }

// ผลลัพธ์: print 1, 2, 3, 4 แล้วหยุด (ไม่ถึง 5)
break คือ "หยุด loop ทั้งหมดทันที" ส่วน continue คือ "ข้ามรอบนี้ไปทำรอบถัดไปเลย" โดยไม่หยุดทั้ง loop
ลองทำ: เขียน loop ที่ print ตัวเลข 1 ถึง 10 แต่ให้ print เฉพาะเลขคู่เท่านั้น (รวมความรู้จากหัวข้อ 6 กับ 7 เข้าด้วยกัน)

public class ProductsModel : PageModel
{
    private readonly AppDbContext _db;
    public ProductsModel(AppDbContext db) { _db = db; }

    public List<Product> Products { get; set; } = new();

    public async Task OnGetAsync()
    {
        Products = await _db.Products.ToListAsync();
    }

    public async Task OnPostDeleteAsync(int id)
    {
        var product = await _db.Products.FindAsync(id);
        if (product is not null)
        {
            _db.Products.Remove(product);
            await _db.SaveChangesAsync();
        }
    }
}

    public int Id { get; set; }
    public string Name { get; set; } = string.Empty;

    // 1 ลูกค้า มีได้หลายออเดอร์
    public List<Order> Orders { get; set; } = new();
}

public class Order
{
    public int Id { get; set; }
    public decimal TotalAmount { get; set; }

    // Foreign Key — บอกว่าออเดอร์นี้เป็นของลูกค้าคนไหน
    public int CustomerId { get; set; }
    public Customer? Customer { get; set; }
}

CustomerId คือ Foreign Key เก็บ id ของลูกค้าเจ้าของออเดอร์นี้ ส่วน Customer? Customer คือ "navigation property" ที่ทำให้เขียนโค้ดเข้าถึงข้อมูลลูกค้าจากออเดอร์ได้โดยตรง (เช่น order.Customer.Name) โดย EF Core จัดการ join table ให้เองเบื้องหลัง

ดึงข้อมูลที่เชื่อมกันมาแสดงพร้อมกัน
// ถ้าไม่ใช้ Include, order.Customer จะเป็น null เสมอ
var orders = await _db.Orders
    .Include(o => o.Customer)
    .ToListAsync();

foreach (var order in orders)
{
    Console.WriteLine(order.Customer.Name + " — " + order.TotalAmount);
}

.Include(o => o.Customer) คือการบอก EF Core ว่า "ตอน query Order ให้ดึงข้อมูล Customer ที่เกี่ยวข้องมาด้วยเลย" ถ้าลืมเขียนบรรทัดนี้ order.Customer จะเป็น null เสมอ แม้ในฐานข้อมูลจะมีข้อมูลลูกค้าจริงก็ตาม เพราะ EF Core ไม่ดึงข้อมูลที่เชื่อมกันมาให้อัตโนมัติ ต้องสั่งชัดเจนทุกครั้ง

แสดงข้อมูลที่เชื่อมกันบนหน้าเว็บ (ฝั่งหน้าตา)

แก้ไขไฟล์ที่: Pages/Orders/Index.cshtml (หน้า list ออเดอร์ที่เคยทำไว้ เพิ่มคอลัมน์แสดงชื่อลูกค้า)

        <tr>
            <td>@order.Customer?.Name</td>
            <td>@order.TotalAmount บาท</td>

ฝั่งหน้าตาไม่ต้องรู้เลยว่าเบื้องหลังมีการ Include ยังไง แค่เรียก @order.Customer?.Name เหมือน property ธรรมดาของ order ปกติ — เครื่องหมาย ? สำคัญตรงนี้เพราะถ้า PageModel ลืม Include (จาก pitfall ด้านบน) หน้าเว็บจะไม่ error แต่แสดงช่องว่างแทนชื่อลูกค้าแทน

ข้อผิดพลาดที่เจอบ่อยที่สุดในหัวข้อนี้: ลืม Include แล้วงงว่าทำไมข้อมูลที่เชื่อมกัน เป็น null ตลอด ทั้งที่ query สำเร็จไม่มี error ใดๆ เป็นปัญหาที่ทำให้เสียเวลา debug บ่อยที่สุดในหัวข้อนี้

MODULE 5ระบบ Login (Authentication / Authorization)
5-6 วัน
  • ความต่างระหว่าง Authentication (ยืนยันตัวตน) กับ Authorization (สิทธิ์การเข้าถึง)
  • ASP.NET Core Identity — ระบบ login สำเร็จรูปที่มากับ framework
  • จำกัดการเข้าถึงหน้าด้วย [Authorize]
Authentication vs Authorization: Authentication คือ "คุณเป็นใคร" (ล็อกอินสำเร็จหรือยัง) Authorization คือ "คุณทำอะไรได้บ้าง" (มีสิทธิ์เข้าหน้านี้ไหม) สองอย่างนี้แยกกันชัดเจน ล็อกอินสำเร็จ (authenticated) ไม่ได้แปลว่าเข้าได้ทุกหน้าเสมอไป
เพิ่ม ASP.NET Core Identity เข้าโปรเจกต์
dotnet add package Microsoft.AspNetCore.Identity.EntityFrameworkCore
// Program.cs
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlite("Data Source=app.db"));

builder.Services.AddDefaultIdentity<IdentityUser>(options =>
    options.SignIn.RequireConfirmedAccount = false)
    .AddEntityFrameworkStores<AppDbContext>();

// ...

app.UseAuthentication();   // ต้องมาก่อน UseAuthorization เสมอ
app.UseAuthorization();

AddDefaultIdentity<IdentityUser> — เปิดใช้ระบบ login สำเร็จรูปที่มีหน้า register/login/logout ให้พร้อมใช้ทันที ไม่ต้องเขียนเองตั้งแต่ศูนย์

app.UseAuthentication() ต้องอยู่ ก่อน app.UseAuthorization() เสมอใน middleware pipeline เพราะต้องรู้ก่อนว่า "ใครเข้ามา" ถึงจะเช็คต่อได้ว่า "เข้าได้ไหม" สลับลำดับผิดจะทำให้ authorization ทำงานไม่ถูกต้อง

จำกัดการเข้าถึงหน้า
[Authorize]
public class AdminModel : PageModel
{
    // เฉพาะคนที่ login แล้วเท่านั้นที่เข้าหน้านี้ได้
    // ถ้ายังไม่ login จะถูก redirect ไปหน้า login อัตโนมัติ
}
[Authorize(Roles = "Manager")]
public class ReportsModel : PageModel
{
    // เฉพาะคนที่มี role "Manager" เท่านั้น
}
แบบฝึกหัด: เพิ่ม Identity เข้าโปรเจกต์ฝึก ทดลอง register ผู้ใช้ใหม่ 1 คน login เข้าใช้งาน แล้วใส่ [Authorize] ที่หน้า Create สินค้า ทดสอบว่าคนที่ยังไม่ login เข้าหน้านั้นไม่ได้จริง
ดูเฉลย
ติดตั้งและตั้งค่าตามตัวอย่างในเนื้อหา จากนั้นเปิด URL /Identity/Account/Register (หน้านี้มาให้พร้อมกับ AddDefaultIdentity โดยไม่ต้องสร้างเอง) กรอกอีเมลและรหัสผ่านเพื่อสมัคร จากนั้นเพิ่ม attribute บนไฟล์ Create.cshtml.cs: 
[Authorize]
public class CreateModel : PageModel
{
    // ...
}
ทดสอบโดยเปิด browser แบบ Incognito/Private (เพื่อไม่ให้มี session login เดิมค้างอยู่) แล้วพิมพ์ URL ของหน้า Create ตรงๆ ควรถูก redirect ไปหน้า login อัตโนมัติ ถ้ายังเข้าได้ตรงๆ แปลว่าลืมใส่ app.UseAuthentication() ก่อน app.UseAuthorization() ใน Program.cs

public async Task<IActionResult> OnPostAsync()
{
    try
    {
        _db.Products.Add(NewProduct);
        await _db.SaveChangesAsync();
        return RedirectToPage("Index");
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "บันทึกสินค้าไม่สำเร็จ");
        ModelState.AddModelError("", "เกิดข้อผิดพลาด กรุณาลองใหม่อีกครั้ง");
        return Page();
    }
}

XSS (Cross-Site Scripting) — แทรก script ผ่านข้อมูลที่ผู้ใช้กรอก

ถ้าผู้ใช้กรอกชื่อเป็น <script>alert('hacked')</script> แล้วระบบเอาไปแสดงตรงๆ โดยไม่ป้องกัน script นั้นจะรันจริงในเบราว์เซอร์ของคนอื่นที่มาดูหน้านั้น

<!-- ปลอดภัย — Razor encode ให้อัตโนมัติเสมอเมื่อใช้ @ -->
<p>@product.Name</p>

<!-- อันตราย — Html.Raw ข้าม encode ทำให้ script รันได้จริง -->
<p>@Html.Raw(product.Name)</p>

Razor Pages เข้ารหัส (encode) ข้อความที่แสดงด้วย @ ให้อัตโนมัติเสมอ ตัวอักษรอย่าง < จะกลายเป็น &lt; ทำให้ browser แสดงเป็นข้อความธรรมดา ไม่รันเป็นโค้ด ใช้ Html.Raw เฉพาะตอนมั่นใจ 100% ว่าข้อมูลนั้นปลอดภัยจริงเท่านั้น (เช่น เนื้อหาที่แอดมินเขียนเอง ไม่ใช่ input จากผู้ใช้ทั่วไป)

CSRF (Cross-Site Request Forgery) — หลอกให้ browser ส่ง request แทนเรา

ถ้าเรา login เว็บแอปไว้แล้วเผลอเปิดเว็บอันตรายในแท็บอื่น เว็บนั้นอาจแอบสั่ง submit ฟอร์มไปยัง เว็บแอปของเราโดยที่เราไม่รู้ตัว (เพราะ browser แนบ cookie login ไปให้อัตโนมัติ)

<!-- Tag Helper ของ ASP.NET Core แทรก anti-forgery token ให้อัตโนมัติ -->
<form method="post">
    <input asp-for="NewProduct.Name" />
    <button type="submit">บันทึก</button>
</form>
<!-- ไม่ต้องเขียนอะไรเพิ่ม แค่ใช้ <form> ธรรมดา ASP.NET Core แทรก token ที่มองไม่เห็นให้เอง -->

ทุกฟอร์มที่สร้างผ่าน Razor Pages ปกติ (ไม่ใช้ raw HTML form ที่เขียนเองทั้งหมด) จะมี anti-forgery token แทรกมาให้อัตโนมัติอยู่แล้ว server จะเช็ค token นี้ทุกครั้งที่ submit ถ้าไม่ตรงจะปฏิเสธ request ทันที

SQL Injection — แทรกคำสั่ง SQL ผ่านข้อมูลที่กรอก
// ปลอดภัย — EF Core แปลง LINQ เป็น parameterized query ให้อัตโนมัติเสมอ
var product = await db.Products
    .Where(p => p.Name == userInput)
    .FirstOrDefaultAsync();

// อันตรายมาก — เอา userInput มาต่อ string ตรงๆ
var sql = "SELECT * FROM Products WHERE Name = '" + userInput + "'";
// ถ้า userInput คือ  ' OR '1'='1  จะดึงข้อมูลทั้ง table ออกมาหมด

ตราบใดที่ใช้ LINQ ผ่าน EF Core ตามปกติ (ไม่เขียน raw SQL เอง) จะปลอดภัยจาก SQL Injection โดยอัตโนมัติ เพราะ EF Core ไม่เคยเอาค่าจากผู้ใช้มาต่อ string ตรงๆ แต่ส่งเป็น parameter แยกเสมอ ถ้าจำเป็นต้องเขียน raw SQL จริงๆ (เช่น query ซับซ้อนมาก) ต้องใช้ FromSqlInterpolated ไม่ใช่ต่อ string เอง

ข้อผิดพลาดที่เจอบ่อย: ใช้ Html.Raw เพราะอยากให้ HTML ที่ผู้ใช้กรอกแสดงผลสวยงาม (เช่น bold, italic) โดยไม่ผ่านการกรองก่อน วิธีที่ถูกต้องคือใช้ library กรอง HTML ที่อนุญาตเฉพาะ tag ปลอดภัย (เช่น HtmlSanitizer) ไม่ใช่ปล่อยผ่านทั้งหมด
แบบฝึกหัด: ทดลองกรอกชื่อสินค้าเป็น <b>ทดสอบ</b> ในฟอร์มของโปรเจกต์ฝึก แล้วดูว่าหน้า list แสดงเป็นตัวหนาจริงไหม หรือแสดงเป็นข้อความ <b>...</b> ตรงๆ (ควรเป็นแบบหลัง เพราะ Razor encode ให้อัตโนมัติ)

AsNoTracking — เร็วขึ้นสำหรับ query ที่แค่อ่านอย่างเดียว

In-Memory Cache — จำผลลัพธ์ไว้ในหน่วยความจำ
// Program.cs
builder.Services.AddMemoryCache();
public class ProductsModel : PageModel
{
    private readonly IMemoryCache _cache;
    private readonly AppDbContext _db;

    public ProductsModel(IMemoryCache cache, AppDbContext db)
    {
        _cache = cache;
        _db = db;
    }

    public async Task OnGetAsync()
    {
        Products = await _cache.GetOrCreateAsync("all-products", async entry =>
        {
            entry.SlidingExpiration = TimeSpan.FromMinutes(5);
            return await _db.Products.AsNoTracking().ToListAsync();
        });
    }
}

GetOrCreateAsync เช็คก่อนว่ามีค่าชื่อ "all-products" ใน cache อยู่ไหม ถ้ามีแล้วก็คืนค่าจาก cache ทันทีโดยไม่ query ฐานข้อมูลเลย ถ้ายังไม่มีถึงจะรัน query จริงแล้วเก็บผลลัพธ์ไว้ใน cache ต่อ SlidingExpiration คือ "ถ้าไม่มีใครเรียกใช้ cache นี้เกิน 5 นาที ให้ลบทิ้ง"

ข้อควรระวัง: ข้อมูลใน cache อาจ "เก่า" กว่าข้อมูลจริงในฐานข้อมูล ถ้ามีคนแก้ไขข้อมูลแต่ cache ยังไม่หมดอายุ คนอื่นจะยังเห็นข้อมูลเก่าอยู่ ต้องจำไว้ลบ cache (_cache.Remove("all-products")) ทุกครั้งที่มีการ Create/Update/Delete ข้อมูลนั้น ไม่งั้นข้อมูลที่แสดงจะไม่ตรงกับความจริง

var orders = await db.Orders.ToListAsync();
foreach (var order in orders)
{
    var customer = await db.Customers.FindAsync(order.CustomerId);  // ยิง query ทุกรอบ loop
    Console.WriteLine(customer.Name);
}

// ถูก — Include ดึงมาครั้งเดียวพร้อมกันหมด
var orders = await db.Orders.Include(o => o.Customer).ToListAsync();

PageModel แค่ "ส่งต่อ" งานไปให้ Service ทำ ไม่มี logic ธุรกิจอยู่ในนี้เลย (ไม่เช็คสต๊อกเอง ไม่คุย EF Core ตรงๆ) หน้าที่เดียวคือแปลงผลลัพธ์จาก Service ให้เป็นสิ่งที่หน้าเว็บแสดงได้

ชั้นที่ 3 — Service (business logic + คุยกับ external API)
public class OrderApprovalService : IOrderApprovalService
{
    private readonly AppDbContext _db;
    private readonly HttpClient _httpClient;   // ใช้เรียก external API เช่น IWS

    public OrderApprovalService(AppDbContext db, HttpClient httpClient)
    {
        _db = db;
        _httpClient = httpClient;
    }

    public async Task<ApprovalResult> ApproveOrderAsync(int orderId)
    {
        var order = await _db.Orders.FindAsync(orderId);

        // เรียก external API เช็คสต๊อกจริงก่อนอนุมัติ
        var response = await _httpClient.GetAsync($"https://iws.example.com/api/stock/{order.ProductId}");
        var stockInfo = await response.Content.ReadFromJsonAsync<StockInfo>();

        if (stockInfo!.Quantity < order.Quantity)
        {
            return new ApprovalResult { Success = false, ErrorMessage = "สต๊อกไม่พอ" };
        }

        order.Status = "Approved";
        await _db.SaveChangesAsync();
        return new ApprovalResult { Success = true };
    }
}

ชั้นนี้คือที่ที่ "งานจริง" เกิดขึ้น ทั้งคุยกับฐานข้อมูล (EF Core) และคุยกับระบบภายนอก (HttpClient เรียก IWS หรือ API อื่น) PageModel ไม่ต้องรู้เลยว่าข้างในเช็คสต๊อกยังไง รู้แค่ว่าเรียกแล้วได้ผลลัพธ์ success/fail กลับมา

ลงทะเบียนทุกชั้นใน Program.cs
builder.Services.AddHttpClient<IOrderApprovalService, OrderApprovalService>();
builder.Services.AddDbContext<AppDbContext>(o => o.UseSqlite("Data Source=app.db"));

AddHttpClient<TInterface, TImplementation> เป็นวิธีพิเศษที่ลงทะเบียนทั้ง Service และ HttpClient ที่ใช้ข้างในให้พร้อมกันในบรรทัดเดียว ปลอดภัยกว่าสร้าง new HttpClient() เองตรงๆ เพราะ .NET จัดการเรื่อง connection pool ให้อัตโนมัติ

สรุปภาพรวมที่ควรจำ: UI ไม่ควรรู้จัก DbContext หรือ HttpClient เลย, PageModel ไม่ควรมี business logic เอง (แค่ส่งต่อ), Service เท่านั้นที่คุยกับฐานข้อมูลและ external API โดยตรง การแยกแบบนี้ทำให้ ถ้าต้องเปลี่ยนวิธีเช็คสต๊อก (เช่นเปลี่ยนจาก IWS เป็นระบบอื่น) แก้แค่ใน Service จุดเดียว ไม่ต้องแตะ UI หรือ PageModel เลย

Repository — ห่อการคุยกับฐานข้อมูลไว้ในที่เดียว
public interface IProductRepository
{
    Task<List<Product>> GetAllAsync();
    Task<Product?> GetByIdAsync(int id);
    Task AddAsync(Product product);
    Task DeleteAsync(int id);
}

public class ProductRepository : IProductRepository
{
    private readonly AppDbContext _db;
    public ProductRepository(AppDbContext db) => _db = db;

    public async Task<List<Product>> GetAllAsync()
        => await _db.Products.AsNoTracking().ToListAsync();

    public async Task<Product?> GetByIdAsync(int id)
        => await _db.Products.FindAsync(id);

    public async Task AddAsync(Product product)
    {
        _db.Products.Add(product);
        await _db.SaveChangesAsync();
    }

    public async Task DeleteAsync(int id)
    {
        var product = await _db.Products.FindAsync(id);
        if (product is not null)
        {
            _db.Products.Remove(product);
            await _db.SaveChangesAsync();
        }
    }
}

Repository รู้เรื่อง EF Core อย่างเดียว ไม่มี business rule ใดๆ ปนอยู่ (เช่น ไม่เช็คว่าราคาต้อง มากกว่า 0 ตรงนี้ — นั่นเป็นหน้าที่ของ Service) ถ้าวันหนึ่งเปลี่ยนจาก EF Core ไปใช้เทคโนโลยีอื่น แก้แค่ไฟล์นี้ไฟล์เดียว โค้ดส่วนอื่นไม่กระทบเลย

Service — business logic ที่ใช้ Repository เป็นเครื่องมือ
public interface IProductService
{
    Task<List<Product>> GetAllAsync();
    Task<ServiceResult> CreateAsync(Product product);
}

public class ProductService : IProductService
{
    private readonly IProductRepository _repo;
    public ProductService(IProductRepository repo) => _repo = repo;

    public Task<List<Product>> GetAllAsync() => _repo.GetAllAsync();

    public async Task<ServiceResult> CreateAsync(Product product)
    {
        // business rule อยู่ตรงนี้ ไม่ใช่ใน Repository
        if (product.Price <= 0)
        {
            return ServiceResult.Fail("ราคาต้องมากกว่า 0");
        }

        await _repo.AddAsync(product);
        return ServiceResult.Ok();
    }
}

Service คือชั้นที่มี "กฎทางธุรกิจ" (business rule) เช่น เงื่อนไขการอนุมัติ, การคำนวณราคาพิเศษ ส่วน Repository มีหน้าที่แค่ "เก็บ/ดึงข้อมูล" ล้วนๆ การแยกสองอย่างนี้ทำให้ทดสอบ business rule ได้โดยไม่ต้องพึ่งฐานข้อมูลจริง (mock Repository แทนได้ตอนเขียน unit test)

PageModel หลังจัดระเบียบ — สั้นลงมาก
public class CreateModel : PageModel
{
    private readonly IProductService _service;
    public CreateModel(IProductService service) => _service = service;

    [BindProperty]
    public Product NewProduct { get; set; } = new();

    public async Task<IActionResult> OnPostAsync()
    {
        var result = await _service.CreateAsync(NewProduct);
        if (!result.Success)
        {
            ModelState.AddModelError("", result.ErrorMessage!);
            return Page();
        }
        return RedirectToPage("Index");
    }
}

เทียบกับตอนที่เขียนทุกอย่างใน PageModel ตรงๆ (แบบที่ทำมาตลอดในหัวข้อก่อนหน้า) โค้ดตรงนี้สั้นลงมาก และอ่านง่ายขึ้น เพราะ PageModel รู้แค่ "เรียก Service แล้วแปลผลลัพธ์เป็นหน้าจอ" เท่านั้น

ลงทะเบียนทั้งสองชั้นใน Program.cs
builder.Services.AddScoped<IProductRepository, ProductRepository>();
builder.Services.AddScoped<IProductService, ProductService>();
ข้อควรระวัง: ไม่ต้องรีบใช้ pattern นี้ตั้งแต่ต้นถ้าโปรเจกต์เล็กมาก (เช่นโปรเจกต์ฝึกที่ทำมาตลอด) การเพิ่มชั้น Repository/Service ให้กับระบบเล็กๆ อาจทำให้โค้ดซับซ้อนเกินความจำเป็น (over-engineering) pattern นี้คุ้มค่าที่สุดเมื่อโปรเจกต์เริ่มมี business rule เยอะขึ้น หรือมีทีมทำงานพร้อมกันหลายคน
แบบฝึกหัด: เลือกฟีเจอร์หนึ่งในโปรเจกต์ฝึก (เช่น การสร้างสินค้าใหม่) แล้วแยกออกเป็น Repository และ Service ตามตัวอย่าง เทียบดูว่า PageModel สั้นลงแค่ไหนจากก่อนแยก

using Microsoft.AspNetCore.Mvc;
using Microsoft.AspNetCore.Mvc.RazorPages;
using InventoryApp.Data;
using InventoryApp.Models;

namespace InventoryApp.Pages.Products;

public class CreateModel : PageModel
{
    private readonly AppDbContext _db;
    public CreateModel(AppDbContext db) => _db = db;

    [BindProperty]
    public Product NewProduct { get; set; } = new();

    public IActionResult OnGet() => Page();

    public async Task<IActionResult> OnPostAsync()
    {
        if (!ModelState.IsValid) return Page();

        _db.Products.Add(NewProduct);
        await _db.SaveChangesAsync();
        return RedirectToPage("Index");
    }
}
