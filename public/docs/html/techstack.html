TECH-STACK / internal-web-app / rev.1

ทางเลือก Tech Stack สำหรับเว็บแอพภายในบริษัท

เอกสารสรุปสำหรับส่งต่อให้ทีมพัฒนาเว็บ อธิบายว่าแต่ละส่วนของ stack คืออะไร ใช้ทำอะไร และทำไมถึงเหมาะกับ requirement ที่มีอยู่

ประเภทระบบ
Internal tool (ใช้งานภายในบริษัท)
แหล่งข้อมูล 1
IWS บน IBM i — อ่านข้อมูลอย่างเดียว (read-only)
แหล่งข้อมูล 2
Microsoft SQL Server แยกเครื่อง — อ่านและเขียน (ฝั่ง admin)
ทีมพัฒนา
ทีมผสม ถนัดหลายด้าน แยกทีมกับทีมเขียนเอกสารนี้
Network
SQL Server อยู่คนละ network กับตัวเว็บแอพ ต้องเปิด access เพิ่ม
Next.js Frontend + Backend framework
ความหมาย
เฟรมเวิร์กที่สร้างบน React รวมทั้งส่วนแสดงผล (UI) และส่วน backend (API routes) ไว้ในโปรเจกต์เดียวกัน ไม่ต้องแยกสอง repo หรือสอง deploy pipeline
ทำไมถึงเหมาะ
ทีมผสมความถนัด ไม่มี specialist แยก frontend/backend ชัดเจน การมี stack เดียวที่ทำได้ทั้งสองฝั่ง ลดจำนวนสิ่งที่ต้องเรียนรู้และดูแล นอกจากนี้ API routes ยังใช้เป็นตัวกลาง (proxy) เชื่อมต่อ IWS และ SQL Server แทนที่จะให้ browser เรียกตรง ซึ่งปลอดภัยกว่า
core framework
TypeScript ภาษาที่ครอบ JavaScript ด้วยระบบ type
ความหมาย
เขียนโค้ดโดยกำหนด type ของตัวแปรและข้อมูลชัดเจน ตัว compiler จะเช็คความถูกต้องให้ก่อนรันจริง
ทำไมถึงเหมาะ
ข้อมูลจาก IWS และ SQL Server มี structure ตายตัว (คล้าย fixed field ใน RPG) การกำหนด type ให้ตรงกับ structure จริงช่วยจับข้อผิดพลาดตอน build แทนที่จะไปพังตอน production โดยเฉพาะจุดที่ต้องเขียนข้อมูลกลับ (insert/update) ซึ่งผิดพลาดแล้วกระทบข้อมูลจริง
core language
IWS Client Layer ตัวเชื่อมต่อ IBM i (Integrated Web Services)
ความหมาย
ชั้นโค้ดเฉพาะ (ไม่ใช่ library สำเร็จรูป) ที่เรียก IWS endpoint แล้วแปลงผลลัพธ์ให้เป็น TypeScript object ที่ frontend ใช้งานง่าย เขียนอยู่ฝั่ง Next.js API routes เท่านั้น
ทำไมถึงเหมาะ
IWS เป็นระบบที่ทีมไม่ได้เป็นเจ้าของ schema (RPG program เป็นคนกำหนด) จึงมองเป็น external API แบบอ่านอย่างเดียว ไม่ต้องมี ORM ครอบ เรียกผ่าน fetch ธรรมดาได้ รูปแบบการเชื่อมต่อ (REST/JSON หรือ SOAP/XML) ต้องยืนยันก่อนเริ่มงาน เพราะกำหนด library ที่ต้องใช้เพิ่ม
read only
Prisma ORM สำหรับ SQL Server
ความหมาย
เครื่องมือที่แปลง table ใน SQL Server ให้เรียกใช้งานผ่านโค้ด TypeScript ได้โดยตรง พร้อม generate type ให้อัตโนมัติจาก schema จริง
ทำไมถึงเหมาะ
ฝั่ง admin ต้องเขียนข้อมูลกลับ (insert/update) ซึ่งเป็นจุดเสี่ยงกว่าการอ่านอย่างเดียว Prisma ช่วยจัดการ transaction และจับ column/type mismatch ตอน build ลดโอกาสเขียน ข้อมูลผิด table หรือผิด type โดยไม่รู้ตัว
read + write

Browser ไม่เรียก IWS หรือ SQL Server ตรง ทุกอย่างผ่าน Next.js API routes เท่านั้น เพื่อไม่ให้ credential หรือ endpoint จริงหลุดออกไปที่ client-side

จุดที่ต้องยืนยันก่อนเริ่ม phase แรก

  • IWS endpoint เป็น REST/JSON หรือ SOAP/XML — กำหนด library ที่ต้องติดตั้งเพิ่ม
  • การเปิด network access ไปยัง SQL Server ต้องขอผ่าน infra team ล่วงหน้า เพราะมี lead time
  • สิทธิ์การเข้าถึง SQL Server (user/password หรือ service account) สำหรับใช้กับ Prisma
เอกสารนี้สรุปจากการพูดคุยเรื่อง requirement เบื้องต้น ใช้เป็นจุดเริ่มต้นสำหรับทีมพัฒนา ยังไม่ใช่แผนงานละเอียด (phase / timeline)
