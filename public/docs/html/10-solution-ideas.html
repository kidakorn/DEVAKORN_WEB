10 ไอเดียแก้ปัญหา Version Control

รวมทางเลือกทั้งหมดที่เป็นไปได้ ตั้งแต่ทำเองฟรีไปจนถึงซื้อเครื่องมือระดับองค์กร เรียงจากง่าย/ถูกที่สุดไปยาก/แพงที่สุด
ฟรีeffort ต่ำ
01
Governance checklist (ไม่ต้องมีเครื่องมือใหม่เลย)

แก้ที่ "กระบวนการ" ก่อนแก้ที่ "เครื่องมือ" — ใช้ checklist/sign-off บังคับว่าต้อง promote ทั้งชุดพร้อมกัน

  • ทำได้วันนี้เลย ไม่ต้องเขียนโค้ดหรือรอสิทธิ์ใคร
  • แก้ปัญหา "ลืม promote บางไฟล์" ได้ทันทีด้วยวินัย ไม่ใช่ automation
  • ไม่แก้ปัญหา "ไม่รู้ว่า prod มี version ไหน" เพราะยังไม่มี history เก็บไว้
แผนที่กำลังทำอยู่
ฟรีeffort กลาง
02
DIY Export-to-Git ผ่าน FTP (Path A)

CPYTOSTMF + FTP ที่มีอยู่แล้ว + git บน PC/build server — ไม่ต้องรอสิทธิ์ admin บน IBMi

  • เริ่มได้ทันทีด้วยสิทธิ์ที่มีอยู่แล้ว ทดสอบบน pub400 ได้ก่อนใช้จริง
  • ได้ git history + diff + tag จริง แก้ปัญหา visibility และ version ผสมกันพร้อมกัน
  • ยังเป็น manual/semi-automated จนกว่าจะสร้าง Python tool ตามแผนที่วางไว้
ฟรีeffort สูง
03
Git เต็มรูปแบบบน IBMi (Path B)

ติดตั้ง git จริงผ่าน SSH + PASE + yum แล้ว automate ทั้งหมดด้วย job scheduler บนเครื่องเอง

  • Automate เต็มรูปแบบ ไม่ต้องพึ่งคน FTP
  • ต้องขอ admin เปิด SSH และติดตั้ง yum ก่อน อาจใช้เวลารออนุมัติ
  • เหมาะทำหลัง Path A พิสูจน์ผลแล้วว่าคุ้มค่าลงทุนเวลา
ฟรีeffort ต่ำ
04
Visual LANSA native Git

เปิดใช้ Git ที่มีอยู่แล้วใน Visual LANSA IDE (Editor Options → Version Control)

  • ไม่ต้องสร้างอะไรเพิ่ม มีอยู่แล้วในเครื่องมือที่ใช้อยู่
  • ครอบคลุมเฉพาะฝั่ง Visual LANSA repository เท่านั้น
  • ควรใช้ควบคู่กับไอเดียอื่นสำหรับฝั่ง RPG/CL บน production
ฟรีeffort กลาง
05
RDi + EGit (IDE-based สำหรับฝั่ง RPG)

ใช้ Rational Developer for i (Eclipse) กับปลั๊กอิน EGit จัดการ source ผ่านหน้า IDE แทน command line

  • เหมาะกับคนที่คุ้นเคย IDE มากกว่า terminal
  • ต้องตั้งค่า remote system explorer เชื่อมกับ IBMi ก่อนใช้งานได้จริง
  • ทีมต้องมี license RDi หรือใช้รุ่นฟรีที่มีข้อจำกัดฟีเจอร์
ฟรีeffort กลาง
06
SAVF-based atomic package promotion

แก้ปัญหา "version ผสมกัน" ที่ระดับ OS object โดยตรง — สร้าง save file (*SAVF) รวมทั้งชุด object แล้ว promote เป็นก้อนเดียว

  • แก้ atomicity โดยไม่ต้องพึ่ง git เลย ใช้ CL คำสั่งมาตรฐาน (SAVOBJ/RSTOBJ)
  • รับประกันว่าทั้งชุดไปด้วยกันเสมอ เพราะเป็นไฟล์เดียวจริงๆ
  • ไม่ได้ diff/history แบบ git — เหมาะใช้ "คู่กับ" ไอเดีย 02 มากกว่าใช้แทน
ฟรีeffort กลาง
07
iForGit (open source lightweight client)

เครื่องมือ open source เชื่อม git กับ source บน IBMi ผ่าน RDi/VS Code โดยตรง

  • ไม่มีค่าใช้จ่าย ติดตั้งง่ายกว่าสร้างเอง
  • ชุมชนเล็ก เอกสารและ support จำกัด ต้องพร้อม debug เอง
  • ยังไม่แก้ปัญหา "promote ทั้งชุด" โดยตรง ต้องออกแบบ workflow เพิ่ม
มีค่าใช้จ่ายeffort กลาง
08
SEE/Change (change management + lock)

เครื่องมือเฉพาะทางที่มี checkout/lock จริงจัง ป้องกันคนแก้ object เดียวกันพร้อมกัน

  • แก้ปัญหา "คนแก้พร้อมกันแล้วโดนทับ" ได้ตรงจุดที่สุดในลิสต์นี้
  • มีทั้งหน้าจอ 5250 และ RDi ให้เลือกใช้
  • เป็น change control มากกว่า git-based diff history เต็มรูปแบบ
มีค่าใช้จ่ายสูงeffort สูง
09
ARCAD Skipper / Aldon LMI / ChangeMan ZMF

เครื่องมือ SCM/ALM ระดับองค์กร ครบวงจรทั้ง version, promotion, และ approval workflow

  • ครบที่สุดในลิสต์นี้ แก้ทั้ง visibility, concurrent edit, และ atomic promotion
  • ราคาสูง ใช้เวลา implement เป็นเดือน ต้องมี buy-in จากผู้บริหาร
  • เหมาะทำหลังพิสูจน์แล้วว่าปัญหาใหญ่พอที่จะคุ้มการลงทุน
ฟรี (ถ้ามีของเดิม)effort สูง
10
CI/CD pipeline เต็มรูปแบบ (Jenkins + git)

ต่อยอดจากไอเดีย 02/03 ให้มี pipeline อัตโนมัติเต็มรูปแบบ: commit → build → test → deploy ขึ้น TAI โดยไม่ต้องมีคนกด FTP เอง

  • ลดขั้นตอนมือให้เหลือน้อยที่สุด ลด human error ได้มากสุด
  • ต้องมี test suite รองรับ (เช่น RPGUnit) ไม่งั้น deploy อัตโนมัติเสี่ยงกว่าเดิม
  • เป็นเป้าหมายระยะยาว ไม่ใช่จุดเริ่มต้นที่เหมาะสมตอนนี้

สรุป

ไอเดีย 02 (DIY Export-to-Git ผ่าน FTP) คือแผนที่กำลังทำอยู่ตอนนี้ เพราะสมดุลระหว่างต้นทุน (ฟรี), effort (ทำได้จริงโดยไม่ต้องรอ admin), และแก้ปัญหาหลักได้ตรงจุด (visibility + version ผสมกัน) ไอเดีย 01 (checklist) ใช้เป็นทางลัดชั่วคราวระหว่างรอสร้างเครื่องมือได้ ส่วนไอเดีย 06 (SAVF) เป็นตัวเสริมที่น่าสนใจถ้าอยากการันตี atomicity แน่นขึ้นไปอีกชั้น

เอกสารสรุปทางเลือกทั้งหมด — ใช้ประกอบการตัดสินใจ ไม่ใช่แผนที่อนุมัติแล้ว
